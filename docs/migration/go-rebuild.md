# Go 后端重建与验收清单

## 已确认的决定

- 从需求、API、数据库文档重建后端，不移植旧语言业务实现。
- 运行服务为 `gateway`、`central`、`worker`；`central` 在同一 HTTP 端口按路径承载 user/admin/billing 逻辑模块。
- HTTP 使用 Gin；数据访问使用 GORM 与 `gorm.io/driver/mysql`（复用 go-sql-driver/mysql 连接池），迁移由 Goose 执行。
- Redis 使用 go-redis/v9；JWT 使用 golang-jwt/jwt/v5；精确计费用 shopspring/decimal，入账金额用整数分。
- 微信支付使用官方 wechatpay-go；汇付天下优先验证其 Go SDK 的接口覆盖。
- 暂不做 MQTT。gateway 的 TCP 厂商协议按适配器隔离，不同协议可监听不同端口。附件中的 5.8.9 协议命名为 `dc589`，默认监听 `:9100`。
- 仅有测试数据，允许重建开发数据库。全部业务功能和资金流程验证后一次切换。
- 本轮只交付 Go 后端与接口；原计划不含前端重建；根据后续问题反馈，本轮追加现有 PC 后台页面接口修复和浏览器验收，小程序仍待后续适配。旧 API/数据库文档与新需求冲突时，以《需求分析》和《Go 技术规格》为准并修订契约。
- 区块链存证、国密、特定监管平台等缺外部规范的可选能力先提供可配置边界和本地模拟验收；真实联调待规范到位。支付测试资料、`dc589` 实机及厂商 OTA 回滚证明缺失期间，生产切换保持关闭。

**Webhook 投递**：新增 worker 投递执行器，HMAC-SHA256 签名覆盖「时间戳.请求体」，逐次投递写入 `webhook_delivery_log`（成功与失败都记），4xx 视为不可重试。后台可查日志并人工重发，重发走同一条签名与校验路径。新增 SSRF 防护 `internal/platform/netguard`，在**创建订阅时**即拒绝回环、私网、云元数据与集群域名，投递前再次校验以覆盖 DNS rebinding。

**告警规则**：`alert_rule` / `alert_subscription` 此前为空表。worker 依据 gateway 遥测评估规则，生成 `alert_event` 并向订阅方投递；指标恢复正常自动 `auto_resolved`，同一设备同一规则不重复开单。后台可维护规则与订阅，并批量关闭未处理告警。

**OTA**：`ota_package` / `ota_schedule` 此前仅只读列表。现可登记校验和、发布归档固件，创建灰度/分批计划并触发下发；gateway 按设备建指令、跟踪 ACK 与失败原因，进行中的计划不可归档。重复触发同一计划不会重复入队。

**管理员与安全**：补齐账号编辑、删除、解锁、重置密码（均写入审计，改角色/改密/重置/删号立即失效既有会话）；实现 RFC 6238 TOTP 双因素，登录在口令通过后不下发令牌，而是返回 5 分钟挑战，凭正确验证码才签发会话，错误码计入锁定。实现数据范围（`admin_data_scope`，无记录视为不限制）与字段脱敏（`admin_field_mask`）。迁移 admin 0030。

**导出**：新增异步导出任务，权限在请求与下载时各校验一次，文件 24 小时过期，过期下载返回 410 并删除文件。

**欠费与优惠券**：计费超出预付部分在同一事务生成 `charge_debt`，用户可查看并按实际欠款发起补缴支付，入账按渠道回执幂等。优惠券在支付意图阶段冻结优惠额与应付金额，支付成功后才核销，重放意图不可更换优惠券。

**DLQ 运维**：实现消费者组、重试上限、死信流与滑动游标重放，游标只增不减以保证每轮有前进；worker 新增流深度、死信清单与重放的运维接口。

**脚本修复**：`scripts/test-integration.sh` 使用了 bash 4 的 `${var^^}`，在 macOS 自带 bash 3.2 上直接失败，改为 `tr` 实现，本地与 CI 行为一致。

**浏览器验收发现并修复的真实缺陷**：

1. `alert_rule.threshold` 为 JSON 列，GORM 无法扫入 `any` 字段，列表返回 `null`（页面显示「大于 null」）；改为显式 `CAST(... AS CHAR)` 后按 ID 批量读取。同一问题影响对账 `diffs_json` 与 OTA `target_filter_json`，一并修复。
2. `customer_admin` 未获得 `billing.meter.review`，而账号创建有「不得授予超出自身权限」的护栏，导致平台所有者无法为新账号分配财务角色；补迁移回填。
3. Webhook 订阅创建时无 SSRF 校验，`https://localhost/`、`169.254.169.254`、`10.0.0.5`、`metadata.google.internal` 均可入库；防护前移至创建路径并抽到 platform 供两处复用。
4. MFA 注册链接的 account 用操作者用户名而非目标账号，会让验证器绑定错身份；改为读取目标账号用户名。
5. `finance_reconcile_log` 的 `reconcile_date` 在前端以原生 `date` 控件提交，自动化与部分浏览器无法稳定赋值；改用 antd DatePicker 并在提交时格式化。

**TOTP 与 SSRF 均有单元测试**：TOTP 通过 RFC 6238 官方参考向量（6 位截断值）；SSRF 覆盖 20 个应拒绝目标与 3 个应接受的公网地址，并特意放开 `198.18.0.0/15`（多家开发 DNS 对所有公网域名返回该段，误拦会导致合法订阅被拒）。

**二轮浏览器验收（提现与告警链路）新增修复**：

6. `settlement_party_amount` 没有 `created_month` 列，而可提现余额的 JOIN 引用了 `p.created_month`，导致余额查询必然失败、提现创建恒返回 503；改为仅按 `settlement_id` 关联。

8. 提现审批与打款重算余额时把这笔自己的 pending/approved 单也算作占用，导致运营永远无法通过自己发起的提现；新增 `AvailableCentsExcluding`，审批与打款都排除当前单。
9. `telemetry` 采样结构体的 `Value` 未映射到 `value_num`，告警引擎读到的永远是零值，任何阈值都不会触发；补显式列映射。
10. `webhook_subscription.event_types` 是 JSON 列，无法扫入 `[]string`，投递器每次都报解析错误并跳过；改为按 ID 批量 `CAST(... AS CHAR)` 后解码。
11. 告警通知写入 `event_outbox` 时 `event_id` 是确定性的，重放评估撞唯一键使整个评估失败；改为把 1062 视为已入队。
12. `webhook_delivery_log` 的 upsert 用 `Where+Assign+Create`，MySQL 生成空 `ON DUPLICATE KEY UPDATE` 报语法错误；改为显式冲突列与更新列，并补唯一索引迁移 admin 0032。
13. Webhook 投递日志为空时不显示任何内容，运营无从判断是"没事件"还是"页面坏了"；补空状态说明。
14. SSRF 探测期间在库里遗留了指向 `localhost`、`169.254.169.254`、`metadata.google.internal` 的订阅记录，已清理。

### 2026-09-29 结果通知消费、账单通知与备份恢复

**结果通知消费**：worker 新增退款结果消费者，消费 `refund_succeeded_stream`，把渠道结算结果幂等入账，并在 `comp_tx_log` 写下每一次尝试的补偿台账。资金相关的三步（退款单转成功、写成功回执、累加支付单已退金额）在同一事务内完成；`refund_success_receipt` 以退款单为主键，重投只会命中已有回执。渠道上报金额与申请金额不一致时拒绝入账——那说明事件描述的是另一笔退款。无法解析的报文直接进死信流，不会阻塞消费者组。

**账单通知**：计费完成后由 billing 任务自动开票，金额取自同一份已提交的计费结果，因此账单与实收不可能不一致；开票同时向订单时间线写入 `bill_issued` 事件。新增 `charge_bill` 与 `charge_bill_read` 两张表（user 0033）。用户侧 `GET /user/bills`、`/user/bills/{id}`、`POST /user/bills/{id}/read`；按 `charge_order_id` 唯一，重放计费不会重复开票；查询与标记已读都在 SQL 里限定 `user_id`，他人账单返回同样的 404。

**备份与恢复**：新增 `scripts/backup.sh` 与 `scripts/restore.sh`，并在开发栈上实跑闭环验证。
- 备份会先确认五个 schema 都存在，缺一个就拒绝产出部分备份；生成后做 `gzip -t` 完整性校验，并对明显过小的产物报错。
- 恢复是破坏性的，因此必须设置 `RESTORE_CONFIRM` 且与归档里声明的 schema 列表逐字一致，不一致时拒绝并回显确切的破坏范围；确認后才 DROP 并重建，避免与旧数据叠加。
- 实测：删除验证数据 → 恢复 → 118 张表全部还原、验证数据回到原状。迁移历史存在数据库里，因此恢复后会自动重放 Goose（未提供 `DATABASE_URL_*` 时跳过并提示）。
- 两个脚本在宿主机没有 mysql 客户端时自动改走数据库容器（`MYSQL_CLIENT_CONTAINER`），因此在任何环境都能运行。

**修复**：排查中发现 `clause.OnConflict` 对本项目的分区表无法生成冲突目标，会产出空 `ON DUPLICATE KEY` 并报语法错误；已全部改为显式的存在性检查 + 插入，避免同类问题再次出现。

**恢复后的运维注意事项（实测发现）**：数据库恢复会把管理账号一并清空，而管理员引导只在进程启动时运行一次，因此**恢复后必须重启服务**，否则后台无人能登录。`scripts/restore.sh` 现在会在结尾直接打印重启命令，不再留下静默的锁死状态。实测确认：恢复后 118 张表与全部后台接口均可正常工作，重启后管理员账号自动重建。
