## 2026-09-30 业务编码清理:只删了真正冗余的那几列

上一节删的是站点编码。这一轮按"删掉多此一举的编码"继续,结果是**28 列里只动了 7 项**,其余每查一个就多一个不能删的理由。分类错了三次,记在这里:

1. **`role.active_code` 不是独立字段**,是 `GENERATED ALWAYS AS (IF(deleted_at IS NULL, code, NULL)) STORED` 的生成列,作用是让"编码在未删除行中唯一"可表达——因为 `(code, deleted_at)` 唯一索引表达不了(每个 NULL 都被当作不同)。它支撑的是保留的 `role.code`,删了就废。`coupon.active_code` 同构,但派生自要删的 `coupon.code`,两者一起走。
2. **`scheduled_task.task_code` 是 Go↔DB 的编译期契约键**。`cmd/worker/main.go` 用 `"alert_evaluate"` / `"webhook_dispatch"` 注册 handler,`worker_db/0003` 用同样字符串播种,调度器靠 `s.Handlers[task.Code]` 与库表 join。Go 编译期不可能知道库里的自增 id。原写的 `worker_db/0007` 迁移据此作废,未应用。
3. **`ota_package.code` 是跨版本身份**:`uk_code_version (code, version, deleted_at)` 唯一,没有独立的包父实体。删它要新增分组列,属表结构重设计。`split_party.party_code` 同理——它就是财务引擎里的参与方身份(`finance.Party.ID` 存的是 code 字符串),并被 `settlement` 两张快照表引用。

实际删除(迁移 `admin_db/0045`、`user_db/0037`):

- **`customer.code`**:全应用零引用的死列,只带一个唯一索引。
- **`charge_offer.code`**:由 `offerCodeFor()` 每次上架时从"套餐+站点+设备"派生,只为满足 `uk_station_code`。它还逼着上架路径把 64 字符的设备编号压成摘要才能塞进编码。offer 实际是按 `station_id + device_id` 查的,没人查过编码。
- **`coupon.code` / `active_code` / `coupon_activity_rule.rule_code` / `coupon_redemption.coupon_code`**:核销表原本**只有 code 没有 `coupon_id`**,是字符串外键,迁移先加 `coupon_id` 并回填再删 code。活动规则的 `rule_code` 还在给 `coupon_grant.source_event_id` 当幂等键种子,改用 `rule.id`——行 id 一样稳定,而且不会被运营改掉。

**顺带修掉一个真实缺陷**:`coupon_redemption` 上有 `uk_redemption (coupon_code)` 唯一索引,而核销是按 `coupon_grant` 逐笔发生的、`coupon.total_quota` 明确支持多次发放——**同一张券全系统只可能被核销一次**,与 `coupons.go` 的配额逻辑直接矛盾。删除该唯一键后换为普通索引。

两处踩坑:迁移版本号按迁移日志里的 `current version` 推算,读错了 schema(那行属于 gateway_db),`user_db` 实际已到 0036,写 0010 直接撞版本号 panic;活动规则的错误文案里还留着"规则码 3–64 位",校验删了提示没删,冒烟时才暴露。

验证:`gofmt`/`go build`/`go vet`/`go test ./...`/`tsc --noEmit` 全绿;开发栈应用 0045/0037 后,`admin_db` 与 `user_db` 中残留的 `code` 列恰好只有 `ota_package`、`permission`、`role`、`split_template`、`split_party` 这几个判定为保留的;冒烟覆盖建券、券列表无 code、建活动规则、规则列表无 rule_code、建站、套餐模板创建、上架返回 `offer_id`、offer 列表无 code。测试数据已清理。

## 2026-09-29 站点编码移除与场地/站点术语统一

- **站点不再有编码，统一用主键 `id`**。迁移 `admin_db/0044` 先 `DROP INDEX uk_code` 再 `DROP COLUMN code`，并删除只为保证编码全局唯一且永不复用而存在的 `station_code_identity` 注册表。先删索引再删列是照搬 0041 的教训：复合唯一索引不会随首列删除而消失。
- **顺带修好一个一直坏着的 C 端接口**。`GET /api/v1/user/station/:code` 原按 `code` 查站点，但小程序 `nearby.js:26` 和 `index.ts:55` 一直传的是 `?id=<station.id>`，`docs/api/user.md` 写的也一直是 `{station_id}`——**文档是对的，代码是错的**，该页面此前只有在站点编码恰好等于数字 ID 时才可能打开。现改为按 `id` 查，路由同步改为 `:id`，实测返回 200。
- 后台建站不再要求编码；仍提交 `code` 字段会得到 400「编码已移除：站点统一使用主键 ID，请勿提交 code 字段」，而不是被静默丢弃。设备查询不再返回 `station_code`，站点与设备的关键词搜索也不再匹配编码。
- **`charge_offer`、`split_template`、`permission`、`role` 等其余编码一律保留**：前两者是运营自定业务编码，后两者是 RBAC 词汇表本身（前端到处 `permissions.includes('station.create')`，迁移 0043 也按 `r.code` 匹配内置角色），`port_code` 则是 `dc589` 协议里设备端口的身份。删除范围仅限 `station.code`。
- **术语统一为「站点」**。此前同一个实体在中文里叫「站点」也叫「场地」、英文里 `station` 和 `yard` 混用，最明显的是 `StationPricing.tsx` 同一行里 `title: '场地'` 与 `` `站点 #${r.station_id}` `` 并存。已统一 18 个文件 110 处，SQL 别名 `yard` 与其派生的 JSON 字段 `yard_version` 同步改为 `station_default` / `station_version`（该字段仅本系统前端使用，两端同改）。
- `migrations/admin_db/0042` 与 `docs/pricing-model-0042.md` 中的「场地」**有意保留**：前者是已应用的迁移且含已落库的 `COMMENT`，后者记录的是**客户现有后台**的界面用语，改了就不再是准确的观察记录。
- 验证：`gofmt`/`go build`/`go vet`/`go test ./...`/`tsc --noEmit` 全绿；开发栈应用 0044 后 `station` 只剩 `PRIMARY` 与 `idx_geo`，冒烟覆盖不带编码建站、带编码被拒、C 端按 id 取详情、404 与非法 id。设备列表查询跑在已无 `code` 列的 schema 上仍返回 200，证明无残留 SQL 引用。

**另记：`docs/api/*.md` 存在系统性路径漂移。** 做了一次"文档端点 vs 代码注册路由"的全量比对，代码注册 140 条，文档中 **93 个端点路径在代码里找不到**。分两类：

- **约 82 条是旧路径改名**，功能都在。例如文档 `/api/v1/public/payment/wechat/callback` 实为 `/api/v1/public/payments/wechat/callback`（复数）；文档 `/api/v1/admin/users/{id}/unlock` 实为 `/api/v1/admin/admin-users/{id}/unlock`（改名以免与终端用户 `users` 撞名）；文档 `/api/v1/admin/billing/reconcile-logs` 实为 `/api/v1/admin/billing/reconciles`。代码是经浏览器实测的一侧，以代码为准。
- **11 条确实没有对应实现**，已逐条定性：

| 文档端点 | 定性 |
| --- | --- |
| `GET /admin/export/tasks/{id}`、`GET /internal/export/tasks/{id}` | 导出任务的**单项详情**未实现；列表与下载已覆盖日常使用 |
| `GET /internal/scheduled-tasks/{id}/last-run` | 定时任务的上次执行记录未实现 |
| `POST /admin/settings/split-templates/{id}/parties` | 分账模板的**追加参与方**未实现；模板本身可建可查 |
| `POST /internal/refund-records/claim`、`/execution`、`/{id}/result` | 退款记录的内部操作端点未实现；退款走 worker 消费 Outbox，无此 HTTP 面 |
| `POST /internal/device-sessions/cleanup-idle` | **空闲会话清理未实现，且当前无对象可清**（见下） |

**关于 `device_session` 这张死表**：`gateway_db.device_session` 有完整结构（会话 ID、协议、远端地址、起止时间、结束原因、收发字节与帧数），但**全代码库零引用**——网关只在内存 `protocol.Registry` 里跟踪会话。`Registry.Attach` 正确返回 detach 闭包并在重连时关闭旧会话，**内存不泄漏**，设备上下线判断也正常。所以缺的不是稳定性，是**连接审计**：无法回答"这台设备什么时候、从哪个 IP 连上来、连了多久、传了多少数据"。

同时这也解释了 `cleanup-idle` 为何没有对应实现且当前无对象可清：会话只在内存里，进程重启即清空，一个针对持久化表的清理端点在本架构下没有意义。

**本轮不实现会话持久化**：设备域的验收项是"注册、心跳扩展字段、结算/分档解析、遥测入库及 Outbox"，会话落库不在其中；且它会改动 TCP 接入热路径（每帧计数、每次断连写库），属于需要显式立项的变更，不在验收范围内顺手加。据实登记于此。

**尝试批量修正旧路径后主动停手**：曾写脚本按"末段 + 层级相同"为上述 93 条寻找唯一候选并批量替换，**逐条人工复核时发现多数映射是错的**，已全部放弃，未改动任何文档。典型错例：

- `GET /api/v1/internal/orders` → 被匹配到 `/api/v1/admin/orders`。前者是**服务间调用**契约，后者是**运营端**契约，把内部接口改写成后台接口会直接误导集成方。
- `POST /api/v1/public/refund/wechat/callback` → 被匹配到 `/api/v1/public/payments/wechat/callback`。**退款回调被错配成支付回调**，仅因两者末段都叫 `callback`。这类错误若写进文档，比留着旧路径危险得多——旧路径至少会让人去找，而错误路径会让人照着接错接口。
- `GET /api/v1/internal/settlements/{id}` → 被匹配到列表端点 `/api/v1/admin/billing/settlements`，把取单条换成了取列表。

**结论**：这批差异的实质不是"改名"，而是 `docs/api/*.md` 大量描述的是**重建前服务的服务间内部契约**，而代码实现的是**面向运营的接口**，两者本就不同。必须逐条判断该端点在 Go 重建中对应什么、是否还需要、该由谁调用，属于需要人工阅读契约的修订工作，不能用文本匹配代替。**旧路径保持原样并在此登记，好过被批量改成看起来合理却错误的路径。**

### 2026-09-29 结果通知消费、账单通知与备份恢复

**结果通知消费**：worker 新增退款结果消费者，消费 `refund_succeeded_stream`，把渠道结算结果幂等入账，并在 `comp_tx_log` 写下每一次尝试的补偿台账。资金相关的三步（退款单转成功、写成功回执、累加支付单已退金额）在同一事务内完成；`refund_success_receipt` 以退款单为主键，重投只会命中已有回执。渠道上报金额与申请金额不一致时拒绝入账——那说明事件描述的是另一笔退款。无法解析的报文直接进死信流，不会阻塞消费者组。

**账单通知**：计费完成后由 billing 任务自动开票，金额取自同一份已提交的计费结果，因此账单与实收不可能不一致；开票同时向订单时间线写入 `bill_issued` 事件。新增 `charge_bill` 与 `charge_bill_read` 两张表（user 0033）。用户侧 `GET /user/bills`、`/user/bills/{id}`、`POST /user/bills/{id}/read`；按 `charge_order_id` 唯一，重放计费不会重复开票；查询与标记已读都在 SQL 里限定 `user_id`，他人账单返回同样的 404。

**备份与恢复**：新增 `scripts/db/backup.sh` 与 `scripts/db/restore.sh`，并在开发栈上实跑闭环验证。
- 备份会先确认五个 schema 都存在，缺一个就拒绝产出部分备份；生成后做 `gzip -t` 完整性校验，并对明显过小的产物报错。
- 恢复是破坏性的，因此必须设置 `RESTORE_CONFIRM` 且与归档里声明的 schema 列表逐字一致，不一致时拒绝并回显确切的破坏范围；确認后才 DROP 并重建，避免与旧数据叠加。
- 实测：删除验证数据 → 恢复 → 118 张表全部还原、验证数据回到原状。迁移历史存在数据库里，因此恢复后会自动重放 Goose（未提供 `DATABASE_URL_*` 时跳过并提示）。
- 两个脚本在宿主机没有 mysql 客户端时自动改走数据库容器（`MYSQL_CLIENT_CONTAINER`），因此在任何环境都能运行。

**修复**：排查中发现 `clause.OnConflict` 对本项目的分区表无法生成冲突目标，会产出空 `ON DUPLICATE KEY` 并报语法错误；已全部改为显式的存在性检查 + 插入，避免同类问题再次出现。

**恢复后的运维注意事项（实测发现）**：数据库恢复会把管理账号一并清空，而管理员引导只在进程启动时运行一次，因此**恢复后必须重启服务**，否则后台无人能登录。`scripts/db/restore.sh` 现在会在结尾直接打印重启命令，不再留下静默的锁死状态。实测确认：恢复后 118 张表与全部后台接口均可正常工作，重启后管理员账号自动重建。

### 2026-09-29 后台菜单入口缺失（真因：权限映射缺项，非缓存）

**现象**：告警配置与数据导出两个页面直接访问路由功能完全正常，但侧边栏对**所有角色**都不显示这两项。

**排查过程中的一次误判**：最初怀疑是浏览器 HTTP 缓存加载了旧 bundle。证据是源码、Vite 提供的模块、生产构建产物里都能搜到这两个菜单项，而页面不显示。带 `?cachebust=1` 重新打开、重启与重建容器都没有变化。这个方向是错的——真因与缓存无关。

**真因**：`admin-web/src/layouts/MainLayout.tsx` 用一张并行的 `menuPermission` 映射表过滤菜单，而这两项新增菜单**没有登记对应的读权限**。`menuPermission['/alert-rules']` 得到 `undefined`，`permissions.includes(undefined)` 恒为 `false`，于是菜单项对任何角色都被过滤掉。这类失效的特征是：路由能直接访问、接口 200、构建产物里有文案，只有菜单消失，且控制台无任何报错。

**修复**：
- 按各页面列表接口实际要求的读权限补齐映射：告警配置 `alert.read`（与告警列表同域），数据导出 `finance.read`（导出任务**列表**接口 `/exports` 的门禁）。注意导出的创建、下载与资源列表另以 `export.create` 为门禁，与列表权限是分离的两把钥匙。
- 过滤逻辑在 DEV 下对缺映射的菜单项打 `console.warn`，把这类静默失效变成立即可见的告警。

**权限面校验**：`admin`（角色 `customer_admin`，72 项权限）同时持有 `alert.read`、`finance.read` 与 `export.create`，两项菜单均出现且功能完整；`customer_cs` 两者皆无，两项都隐藏。

### 2026-09-29 钱包充值回调整体失效（资金缺陷，已修复）

为实现"活动"规则引擎而追查首充优惠的触发点时，发现一条**更严重的资金缺陷**：钱包充值付款后，平台回调会直接拒绝，钱包永远不到账。

**链路与故障点**：`POST /api/v1/user/wallet/recharge` 只创建 `payment_order`（`biz_type='wallet_recharge'`）与 `wallet_recharge_request`，**不创建 `payment_intent`**，随后发起预下单。微信异步通知到达时，`PaymentCallbackStore.Apply` 第一步是按 `merchant_order_no` 查 `payment_intent` 并加行锁，查不到即 `ErrPaymentCallbackConflict`。因此每一笔充值通知都被判为"验签支付不匹配意图"而拒绝：**用户已付款、微信已扣款、平台不入账、余额不变**。更糟的是该函数在查到 intent 之后还会无条件创建 `ChargeOrderRecord`，若仅补建 intent 而不分流，充值会造出一条设备为空的假充电订单。

**修复**：把 `payment_order` 提到事务最前按 `order_no` 定位（`merchant_order_no` 对两类业务都是 `order_no`），按 `biz_type` 分流——`wallet_recharge` 走新增的 `settleWalletRecharge`，`charge` 走原有路径并新增 `intent.PaymentOrderID == order.ID` 绑定校验（比原先按 order_no 查更严，防止已验签通知结算到他人订单）。未知 `biz_type` 直接拒绝。

到账事务内依次完成：核对请求归属与金额（请求金额、支付单金额、通知金额三者必须一致）→ 摘要重放校验 → 标记支付单为已付 → 锁钱包行并加余额（乐观锁带 `version`）→ 写 `wallet_txn`（`biz_type='recharge'`，带 `balance_after_cents`）→ 投递 `wallet_recharge_settled_stream` 事件，供后续活动规则挂载。

**两处刻意的设计取舍**：
- **钱包被冻结时仍然入账**。钱已经在渠道账上了，此时拒收等于让客户凭空损失；冻结的语义是"不可支出"，不是"拒绝入账"，所以照常加余额但不放开支出。
- **充值没有 `biz_id` 可绑**。`wallet_recharge_request` 只有 `request_id` 这个业务键，没有代理主键，因此重放判定改用"支付单已 paid + 渠道交易号一致 + 金额一致 + 验签摘要一致"四者同时成立，而不是绑定业务 id。

**过程中自己踩了本项目的经典坑**：新写的查询带了 `deleted_at IS NULL` 且读取了 `id` 列，而 `wallet_recharge_request` 两样都没有——集成测试立刻以 `Unknown column 'deleted_at'` 失败才暴露出来。这是本项目反复出现的"代码假设数据库存在实际不存在的结构"，新代码同样会犯，已由集成测试兜住。

**验证**：`TestVerifiedRechargeCreditsWalletExactlyOnce` 覆盖首次到账（余额 5000、`wallet_txn` 恰好 1 行）与重复回调（返回 `Replayed`、余额不变、**不产生任何充电订单**）；`TestVerifiedRechargeRejectsAmountMismatch` 覆盖请求金额与支付单/通知金额不一致时必须拒绝且余额保持 0。原有两条充电回调测试未回归，`-race` 全量 20 个包全绿。

### 2026-09-29 活动规则后台页面与审计写入 schema 缺陷

**活动规则后台页面**：上一节只给了接口，运营在后台点不到，等于管不了。已在优惠券页增加「活动规则」标签页：列表（规则码/触发/活动券/门槛/预算与单人上限/已发放/窗口/状态）、新建、按状态启停，并显示每条规则的实际发放量。浏览器实跑：进入页面 → 停用 → 状态与按钮在停用/启用间正确切换 → 启用恢复，数据库与审计逐条对上。

**过程中一个反直觉的 bug**：快照最初返回 base64。排查时先怀疑 MySQL 的 `json` 列二进制返回，加了 `CAST(... AS CHAR)` 无效；又怀疑 GORM 复用 Count 的 statement，重写了查询构造仍无效。真正原因是响应结构体把字段声明成了 `*[]byte`，而 `encoding/json` 对 `[]byte` 一律序列化为 base64。**教训：base64 症状指向 Go 侧的类型声明，不要先去改 SQL。**


### 2026-09-29 活动规则触发点补挂（满减与节日）

上一节把引擎做完却只挂了首充，满减与节日的触发点空着——引擎再完整，不挂上去也不会发券，属于典型的"写了但没生效"。

### 2026-09-29 遥测聚合落地（修正长窗口静默截断，并推翻上一条结论）

上一节把"聚合表是死 schema"当作结论记下，并判断不值得为无消费者的表增加热路径开销。**这个判断在发现真实缺陷后被推翻。**

**触发重新评估的缺陷**：曲线读原表用的是 `ORDER BY ts DESC LIMIT limit*8`，而 `MaxWindow=24h`、`MaxPoints=2000` 即上限 16000 行。设备约 5 秒一采、每次写多个指标（电表、功率、信号、电压、温度），24 小时约 5 万行。取最新 16000 行、按秒归组后，**用户申请 24 小时曲线只会拿到最近约三分之一的时间段，响应里没有任何提示**——运维看不出来，用户也只会以为"那段时间没充电"。这不是一张没用的表，而是一个正在悄悄返回错误结果的用户可见功能。

**教训**：把"当前没有消费者"当成不实现的理由时，先确认那条消费路径本身是不是已经坏了。上一轮正是从"聚合表是死 schema"这个正确的观察出发，得出了错误的结论。

**写入**：新增 `internal/gateway/store/aggregate.go`。TCP 路径（`insertMeasurements`）与断线补传路径都在**同一事务内**写聚合，保证不会出现"聚合声称有的样本原表没有"。每条路径每事件每粒度各一条语句批量 upsert，不是每个指标一条——否则聚合写入会主导设备帧的处理成本。

**冲突目标必须显式写出**：两张表按 `bucket_month` 分区且 `uk_bucket` 包含该分区键，让驱动自行推断冲突目标会生成空的 `ON DUPLICATE KEY`（本项目此前已在分区表上踩过这个坑）。因此列清单显式给出，更新语句用滚动均值：

```
avg_value = (avg_value * count + VALUES(avg_value) * VALUES(count)) / (count + VALUES(count))
min_value = LEAST(min_value, VALUES(min_value))
max_value = GREATEST(max_value, VALUES(max_value))
count     = count + VALUES(count)
```

滚动而非覆盖是必需的：设备重发同一帧时聚合必须如实累加，否则均值会漂移。

**读侧**：`chooseSource` 按窗口与点数预算选表。预算够就继续走原表保留逐秒细节（细节永远比汇总好，只要负担得起）；超出则走聚合，6 小时以上用小时、否则用 15 分钟。估算刻意偏保守（按每秒 4 行），宁可过早切换到汇总，也不要重现静默截断——这两个方向犯错的代价不对等。

**响应新增 `granularity`（`raw`/`15min`/`hourly`）与 `bucket`**：调用方必须能分辨自己看的是逐秒还是汇总，否则一条 24 小时曲线被降采样后与逐秒曲线长得一模一样，没人会察觉细节已经没了。

**验证**：集成测试真实执行——同桶 3 个样本折叠为一个桶、均值 200、极值 100/300、设备级指标落 NULL 端口而非端口 0、小时粒度同样正确；再喂一次同一样本后 count 变 4 且滚动均值为 175，证明累加而非覆盖。端到端实跑：1 小时窗口返回 `granularity=raw` 361 点全细节，12 小时窗口返回 `granularity=hourly` 12 点且完整覆盖 12 个小时。

**后续补齐**：`docs/api/gateway.md` 描述的 `historical-curve` 端点现已实现。central 校验订单归属并传入设备、端口与精确订单时间窗；gateway 读取聚合表并给出摘要。聚合桶边界可能包含相邻会话的样本，响应通过 `boundary_approximate` 标明；订单精确结算电量来自 central 的订单记录。


### 2026-09-29 指标导出落地（/metrics）

上一节把"指标导出"列为未完成，理由是需要运维选型。**选型确实还没做，但端点本身不需要等**：暴露指标和决定用什么阈值告警是两件事，前者现在就能做，后者仍然是运维决策。把它整项挂在"等选型"下面，等于用未来的决定阻塞今天就能交付的部分。

### 2026-09-29 角色与权限管理补齐（RBAC 此前只有强制、没有管理）

扫描文档端点与代码路由的差异时，发现 `GET /api/v1/admin/roles` 与 `GET /api/v1/admin/permissions` 在 `docs/api/admin.md` 里有、代码里找不到。查证后结论要分两半说。

**已经存在的**：角色列表**早就实现了**。`internal/central/admin/operations.go` 有一个通用只读资源注册辅助 `get(名称, 权限, 表, 列, 软删除)`，其中一行就注册了 `GET /api/v1/admin/roles`，只返回 `id,code,name`。前端建号弹窗的角色下拉一直靠它填充。`role.create`、`role.update`、`role.delete` 三个权限也早已在种子数据里。

**缺失的**：
- 角色列表只有三个字段，**看不到该角色持有哪些权限、下面挂着几个账号**——运营无法判断"财务"到底能做什么。
- **权限字典端点不存在**，因此权限体系对运营是黑盒。
- **没有任何创建或调整角色的入口**。三个 `role.*` 权限没有消费者，只能靠改数据库或发版迁移。新岗位进来无法配一个只读角色，权限模型实际上是写死的。
- `docs/api/admin.md:323` 写着"新建角色需在角色管理中授权"，指向一个不存在的界面。

**实现**（`internal/central/admin/roles.go`）：
- `GET /api/v1/admin/roles` 升级为返回 `id/code/name/description/is_builtin/permissions[]/user_count`，**门禁保持 `admin_user.read` 不变**——建号弹窗已在用这个端点，收紧门禁会打断所有非超管的建号流程，新字段是原三字段的超集。通用辅助里那行重复注册已移除（否则 gin 直接 panic 拒绝启动）。
- `GET /api/v1/admin/permissions` 返回全部 75 条权限字典，按模块排序。
- `POST /api/v1/admin/roles`、`PUT /api/v1/admin/roles/:id`，门禁用**早已存在却无人消费的** `role.create` / `role.update`，没有新增权限编码。

**安全边界**：写操作的规则与建号一致——**只能授予自己已持有的权限**。没有这条，`customer_admin` 可以拼出一个从未有人审阅过的权限组合塞给账号，审计日志还会如实记下这次提权。实跑确认：用 `qa_finance` 调 createRole 返回 1003，读权限字典返回 403。

**内置角色的权限被锁定**：四个内置角色承载运营自身的访问权，允许改它们的权限集意味着最后一个管理员可以把自己锁在门外。因此内置角色只可改名称与描述，权限集冻结，接口返回 `permissions_locked` 明确告知。

**一次自我纠正**：我最初判断"RBAC 完全没有实现"，依据是 grep 字面路径没命中。实际路径由辅助函数拼装，字面搜索漏掉了它。**结论发出去之前应该用运行中的系统确认，而不是用一次文本搜索。**这次还顺带发现我一度新增了重复的 `role.read`/`role.manage` 权限——种子数据里本来就有 `role.create/update/delete`，多加既冗余又与既有命名不一致，已回滚该迁移并改用既有编码。

**补做 `DELETE /api/v1/admin/roles/{id}`**：上一条把它记为"需要显式决策、不顺手做"。复核后认为这三件事都有明确且安全的默认，不必等决策：
- **内置角色不可删**：它承载运营自身的访问权，删掉可能把最后一个管理员锁在自己的控制台外。
- **仍有账号在用的角色不可删**：那些账号会在删除的瞬间静默失去全部权限。让运营先改派、再删除，比替他默默做完要好。
- **不能删自己正在使用的角色**：同一后果的另一条路径。

行做软删除（表已有 `deleted_at`），这样审计与历史操作人名称仍能解析；`role_permission` 同步清理。实跑：内置角色 409、不存在 404、空角色成功（软删除生效、列表不再出现、审计留下 create/delete 成对记录）。

### 2026-09-29 设备会话审计落地（总表第 8 项与 cleanup-idle）

`gateway_db.device_session` 此前结构完整但全库零引用，网关只在内存 `protocol.Registry` 跟踪会话。内存不泄漏、上下线判断正常，缺的是**连接审计**：无法回答"这台设备何时、从哪个 IP 连上、连了多久、传了多少数据"。

**为什么这样设计计数路径**：逐帧写库会把一次数据库往返放进 TCP 读循环，一个狂发帧的设备就能拖垮自己的连接。改为**内存原子计数、断连时单次落库**。进程被强杀时正在计数的会话会丢行，这是有意的取舍：审计问题是"这条连接活了多久、搬了多少数据"，丢行可恢复，卡住的 socket 不可恢复。

**会话标识用注册应答里发给设备的服务端 session 字节**（设备此后每帧回带），而不是自增 ID：重连因此产生**新行**而不是覆盖上一条，审计才看得到断线次数。

**关闭原因**按真实退出路径分类，不是一个笼统的 `error`：`read_timeout`（读超时）、`protocol_error`、`replaced`（被新登录挤掉）、`context_ended`、`device_closed`。`Registry.Attach` 新增可选回调，**仅在确实替换掉旧连接时**触发，因此"被替换"不会被误记成设备主动断开。

**分区键取会话开始时间**，不取结束时间：跨零点的会话整条归属开始那天，若按结束时间推导，同一 session 的写与后续读会落在不同分区。新增测试专门覆盖 23:59 开始、00:01 结束这一情形。

**upsert 显式查存在性再写**：`device_session` 是分区表，推断冲突目标会生成空 `ON DUPLICATE KEY` 并被 MySQL 判为语法错误——这是本项目已踩过的坑（`clause.OnConflict` 同样在遥测表上失败过）。重复关闭按更新处理且不算失败：重连风暴与重试都会走到这里，第二次写携带相同的终值。

**落库失败不掩盖协议错误**：defer 里用的是 `context.WithoutCancel`，且不改写 `ServeConn` 的返回值——设备该断照断，审计写不进去不会变成"因为数据库满了所以设备连不上"。

**`SessionRecorder` 与 `Sink` 分开**：会话只在连接结束后才已知，把写会话塞进 `Sink` 会逼所有适配器实现它。未能实现该接口的 sink 会被安静跳过，而不是拒绝服务设备。

**补齐 `POST /internal/device-sessions/cleanup-idle` 及配套的 `GET /internal/device-sessions`**：前者清理**进程崩溃**遗留的未关闭行，后者先列出待清理对象供人工确认，再决定是否执行。只处理 `ended_at IS NULL` 且静默超阈值的行，**已正常关闭的会话永不重写**（其计数已是终值，重打会篡改真实记录）。清理与判定在同一事务内，且每行更新再次校验 `ended_at IS NULL`，避免与活着的进程抢同一行；单次限量以免长事务。

**验证**：`go vet ./...`、`-race` 单元测试（计数正确性、零帧会话仍留可用行、8 goroutine 并发计数不丢数）通过；`scripts/test/integration.sh -race` 真实 MySQL 通过，覆盖插入落库、重复关闭幂等、跨零点分区键、缺失身份被拒、只清理遗弃会话、重复执行为 no-op、越权 401。

**真实数据库揪出的三个问题（都是只在跑库时才暴露的）**：

1. **`protocol` 列是 `ENUM('tcp','mqtt')`，我却写了适配器名 `dc589`**，MySQL 直接截断报错。这不是笔误而是**语义错配**：该列回答"这台设备用什么方式接入"，厂商身份从 device 行就能关联到。已改为显式的 `Transport` 类型与常量，适配器名不再有地方能传进这一列，并补了一条断言守住这个词表。
2. **`created_month` 是 DATE 而非字符串**，按带时分秒的时间戳比较会静默匹配不到行。分区键的推导与比对都必须归一到当天零点。这条在 store 层和 cleanup 端点各犯了一次。
3. **`httpapi.OK` 会把数据包在 `{code, message, data}` 信封里**，而我最初的测试直接把响应体反序列化到顶层结构，于是永远读到 0。是**测试写错、不是处理器错**——我一度以为是端点没生效，专门加临时测试打日志才定位到。教训：断言失败时先确认是"实现错"还是"断言错"，别直接改实现。

**如实说明三点**：一是这批验证用的是**本地模拟设备**，未做真实断网与进程强杀演练，进程被 SIGKILL 时的行丢失行为只有代码路径保证、没有实测；二是空闲阈值为默认 15 分钟，属基准值，未按客户实际流量校准；三是全量 `-race` 并行跑时 `TestScheduledTaskLeaseLogAndTrigger` 偶发失败，单独连续跑三次均通过，且该测试与本次改动无交集，属既有偶发而非本轮引入。

### 2026-09-29 本地模拟设备（dc589 设备侧实现）

此前"模拟设备"只有两种：一是 Go 集成测试里的一次性连接，二是 `scripts/*.ps1` 走的 **JSON 行**演示通路——后者虽然也连 `127.0.0.1:9100`，但根本不是 5.8.9 二进制帧。**没有可复用的、走真实协议的独立设备实现**，而没有厂商硬件就无法端到端走充电闭环。

**先补齐了编解码的另一半**。原 `dc589` 包只有服务端侧：设备要发的 A0/A4/B8/BA/BB/C0/A8 编码全缺，设备要读的 B7/B9/A1 解析也全缺。新增 `device.go` 补齐，并加 `RemoteResult`/`TimeRequest`/`TimeReply`/`ChargingBand` 常量，取代散落的十六进制字面量。**每个编码函数都以对侧解析函数写往返测试**（设备 Build ↔ 网关 Parse 必须完全一致），这是防协议漂移的关键——字段挪位不会编译失败，但往返测试会失败。编解码留在 `dc589` 包内而非复制进模拟器，就是为了保住单一实现。

**顺带暴露一个真实约束**：注册帧的设备号是 8 字节 BCD，即**恰好 16 位十进制数字**（厂商样例 `5348240514082652`）。而建档接口的正则是 `^[A-Za-z0-9_-]{8,32}$`，**允许字母和下划线**。也就是说 `QA-DEV-A001` 这类设备能建档成功，却**永远无法通过 dc589 注册**。这不是模拟器的问题，是现有两条规则的缺口，已如实登记；未擅自收紧建档正则，因为那会让现存的字母设备号无法再建档。

**模拟器按协议分包**：`internal/gateway/simulator/dc589`（包名 `dc589sim`）与 `cmd/simulator-dc589`。第二个厂商或 MQTT 板子各自另起一个包与命令并列，而不是在本实现上加 flag——不同协议能表达的行为并不相同。包名取 `dc589sim` 而非 `dc589`，是为了它仍能 import 自己实现的那个协议编解码包。

**模拟器不是网关的 mock，而是同一契约设备端的第二种实现**：真实 TCP、真实 5.8.9 帧、服务端侧的 `TCPAdapter` 原样解析。计量按每秒推进、订单号从 B7 原样回送到 BB（B8 字节，板子不解释它，回声才是把结束帧绑回订单的依据）。

**七个场景**：`by-energy` / `by-time` / `stop-on-command` / `reject-start`（驱动退款路径）/ `fault` / `silent`（验证读超时与遗弃会话清理）/ `reconnect`（验证会话替换与连接审计）。

**验证**：编解码往返单测 + 五个端到端测试，**全部对真实 `dc589.TCPAdapter` 走真实 TCP socket**，`-race` 通过——注册心跳、B7→B8→计量→B9→BB 全链路、拒绝启动、故障上报、重连。CLI 参数校验也覆盖：设备号非 16 位数字、场景名拼错都会给出可操作的错误而不是连上去被拒。

**如实说明**：
- 这**不能替代实机联调**。模拟器证明的是编解码与会话逻辑自洽，**不覆盖**帧时序、电气量程、对时精度、厂商固件的边界行为与异常断电。总表第 4 项仍保持未解除。
- 端到端测试中的订单号是自造的，**未验证与真实 `charge_order.id` 的绑定**——那需要支付与计费落库，属于另一个端到端脚本的范畴。
- 未接入 `compose.dev.yaml`（按确认只做独立二进制），也**未在浏览器/后台做过可视化验收**。

### 2026-09-29 充电套餐：模板与站点实例拆分

原"充电方案"把套餐和站点绑在一起：`charge_offer.station_id` 为 NOT NULL 且唯一键是 `(station_id, code)`，**创建时就必须指定站点**，界面还是一个原始的"可售站点 ID"数字输入框。运营的诉求是两步：先建套餐，再决定应用到哪个站点。这是数据模型变更，不只是加个按钮。

**拆成两层**（迁移 `admin_db/0039_charge_package.sql`）：

- `charge_package` —— 套餐模板，名称/编码/方式/价格/状态，**不含站点**，自身不可售。
- `charge_offer` —— 站点实例，即用户实际能买的条目，**结构与小程序查询链路完全不变**（`pricing/offer.go` 仍按 `station_id` 查，新增 `package_id` 关联）。
- "应用到站点"= 把模板的值**复制**一份落到该站点。

**复制而非引用是刻意的**：套餐改价不得回溯改变某站点已经在卖的价格，也不得影响已付款订单的结算快照。集成测试专门验证了这一点——改完套餐后已应用的 offer 价格纹丝不动。

**拒绝重复应用**（唯一键 `uk_package_station`）：同一个套餐应用到同一站点两次会被 409 拒绝。否则小程序端会出现两条无法区分的可选项。为让这个拒绝**可被发现而不是只能撞上去**，套餐列表直接带出"已应用站点"列。

**停用套餐不允许应用**：否则会在站点上落下一条谁也买不到的记录，运营只会觉得是"应用了但没生效"。停用应先启用再应用。

**接口路径按要求一并改为 `charge-packages`**：`GET/POST /api/v1/admin/settings/charge-packages`、`PUT .../:id`、`POST .../:id/apply`。**旧的 `charge-offers` 管理端 CRUD 予以保留**——库中仍存在 `package_id` 为空的存量 offer 属于早期数据，直接删除管理入口会让它们无法维护；新界面已不再调用它。这是一处已知的模型不一致，清理时机由运营决定。

**界面**：列表从"站点维度"改为"套餐维度"，新增"应用到站点"操作，弹窗内站点下拉支持输入编码/名称/地址筛选（复用 `GET /admin/stations?keyword=`，只取运营中站点，因为停用站点不应新增可售套餐）。价格输入与展示改为**元**，存储仍为整数分。菜单与页面文案统一为"充电套餐"。

**验证**：`scripts/test/integration.sh -race` 真实 MySQL 通过，覆盖"建套餐不产生任何 offer"、参数校验、应用成功、重复应用 409 且 offer 数量不变、改套餐不影响已应用快照、过期版本 409、停用套餐拒绝应用、列表回带已应用站点、越权 401。另在开发栈实跑：建套餐 → 应用于站点 → 重复应用被拒 → 列表显示"套餐验收站点（3）"→ offer 行 `package_id=1, price_cents=3000, status=active`，验收数据已清理。

**待人工验收**：弹窗的站点筛选与保存交互**未在浏览器点过**（需人工登录）。

### 2026-09-29 计费规则同样拆为模板与站点实例

按运营要求，计费规则与充电套餐采用**同一套业务流程**：创建时不绑定站点，之后再"应用到站点"。

**迁移 `admin_db/0040_pricing_rule_template.sql`**：新增 `pricing_rule_template`（名称/模式/分时/服务费/起步价/状态/版本，无站点），`pricing_rule` 增加 `template_id` 并保持原有语义不变——**它本来就是按站点版本化的实例表**，计费侧 `ActiveStationRule` 仍按 `station_id` 取生效中最高版本，计费结果仍存 `pricing_rule_id + version + 快照`。

**应用是复制而非引用**：模板改价不回溯改变某站点正在执行的规则。实测验证：模板起步价 50 分时应用出 v1，随后把模板改成 88 分，v1 仍是 50 分；停用后重新应用才得到 v2=88 分。

**重复应用按运营要求直接 409**，与充电套餐一致。相应地，**站点改价必须先停用现行规则再重新应用**——因此"已应用"是对**生效中**那一行的检查，而不是表上的唯一约束；`pricing_rule` 仍按站点累积历史版本（旧的停用、新的生效），与改造前行为相同。界面的提示与确认文案都写明了这一步。

**停用分两层**：停用模板只阻止再次应用，**不动已应用站点的现行规则**（否则站点会突然没有费率而无法发起支付）；停用站点规则只影响该站点。两者各自独立。

**移除了 `POST /api/v1/admin/settings/charge-rules`**：这条接口让创建时就绑定站点，与新流程冲突。原有的验收测试已改写为走"建模板 → 应用"，并完整保留了它原先覆盖的行为：幂等重放（同 request_id 返回同一条并带 `replayed:true`）、`expected_version` 冲突 409、版本递增、旧版本自动停用、无权限 403、非法时段 400、停用幂等、并发应用只有一方成功。

**两个真实 bug 由这次改造暴露**：

1. **模板读取缺列名映射**。GORM 从 Go 字段名 `Minimum`/`ServiceKWh` 推断出 `minimum`/`service_k_wh`，与真实的 `min_charge_cents`/`service_fee_cents_per_kwh` 对不上，读出来全是零值——**会把一份零价费率静默应用到线上站点**。已改为显式 `gorm:"column:..."` 映射。这与本项目此前在告警 `threshold`、对账 `diffs_json`、OTA `target_filter_json` 上踩的是同一类坑。
2. **并发应用双双成功**。版本原先用 `MAX(version)` 这个**非锁定读**，在 REPEATABLE READ 下读到的是事务开始时的快照，两个操作者会看到同一个旧版本而都判定通过。改为按版本降序取一行并加 `SELECT ... FOR UPDATE`，这样读到的是最新已提交行并会等待对方事务。修复后连续三次 `-race` 跑该用例均稳定。

**界面**改为"规则模板 / 站点规则"两个页签：模板页可新建、编辑、停用、应用到站点（弹窗内站点下拉支持关键字筛选，并提示需先停用）；站点规则页展示各站点当前生效的版本与历史版本，可单独停用。表单金额统一改为**元**（含分时电价与时段服务费），存储仍为整数分。

**验证**：`scripts/test/integration.sh -race` 通过；开发栈实跑 建模板 → 应用 v1 → 重复应用 409 → 改模板不回溯 → 停用站点规则 → 重新应用得 v2 且价格已更新，验收数据已清理。**浏览器点击未做**（需人工登录）。

## 2026-09-29 计费域推倒重来（参照乐摇摇模板管理体整体验）

运营提供了真实商用后台（乐摇摇 `b.leyaoyao.com` 模板管理，171 个模板）供体验对照，并明确授权：**项目仍在开发中、无实际用户，允许推倒重来**。本节记录据此做的模型重建。

### 体验到的事实

新建模板是**三步向导**而非一张长表单：① 模板名称(≤20)/备注(≤50)/适用设备/模板类型——「模板类型」实际只有一个值「计费模板」；② 计费方式 → 选计费模式（服务端计费/时长/电量/功率/脉冲共 5 种），模式一变表单整体重排；③ 保存后进只读详情页，只有「禁用/复制/编辑」三个动作。

「服务端计费(实时功率)」的字段树：收费标准（时段 × **低档瓦/高档瓦** × 电费单价元/小时 × 服务费单价元/小时 × **只读合计列**）、**超过最大功率档电费单价 元/度**、充电费率（临时/刷卡 × 电费/服务费 倍数）、按时间充电（时长套餐最低启动余额/规定时间内免费/电费最低消费）、按金额充电、次卡独立套餐、电损率、默认充电方式、在线卡最大充电时长、7 个用户端展示开关。套餐编辑器只有「套餐名称 + 数值」两列，带删除和上下排序。

### 学的与去掉的

**学**：三步向导（4 个基础字段先落地）；**按模式重排表单、只显示该模式有意义的字段**；合计列只读自动求和；超档兜底单价 + 自然语言说明；详情页纯只读、状态切换只有三个动作；展示开关独立成组。

**去**：
- 「模板类型」这层——只有一个值，纯多余的一次点击；
- 「计费方式 → 计费模式 → 子模式」三层嵌套——真实差异只是**谁算账**，做成 7 个平铺选项让用户猜；改为一级单选 `计费基`；
- 套餐内嵌在模板里——运营需要「同一套费率配不同套餐」和「同一批套餐复用到多个站点」，内嵌就废了；ChargePilot 改为套餐作为模板的子实体，随模板整体应用；
- 服务费的三口径 tab（时长和功率/电量/次）——那不是"服务费的收费方式"，是三个不同的**计费基**，不再单独造一层；
- 展示开关 7 个平铺——按充电过程/订单结果/规则说明分组。

**一句话**：学它的界面骨架，不学它的领域模型。它的模型是给设备端老固件兜底的历史包袱，我们是服务端算账，可以更干净。

### 做的

**1. 计费内核合并（P0）**。原 `PriceActual`（结算）与 `EstimateCharge`（预估）是两套独立实现，这正是此前两个真实 bug（GORM 列映射、并发 `MAX(version)`）的土壤。现合并为**单一 `pricing.Cost(spec, usage)`**，两侧只负责把用量整理成 `Usage`。新增五种计费基：

| 计费基 | 口径 | 单价单位 |
| --- | --- | --- |
| `energy` | 时段电价 × 电量 | 元/度 |
| `power_tier` | 梯度功率档位 | 元/小时（折算等效电价） |
| `max_power` | 整场峰值功率 × 时长 | 元/小时·kW |
| `per_minute` | 单价 × 分钟 | 元/分钟 |
| `per_session` | 整场固定金额 | 元/次 |

服务费不再是独立概念，而是 `ServiceMode ∈ {none, energy, minute, minute_power, session}`，即"服务费线套用哪个计费基"。

**2. 语义修正**。原 `min_charge_cents` 是补到 **total** 上的，导致服务费被当作找零垫子被撑大；现改为 `min_electric_cents`，**只兜电费**。新增 `free_minutes`（规定时间内结束则本次免费）、`loss_rate_bp`（电损率）、`multipliers`（临时/刷卡 × 电费/服务费倍数，0 表示不启用，默认 1.0x）。`charge_offer` 复用了 `FreeMinutes` 的短路：`EnergyWh == 0` 直接返回零账单，未用完的预付套餐全额退。

**3. 迁移 `admin_db/0041_pricing_template_rebuild.sql`（破坏性）**。删除 `pricing_rule_template`、`charge_package`，以及**从未被任何 Go 代码引用的遗留表 `pricing_template`**（名称正好复用）。`pricing_rule` 丢弃 `mode/time_of_use_json/service_fee_cents_per_*/min_charge_cents` 五列，改为 `spec_json` + `channel`。新建 `pricing_template`（名称/备注/`spec_json`/`display_json`/状态/版本）与 `pricing_template_package`（模板子表：名称/kind/金额/时长/充满自停/排序/状态）。**原表数据直接删除而非转换**——没有可保留的内容，带过去只会产出新引擎跑不动的费率。

**4. 接口**。`/settings/pricing-rule-templates` → `/settings/pricing-templates`，新增 `GET .../:id`（详情，编辑页与详情页读同一份数据）与 `POST .../:id/copy`（复制变体，不动在跑的模板）。`charge-offers` 降为**只读 + 停用**：手工创建 offer 等于造一个没有对应模板套餐的孤儿套餐。apply 在**同一事务**内写 `pricing_rule` + 复制全部套餐为 `charge_offer`——半套应用会留下一个按没人发布的费率卖的站点。

**5. 界面**（`PricingTemplates.tsx` 取代 `PricingRules.tsx` + `ChargePackages.tsx`）。三步向导；表单**按计费基重排**——`per_minute` 不出现时段表，`power_tier` 才出现档位表，`per_session` 只剩一个金额；全局策略折叠成摘要；详情页只读；金额一律元、存储一律分。

### 新登记的未决项

- **档位收费单位已于 2026-09-30 明确**：实时功率分档电价按元/度，最高功率分档按元/小时；换算下拉已移除。`per_hour_at_ceiling` 仅保留历史规则及快照兼容，旧模板需按原实际等效电价显式转换后再发布。详见 `docs/api/go-admin-pages.md`。

1. **🔴 阻塞：真实设备登录后必然被断链。** 5.8.3 工作流程明文要求 A0 登录后必发 `0xC7` 获取计费模板，而 `dc589/adapter.go` 的 `default` 分支对未知指令 `return error`。现有集成测试与模拟器不按该流程发 C7，因此掩盖了该缺陷。

## 2026-09-29 0042 收口：把三处「建模了但没接线」的地方真正接上

前一轮把内核、协议、迁移、后台、前端都写完了，但**有三处是建模完成却没有调用方的**——它们在测试里全绿、在生产里一行也不执行。这一节是专门为这三处做的，也是本轮验收的重点。

### 一、协议能力授权：默认拒绝，且在设备进门时就拒

`device_meta` 早就有 `reports_energy` / `reports_segmented_power` 两列，但**没有任何代码读过它们**。现在 `capabilityBlock()` 把六种计费方式逐一映射到需要的计量能力：

| 计费方式 | 需要的能力 |
| --- | --- |
| `device_duration` | 无——桩端自己计时 |
| `server_energy` / `device_energy` | 上报电量 |
| `server_realtime_power` / `server_max_power` / `device_power` | 上报分段功率 |

三处调用点：

1. **apply 前**：`checkMetering()` 逐台核对，**每台不合规的设备都按编号点名**，而不是笼统说「部分设备不支持」。整场拒绝，不做「跳过不合规的那几台」——那会让它们继续按旧价计费而没有任何日志说明。
2. **候选列表**：`pricing-template-candidates` 带上 `unavailable_reason`，让运营在表单填完之前就知道选不了。
3. **设备矩阵**：返回 `charge_mode` / `reports_energy` / `reports_segmented_power`，前端加「计量能力」列。被拒之后至少看得见、也改得动。

**默认拒绝**：未声明能力的设备一律按「什么都不上报」处理。新协议没有承诺的字段就不能假设它有——这条写进了注释，因为它的反面（按「大部分板子都有」来猜）正是这一列要防的事故。

#### 一个自己踩出来的洞，以及补上的位置

我第一版在 apply 里加了「该站点下没有设备就拒绝」。集成测试立刻挂了——而**测试是对的**：硬件到场之前先给场地定价是正常业务。于是撤掉这条拒绝，顺着往下想却发现真正的问题在别处：

> 能力检查只覆盖**发布那一刻已经存在**的设备。空场地先定了一个按电量计费的规则，六个月后到货的板子从未经过那次检查。

所以拒绝挪到了**设备进门的地方**：`checkImportAgainstYard()` 在批量导入时核对场地现行计费方式，**整批拒绝**（一半可计费一半不可的机队，等于给运营留了一份要手工对账的烂摊子）。

### 二、消费封顶接进停机回路

`SpendCapCents` / `StopGraceSeconds` / `DecideStop()` 上一轮就写好了，**但 `DecideStop` 没有任何调用方**——运营设了封顶金额，平台不会停机，钱照扣不误。

新增 `pricing.StopAtMeter(rule, meter)`，接进 `AutoStopper`。它复用 `PriceActual` 的**同一套电表校验**（把这段抽成 `usageFromMeter`），所以封顶是在「一张能用来结算的电表」上判的，而不是在更宽松的读数上——否则停机的时刻会和服务端算出来的金额对不上，而且两边单看都不像错。

三个「不决定」也是决定：**封顶为 0 不停**、**设备计费不停**（那是桩端的钱）、**电表不可结算不停**（那是账单复核问题，不是超支问题）。

### 三、协议：心跳超时按设定值算，而不是拍脑袋的常数

`adapter.go` 里那段注释早就写着「读超时应该是三倍心跳周期，不是这个 build 随便挑的常数」——**然后下一行就是 `90 * time.Second`**。注释说对了一件事，代码做的是另一件。现在读超时跟着 `0xA6` 下发的 3 秒走，即 9 秒。

另加 `0xE0`/`0xE1`（`power_control.go`）：**只实现文档写明的 `0 = 移除功率`**，未知操作码由 `ErrPowerOperationUnknown` 按名拒绝而不是猜一个值编出去。`0xE1` 参数位回 `0xFFF1` 按失败标记处理（登记未决项 28：这个标记本身未在实机验证过）。

### 刻意没做的，以及为什么

- **`0xB4`/`0xB5`/`0xB6`/`0xBD`/`0xD0`/`0xD1`**（投币与在线卡）：仓库里**没有这六条指令的字段表**，只有指令名。凭指令名编帧就是把猜的东西送进生产。现状由 P0 的「未知指令不断链」兜住——板子发这些帧不会断链，只会被记录。**登记未决项 29，等厂商字段表。**
- **12 路以上双包合并**（未决项 25）：文档自相矛盾（「12 路以上」却写「前十路 + 后十路」，A4 说前 12 个相同、B1 说前 9 个相同），**必须实机确认才能写**。

- `./scripts/test/integration.sh -race` 全绿（`internal/central/admin` 8.8s）。

## 2026-09-29 电川协议对照（以 5.8.9 全文为准，撤回上一版 P0 结论）

运营先后补充《电川 5.8.3》《电瓶车对接协议 5.8.9（2024.11.28）》两份协议全文。**定论报告见 [`docs/protocol/dianchuan-589-vs-dc589.md`](../protocol/dianchuan-589-vs-dc589.md)**，基于 5.8.3 的初版报告已被取代。

**先说更正**：初版依据 5.8.3 工作流程判定「设备登录后必发 `0xC7`，`dc589` 的 `default` 分支会直接断链，判定为 P0 阻塞」。**该结论撤回**——5.8.5 变更记录明写「修改工作流程不向平台发送 `0xC7` 指令」，5.8.9 流程为「连接 → `0xA0` 登录 → 发送心跳」。**教训**：厂商协议有版本，且**行为约定（如工作流程）会随版本直接反转，而字段表里看不出来**。拿到协议必须先读变更记录。

**保留的结论**：

1. **配置下发通道确认存在**：`0xC3` 下发参数表、`0xC4` 返回 **13 个分类错误码**（含「刷卡时间/电量超范围」「刷卡金额超范围」「分档功率设置错误」「分档比例值设置错误」），`0xC5`/`0xC6` 可回读校验。这确定了**未决项 17 的实现路径**：下发失败是可分类到具体字段的，不必笼统记「下发失败」。`0xC3` 长度存在 **33 字节（5 档机型）/ 43 字节（8 档机型）二义性**，不能写死校验。
2. **`10/11/12` 确认为长充模式**（初版存疑项已消除），但文档明写「**此模式正常状态下不使用**」。当前 `BuildStart` 接受 6 个值且 `ChargeMode` 是直接类型转换，**上层误传会被原样下发**。
3. **5.8.9 唯一计费语义变更：本地电量计费模式**。参数表第 1 项新增 `3=电量先消费`、`4=电量先按键`；第 3/4 项「本地投币/刷卡一次**时间/电量**」的单位**随运行模式改变**（时间模式 `1=1 分钟`，电量模式 `100=1Kwh`）。**同一字节值 `240` 在两种模式下差 100 倍**，是最容易造成金额误差的一处。
4. **停止失败不告警**（现存缺陷）：`gateway/store/mysql.go` 对 `0xBA` 返回的 `0x00`（无此端口）与 `0x04`（端口故障）直接 `return nil`，命令永远停在 `stopping` 且无任何告警——正是未决项 23 要求的「停止失败必须显式告警」。
5. **端口遥测能否收到取决于板子默认值**：`0xA6` 的「是否上传端口状态」开关由平台下发，dc589 从不发送 `0xA6`。**能解析 ≠ 能收到。**
6. **12 路以上主板心跳为双包**，`dc589` 不合并两包，每条心跳记录只含一半端口明细而「正在充电端口数」是全量。文档在该处自相矛盾（前 12 个 vs 前 9 个相同、12 路 vs 前后十路），合并规则需实机确认。

**dc589 已实现的 17 条指令逐字节核对无误**——帧格式、各指令长度、字段偏移、单位、校验全部与 5.8.9 吻合，包括每端口 13 字节步长与 `0xBB` 全部 44 字节偏移。**问题始终只在覆盖面：5.8.9 共 36 条指令，未实现 19 条。**

**仍未确认**：仓库此前没有 5.8.9 文档的判断已不成立，但**实机相关项全部仍未验证**——`0xC3` 长度、`0xC4` 应答是否必达、双包合并规则、心跳超时合理值、`0xE0` 操作类型全集。`未决项 22`（功率是独立类型还是分档修饰）**保持未决**，但已可排除「协议存在按功率的独立充电类型」这一支。

## 2026-09-29 计费域建模修正（0042，实测驱动）

0041 的模型只基于「模板管理」一个页面推导。本轮补做了乐摇摇「套餐设置」**全部三层页面 + 切换记录**的完整体验，**推翻了 0041 的三处结构性错误**。

> **完整方案见 [`docs/pricing-model-0042.md`](../pricing-model-0042.md)**，含逐项实测证据、字段清单、建模代码骨架与落地顺序。本节只记结论与对 0041 的修正关系。

### 推翻 0041 的三处结构性错误

| 0041 做法 | 实测真相 |
| --- | --- |
| 5 种计费基拍平成一级枚举 | 真实是**两类六种**：主轴是「谁计费」（服务端 / 设备），服务端侧再分按实时功率/按最大功率/按电量，设备侧分时长/电量/功率档位。**电量两侧都有且不是同一个东西**。**脉冲只出现在桩侧，网关侧没有**，是桩端硬件计费不是服务端模式，本轮不做 |
| 服务费是 `Spec` 上的一个枚举字段 | **电费与服务费是两条独立的线**，各有开关（分处两个界面）、各有计费基、**可自由组合**（电费按度 + 服务费按小时 同时成立） |
| 套餐内嵌在计费模板下 | 套餐是**独立模板池**（170+ 计费模板的「选择模板」弹窗 + 设备页独立的「添加套餐」入口），同一费率可配不同套餐、同一批套餐可复用到多个场地 |

### 新发现的两个真实机制

**链式切分**（两处）：档位的低档/高档除末档外全部灰显，由系统保证首尾相连；时段改一个结束时刻即自动派生出下一段（如 24:00 改 09:30 → 自动生成时段2 09:30~24:00），时间粒度 30 分钟。**这两处都在 UI 层杜绝了区间重叠/断档**——而这类脏数据会直接导致漏算电费。存储应记链式边界（每档结束瓦数、每段结束时刻）而非独立的高低档/起止对。

**下发是异步任务**：切换记录有「设备明细 / 任务记录」两页签，记录状态（成功·进行中）、操作人、**切换前后计费方式**、每设备处理进度，设备切换明细页还给出**下发后的套餐内容快照**。实测存在一条创建后数日仍「进行中 0 台已处理完成」的记录。→ 当前 apply 的纯同步事务假设不成立，已登记为未决项 17。

### 其它实测发现

- **退费是两个正交维度**（退费路径：退至余额/原路退回 × 退费规则：不退款/实时退款/限时退款），卡片上显示为 `限时退款(时效外不退款)-原路退回` 这样的组合串。0042 途中曾误建模为单层枚举，已修正。
- **「充值设置」是充值套餐**（名称≤10字/充值金额/**赠送金额**，6组可增删排序），不是余额门槛。赠送金额是营销玩法，此前完全没这个概念。
- **「电费费率」是倍率**（临时 __ 倍 / 刷卡 __ 倍），且**专属电费线**，与服务费无关。
- **合计列只在两条线同为「元/小时」时出现**——不给不可加的列做假合计，这个克制值得学。
- 场地矩阵有充电桩/充电桩网关两个页签，两类设备计费能力不同。
- 「批量设置」是**跨场地多选**，不是场地内批量。

### 计费方式的分类轴：两类六种（产品口述确认）

产品给出的分类比后台 UI 分组更准：**先分「谁计费」，再分「按什么计」**。

- **服务端计费**（`server_*`）：按实时功率 / 按最大功率 / 按电量——费用由 `pricing.Cost` 按实绩算出
- **设备计费**（`device_*`）：时长 / 电量 / 功率档位——费用在下单时即由用户实付金额定死，桩端把这笔钱花完即停

**「电量」在两侧都出现且不是同一个东西**，这是 0041 把二者混成「电量模式」的根因，必须拆开。建模上拍平成 6 个枚举值而非 `server|device` + 三元组：设备侧三种模式没有任何二级属性，用嵌套结构会造出「设备侧也能填 server_basis」的脏字段；主轴由 `Executor()` 推导，不冗余落两列。协议能力授权只约束 `server_*`（依赖上报实绩），`device_*` 三种不受限——它们要的正是桩端自己能量出来的东西。详见 `docs/pricing-model-0042.md` 6.1 / 6.5.1 / 6.7。

### 桩端三种模式（时长/电量/功率）的业务逻辑（产品口述确认）

后台给设备配模式与套餐 → 用户选套餐支付 → **支付后设备启动时**按所选套餐向设备下发对应内容 → 设备自主消耗 → 耗尽自动停止。三种模式**变的只是桩端拿什么去花这笔已收的钱**：`device_duration` 花时间、`device_energy` 花电量、`device_power` 花**金额**（按功率档位费率实时扣，1 元 ÷ 2 元/小时 = 半小时）。由此确定：设备计费下服务端**不参与任何结算计算**，**设备是执行方而不是计费方**（`device_power` 虽然在桩端做乘除，但算的是「余额够不够」而非「该收多少」）；金额在支付时已由套餐定死，服务端只做「套餐 → 下发什么」这次查表。套餐是「价格 + 消耗口径」的二合一，不可拆成两个独立配置。**「功率档位」是费率表（瓦数 → 元/小时），不是功率控制上限**——这一点纠正了本文早前「设备按功率范围控停」的错误建模，也使未决项 20 的适用范围收窄为时长/电量两种模式。单次充电的控制量下发与「切换计费方式」的异步任务（未决项 17）是两回事。三个展示开关（显示功率/混合模式/隐藏单位）语义仍未确认，判定为只影响桩端展示，已列不做。

### 我在本轮犯的三次同类错误（记录以免重犯）

1. 「按电量没有档位表」——只看了默认单时段就下结论，漏了时段可切分成多条
2. 「按最大功率的服务费没有三个 tab」——在**服务费开关关闭**状态下看的编辑器
3. 「按电量的服务费也没有三个 tab」——犯了完全相同的错

**教训**：判断一个字段「有没有」之前，必须先把它**展开到最终形态**再看。开关关闭态 ≠ 功能不存在。

### 当前状态

方案已落盘 `docs/pricing-model-0042.md`；0042 与 gateway 0009 迁移**已在开发库实跑通过**，后端接口与前端三个页面**已接通并跑通冒烟**。

**本轮新增的三条已在上面「0042 收口」一节记录。** 仍未做的是需要厂商字段表或实机的部分：投币与在线卡链路（`0xB4`/`0xB5`/`0xB6`/`0xBD`/`0xD0`/`0xD1`）、12 路以上双包合并、`0xE0` 操作类型全集、`0xC3` 长度二义性——**这四项都没有编帧，因为编不出可信的帧。**

### 开发栈实跑中抓到的两个缺陷

1. **切换任务接口返回 PascalCase。** `switchTaskRow` / `switchTaskItemRow` 两个结构体**漏了 JSON tag**，Go 于是按字段名输出 `TaskNo` / `ModeBefore` / `DeviceID`。而前端 `StationPricing.tsx` 一直按 snake_case 读——也就是说**「切换记录」那个页签在浏览器里每一列都是空的**。接口冒烟时发现：所有字段读出来都是 null。已补 tag。
2. **拒绝时写了两个 JSON body。** 能力检查在 `createImport` 里已经自己回了 409，外层的通用错误分支又追着回了一个 5003，两个 JSON 文档拼在一个响应里，任何客户端都解析不了，运营看到的还是笼统的数据库错误而不是「这台板子量不了」。补了 `errAlreadyReported` 的判断（该错误本来就在 `pricing_templates.go` 里定义，只是这个文件没接）。

第 2 条的教训是：**`errAlreadyReported` 是一个必须每个提前返回的 handler 都记得处理的东西，而「记得」本身就是缺陷来源。** 目前只在三个文件里处理，已逐个核对：每个 `return errAlreadyReported` 的 handler 都有对应的判断。

### 提交之后又抓到的一个：协议回执全部落进「未知指令」

提交完 7 批之后按缺陷类型做了一轮复查，发现和上面两个是同一类问题的第三个实例，而且更严重。

本轮给平台加了三组下行：`0xA6` 心跳周期、`0xC3` 参数表、`0xE0` 移除功率。**加了，但它们的回执一条都没接。** 适配器的指令 switch 只认 `0xA8`、心跳、开始/停止应答、`0xBB`、`0xC2`，其余全进 `default`——也就是「记录为未知指令后跳过」。于是：

- 板子拒收参数表（`0xC4` 带 13 个错误码，每个指向具体字段）→ 记成「对端发了我不认识的指令」，**原因消失**。这恰恰是运营最需要看见的一种情况：板子会继续用它原来的值跑，会话看起来一切正常。
- `0xA7`（心跳周期应答，平台自己刚发出去的 `0xA6` 的回执）→ 同样是「未知指令」。
- `0xC6`（板子主动上报当前参数表）→ 同上。
- `0xE1`（功率控制被拒）→ 同上。

上一轮修 `0xBA` 的 `0x00`/`0x04` 时我说「把拒绝当成无需处理，导致看不见」——**同一条路我只修了一条，另外四条原样留着**，而且新加的三组下行正好各自配了一条这样的路。测试里之所以没发现，是因为**平台从来没发过这些下行，所以这些回执在测试中从未出现过**——和 `DecideStop` 一模一样的成因：建了模型，没有调用方，于是整条路没被执行过。

处置：适配器新增 `ConfigResult` 事件类型，`0xA7`/`0xC4`/`0xC5`/`0xC6`/`0xE1` 统一走一个分支，回执里的错误码落到 `ResultCode`。**解码失败不断链**——一块能说话但说了本 build 不认识的形状的板子，仍然是一块在说话的板子，为此断链会让它因为一个与「桩子坏了」无关的原因变得不可达。新增 `adapter_dispatch_test.go`，用真实 loopback socket 把适配器跑起来，断言「拒收参数表」是一条带错误码的 `ConfigResult`，而不是一条未知指令。

顺带修了一个我在写这个分支时自己引入的问题：本来打算把 `0xC6` 解码后的结构体写回 `event.RawPayload`，那会**覆盖重放记录**——重放的东西不再是板子发出来的那份了。改成只判断能否解码，原始字节保持原样。

**这一轮的教训比前两次都具体：一类缺陷修干净，要靠「按类型复查」而不是「修到测试变绿」。** 测试变绿只说明你想到的那条路通了。

### 第四个：整个「套餐模板池」页面返回 503

继续按类型复查，这次查的是「schema 与代码不一致」——本项目已经栽过一次（0042 迁移建了两列退费、Go 侧还在读写单列）。做法是把后台所有只读端点对着真实开发库走一遍，看有没有 500。

**`GET /api/v1/admin/settings/package-templates` 返回 503**，也就是说这个页面从写出来起就没打开过。原因是列表查询里写了：

```sql
CONCAT(IF(o.device_id IS NULL,'全场','设备 ',o.device_id))
```

`IF()` 只接受三个参数（条件、真值、假值），这里把 `o.device_id` 当第四个参数传了进去。MySQL 直接报 1064。

三个值得记下来的点：

1. **这不是编译错误，也不是单测能发现的。** 它只在真实查询打到真实 schema 时才现形。集成测试也没发现，因为**这个端点根本没被集成测试调用过**——和协议回执那条一样，**没被调用的路径不会被测到**。
2. **我一开始怀疑是中文编码问题**，因为报错位置正好在 `'设备 '` 后面，而库里其它中文是好的。逐级二分才定位到与编码无关：`IF(1=1,'a','b','c')` 单独立即报错。**先验证再下结论，否则会去修一个不存在的问题。**
3. 库里的中文确实是好的（`hex()` 是标准 UTF-8），`mysql` CLI 显示成 `????` 只是它自己的终端编码。差点当成缺陷去「修」。

处置：改写为 `CONCAT(IF(o.device_id IS NULL,'全场','设备 '),o.device_id)`；并在集成测试里加了一段**把所有只读端点走一遍**的断言，注释写明原因——这样下次再有拼错的表达式或对不上的列，会在集成测试里当场红，而不是等到有人打开那个页面。

### 第五个：新端点的权限码从没进过权限表，端点对所有人 403

继续按类型查「写了但没生效」，这次查权限。`Require` 没有超级管理员旁路——它只比对用户实际持有的权限集合。于是新加的计量能力端点写的是 `Require("device.update")`，而**权限表里根本没有这个码**：系统只有 `device.read` 和 `device.import`，没有第三个设备权限。

后果是这个端点**任何角色都调不通，包括超管**，而且是永久且无声的。之所以没人发现，是因为**这个端点从没被调用过**——和上面两次一模一样。

处置分两层：

1. **迁移 `0043` 建 `device.metering`，并授予持有 `device.import` 的角色。** 权限归属不是随手挑的：能定价的角色不应该同时能替硬件自证清白，否则「能力检查拒绝按电量下到一个量不了的板子」这道闸门就成了摆设——先声明「这个板子支持电量」就能绕过去。**能上架板子的角色才知道到的是什么硬件。**
2. **新增 `permissions_integration_test.go`，扫源码里每一个 `Require("...")`，与权限表比对。** 这一类缺陷只有源码扫描能全量抓住：新加的路由、以及以后任何人新加的路由，只要权限码没种进表，集成测试立刻红。测试写完后**特意把权限码改回 `device.update` 验证它确实会失败**，报错是：

   > these route guards name a permission that was never seeded, so the route answers 403 to everyone: [device.update]

      能失败的测试才算测试；改回去之后才提交。

### 第六个：退费策略（两维正交）保存接口从未成功过

继续查「写了没生效」，这次把**写操作**也走了一遍——前面只扫了只读端点。

`PUT /api/v1/admin/settings/station-policies/:id` 注册成了 `:station_id`，而 `pathID()` 读的是 `c.Param("id")`。参数名对不上，`c.Param("id")` 永远为空，于是 `saveStationPolicy` 对**每一个请求**都回「ID 必须为正整数」。

这个端点是本轮 0042 迁移的产物——退费从单枚举拆成 `path`/`rule` 两个正交字段，拆完却存不进去。`GET` 能读（因为没有路径参数），`PUT` 永远失败。**症状只有一个验证错误消息，出现在一个还没人打开过的页面上。**

同一个成因，第四次。前三次分别是协议回执、套餐模板池列表、计量能力端点，**共同点是「这一段代码从来没有被成功执行过一次」**。

扫了全包的路由参数名，确认只有这一处不匹配（其余带参路由都叫 `:id`，或者用的是 `withdraw_no`/`refund_no` 这类字符串键，本来就不走 `pathID`）。

处置：参数名改回 `:id`；在集成测试里补上这个写操作，并断言**读回来的 path 与 rule 是两个独立字段**。同样先改回 bug 验证测试会红，报的是

> PUT settings/station-policies/1 got 400 want 200: {"message":"ID 必须为正整数"}

再改回来提交。开发栈实跑：保存返回 200/version=1，列表读回 `scan_refund_path=balance`、`scan_refund_rule=time_limited`、卡侧两个字段同样分立。

**四处同类缺陷的共同结论**：一个端点/分支是不是活的，不能靠「代码写了、单测过了」判断，**只能靠真的成功执行过一次**。每加一个对外能力，就把「成功执行一次」写进集成测试——不是断言它返回 200，而是断言它**写进去的东西读得回来**。

### 第七个（最重的一处）：套餐上架接口从来没有成功执行过一次

把**写操作**也走一遍之后，挖出第五处同类缺陷，也是最重的一处。

`charge_offer.code` 是 `NOT NULL` 且**无默认值**，而上架处理把它留空、先 `insert` 建行、再用第二条语句补写 `code`。于是第一条 insert 必然失败：

```
Error 1364 (HY000): Field 'code' doesn't have a default value
```

**「套餐上架」这个接口从来没有成功过一次。** 补写那行代码上方的注释写的是「code 可以写在同一条 insert 里」，而代码做的正好相反——**注释描述的是应该怎么做，代码做的是另一件事，两者长期并存而没有任何东西会反对。**

发现路径值得记下来：live 冒烟里 apply 报 503，但容器日志里**没有任何输出**（`resourceFailure` 把错误转成了统一文案「数据暂时无法读取或保存」）。于是没有猜——写了个临时程序用同一套 `dbconn` 把那两条语句跑一遍，逐步缩小到 `insert` 本身，才拿到 1364 和字段名。**遇到日志里查不到的错误，去把语句跑一遍，不要猜。**

处置：`code` 改为**可提前算出**——取套餐、站点、设备范围这三个唯一要素。唯一索引 `uk_station_code` 只要求站内唯一，而设备编号最长 64 字符，所以设备部分取摘要而不是原值。取消第二次写。

顺带修了两个同源问题：

1. **重复上架的判定没有过滤 `status`。** 下架后的套餐仍被算作「已上架」，所以运营下架之后**永远无法再上架**——请求一直被回「该套餐已在此处上架」。改为按目标处的实际状态分三种：该处仍在售则返回既有 offer 并标记 `replayed`（重试不该看起来像冲突，调用方无法区分重复与失败）；已下架则把**同一行**重新上架并标记 `relisted`，而不是再建一行只差「充电用户能不能看见」的记录。
2. **计价模板更新的乐观锁字段叫 `version`，而套餐模板、场地策略、设备规则都叫 `expected_version`。** 同一个操作在兄弟资源上两种拼法，按其余接口写的客户端会得到一个来由不明的 400。统一为 `expected_version`，前端同步。

开发栈实跑：上架 200；重复上架 200 且 `replayed=true`；下架后再上架 200 且 `relisted=true`，站内只有一行 active。

### 五处同类缺陷的共同结论

| # | 位置 | 症状 | 为什么没被发现 |
| --- | --- | --- | --- |
| 1 | 协议回执 `0xA7`/`0xC4`/`0xC6`/`0xE1` | 拒收的参数表被记成「未知指令」 | 平台从未发过这些下行，回执在测试中从未出现 |
| 2 | 套餐模板池列表 | `IF()` 传四个参数，页面一直 503 | 端点从未被集成测试调用 |
| 3 | 计量能力端点 | 权限码没种进表，对所有人 403 | 端点从未被调用 |
| 4 | 退费策略保存 | 路径参数名与读取处不一致，从未成功 | 端点从未被调用 |
| 5 | 套餐上架 | `code` 列 NOT NULL 却在插入后补写 | 端点从未被调用 |

**五处全都属于同一句话：一段代码从来没有被成功执行过一次。** 编译通过、单测全绿、`vet` 干净，都不代表它是活的——它们只证明被测到的那部分活着。

由此得到四条比逐条修复更重要的结论：

1. **每加一个对外能力，就在集成测试里真的成功执行一次**，而且断言的是「**写进去的东西读得回来**」，不是「返回 200」。第 2–5 处如果当初断言的是读回内容，全部都会当场红。
2. **写操作要和读操作一样被走一遍。** 前面三轮只扫了只读端点，五处里有两处只出在写路径上。
3. **注释不能替代测试。** 第 5 处的注释精确描述了正确的做法，代码做了相反的事，两者长期并存且没有任何东西会反对。
4. **能失败的测试才算测试。** 本轮三道新闸门（回执分发、只读端点全量走查、权限码源码扫描）每一道写完都先改回 bug 验证它会红，再改回来提交。

### 第八、九处：充电用户侧读套餐的查询，两处都与自己的注释不符

继续按「注释描述正确做法、代码做另一件事」这条查，查到了充电用户侧的套餐读取。

**一、下架的套餐仍然在卖。** 0042 给 `charge_offer` 加 `deleted_at`，正是为了套餐下架后还能留历史；**后台列表一直过滤了它，充电用户侧的 `ActiveOffers` 与 `ActiveOffer` 没有**。于是运营认为已经下架的套餐，充电用户照样看得到、也照样点得起来。

**二、设备独立套餐没有覆盖场地版。** `ActiveOffers` 的注释写的是「这台设备自己的，加上它**没有覆盖的**场地版」，而查询是 `device_id = ? OR device_id IS NULL`——被覆盖的场地版照列不误，**同一个套餐在充电用户列表里出现两次**。0042 引入设备级套餐的目的正是让一个场地同时跑两套东西，所以这条覆盖是模型的一部分，不是优化。改为排除该设备自己已经在卖的 `package_template_id`；同场地其它设备不受影响，仍然看到场地版。

新增 `offer_test.go` 走真实 MySQL：这两处都在 SQL 里，**假的 Store 会附和查询本该说的内容，而不是它实际说的**。

至此「注释与代码不符」在两轮里出现两次，都是同一形状：

| 处 | 注释说 | 代码做 |
| --- | --- | --- |
| 套餐上架 | code 可以写在同一条 insert 里 | insert 之后再补写 |
| `ActiveOffers` | 加上它没有覆盖的场地版 | 被覆盖的也列出来 |

**「注释说要做 A、代码在做 B」是一类可以主动搜的缺陷**，比逐个读函数更省事：凡是写着「应当/不会/必须/正是为了」的句子，都值得拿代码对一遍。

## 2026-09-30 充电用户列表：一个不存在的词，和三处会 500 的写法

后台一直看得到订单、反馈、报障，但每处都只带一个裸 `user_id`——客服接到投诉时没法把人找出来。新增「充电用户」资源时连着踩了四个坑，都记在这里。

### 第一处：借了一个不属于这个业务的英文词

新权限最初起名 `<配送员>.<read>`，理由是避开 `admin_user.read`。**理由本身站不住**：那只是一个「人眼容易看串」的撞名，为此选了一个业务上根本不存在的说法——那个词在英文里指外卖/快递配送员，而二轮车充电的用户是「充电用户」。为躲一个软问题换来一个硬错误。

改为 `charge_user.read`，同样避开了 `user.read` 与 `admin_user.read` 的混淆，但用的是界面上真实存在的词。**教训**：起名时如果理由是「和别的词不像」而不是「这个说法是对的」，先怀疑是不是在用一个错误的词绕开问题。

因为 0046 尚未提交、只在本地应用过，**把库回退到 45 再重新应用**改名后的迁移，而不是再补一个 0047——本地状态必须和全新部署完全一致。

### 第二处：GORM 按结构体名推导表名

`Model(&ChargeUserRow{})` 没有 `TableName()`，GORM 推出 `charge_user_rows`，这张表不存在，列表接口直接 5003。

难查的地方在于**报错完全不提示表名**——`resourceFailure` 把所有非冲突错误都映射成「数据暂时无法读取或保存」，容器日志也是空的。最后靠写临时测试直接调 store 才拿到原文。仓库里凡是走 `Model(&X{})` 的结构体都有 `TableName()`（`Station`→`station`、`Account`→`admin_user_role`），唯独新写的这个漏了。**这条规矩是现成的，照着做就不会漏。**

### 第三处：`station_id` 不在 `charge_order` 上

写最近订单摘要时顺手 `SELECT c.station_id`，想当然以为订单表存了站点。真实 schema 里没有这一列——**后台查订单所属站点一直靠 `charge_payment_intent` 关联**，而那张表对 `charge_order_id` 建了唯一键，一单至多一条意图，LEFT JOIN 不会放大行数。

同一条查询里还有个更隐蔽的坑：`charge_order` 按 `created_month` 做 RANGE 分区，`created_month` 是分区键且**没有默认值**，必须显式写入。

### 第四处：GORM 把切片字段当关联，拒绝整条查询

券与报障计数原本 `Scan(&detail)`，而 `ChargeUserDetail` 带着 `RecentOrders []ChargeUserOrderBrief`，GORM 解析到关联字段后直接以「未定义外键」失败。**报错发生在解析阶段，跟 SQL 对不对完全无关**——三条 SQL 单独在库里跑全是正确的。改为扫一个只含三个计数的小结构体再赋值。

**这一处的教训最值钱**：接口 500 但 SQL 单独执行没问题时，先怀疑 GORM 的结构体解析，而不是继续调 SQL。能绕开的路径是：先确认每条 SQL 在库上正确（`information_schema` 查真实列名，别靠印象），再把 GORM 层拆开逐个验证。
