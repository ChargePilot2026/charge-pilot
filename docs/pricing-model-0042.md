## 0. 本轮为什么要推翻 0041 的部分结论

0041 的模型是基于「模板管理」页推的，实测后发现三处结构性错误：

| 0041 的做法 | 实测真相 | 后果 |
| --- | --- | --- |
| 5 种计费基拍平成一级枚举 | 真实是**两类六种**：主轴是「谁计费」（服务端 / 设备），服务端侧再分按实时功率/按最大功率/按电量，设备侧分时长/电量/功率档位。**电量两侧都有且不是同一个东西** | `Spec` 形状错了，且设备侧模式被误当成了要算钱的模式 |
| 服务费是 `Spec` 上的一个枚举字段 | 电费与服务费是**两条独立的线**，各有开关、各有计费基、可自由组合 | 两条线被错误耦合 |
| 套餐内嵌在计费模板下 | 套餐是**独立模板池**，与费率解耦 | 同一费率配不同套餐做不到 |

本文逐条给出实测证据。

## 1. 页面结构：三层，不是我以为的两层

「套餐设置」入口 `#/siteList`，三层页面各自职责不同：

### ① 场地列表 `#/siteList`
- 顶部：搜索框（场地名称）+ 右上角「切换记录」
- 每张场地卡**平铺展示**退费组合：余额充值 / 扫码退款 / 在线卡退款 / 超时启动退款
- 底部「批量设置」→ 场地卡变复选框 → 全选 / 已选择 N 个场地 / 下一步（**跨场地多选**，不是场地内批量）

### ② 场地详情 `#/mealSetting`
| 区块 | 内容 |
| --- | --- |
| 安全保障设置 | 按次保障：商家承担模式 / 用户承担模式（各附一句说明，最高赔付 100 万）**无编辑入口** |
| 充值设置 | 充值入口开关（先充值后消费）+ **充值套餐**列表 |
| 退费设置 | 扫码退款 / 在线卡退款 / 超时启动退款，各带「编辑」 |
| 其他设置 | 消费前验证手机号（开关） |
| 充电套餐 | 设备矩阵 |

**充值设置 = 充值套餐**（不是余额门槛）：套餐名称（≤10 字，不填则不展示）/ 充值金额（元）/ 赠送金额（元），默认 6 组，带删除与上移，可「新增充值套餐」。

**退费设置 = 两个正交维度**（0042 曾误建模为单层枚举）：
- 退费路径：`退至余额`（系统自动退至充电账户余额，可下次充电抵用） / `原路退回`（退至原支付渠道，银行卡等）
- 退费规则：`不退款` / `实时退款`（按实际剩余时长或电量退款） / `限时退款`（时效外按比例退款）

两维组合后卡片上的展示形如 `限时退款(时效外不退款)-原路退回`、`实时退款-原路退回`。**扫��与在线卡各自独立配置**（在线卡多一个「按比例退款」的变体）。

**充电套餐区（设备矩阵）**：
- 设备类型页签：`充电桩` / `充电桩网关`（两类设备计费能力不同）
- 搜索框：设备编号
- 下拉筛选：`全部模式` / `电量模式` / `时长模式` / `服务端计费(实时功率)`——**只有这 4 个值**
- 表格：设备 → 当前计费模式 → 箭头（进设备详情）

实测对照（同一场地广州大学城11）：
- 充电桩侧出现 `时长模式` 与 **`脉冲计费`**
- 网关侧出现 `服务端计费(实时功率)` / `时长模式` / `电量模式`，**无脉冲**

→ **脉冲只出现在桩侧，网关侧没有**。它是桩端硬件计费，不是服务端计费模式。0041 把它当第 5 种计费基属于过度建模，本轮按用户指示**不做**。

### ③ 设备详情 `#/batchTimeSet`
- 顶部：设备数量统计 / 已选择设备 N 台 / 「设备明细」（**只读清单**，非多选器）
- 计费模式行：点击弹出「选择计费模式」→ `服务端计费` / `时长模式` / `电量模式`（3 项）
- 充电套餐：`选择模板` + `添加套餐`
- 规则说明：自动生成 + 可手工编辑
- 模式相关的展示开关（时长模式：显示功率 / 混合模式 / 隐藏单位）
- 底部「保存」

**设备级「选择计费模式」只有 3 项**，与场地矩阵筛选一致，都没有脉冲。

### ④ 切换记录 `#/switchRecord/equipmentList`
两个页签：

**设备明细**（每设备一条）：充电桩编号 / 状态（成功·进行中）/ 操作类型（修改设备计费和套餐）/ 创建时间 / 完成时间 / **切换前计费方式** / **切换后计费方式** / 「设备切换明细」按钮

**任务记录**（每次操作一条）：状态筛选 / 设备数量 `1台(1台已处理完成)` / 操作人 / 「任务明细」按钮

**设备切换明细**（单设备）：修改前后计费方式 + **下发后的套餐内容快照**（如 `0.1元/20分钟`、`2元/1分钟`）

> **关键设计含义**：给设备下发计费是**异步任务**，有成功/进行中状态、有操作人、有前后对比。实测中存在一条 `2026-09-23 01:40:01` 创建、至今仍「进行中 0台已处理完成」的记录。
> 这意味着 **apply 不能是纯同步事务**——写库即生效的假设不成立，必须有任务与下发结果。

## 2. 计费方式：两类六种（不含脉冲）

新建模板第二步「计费方式」共 5 个选项（A 级实测），按用户指示**只做前 4 个**。产品口述给出了比 UI 分组更准的分类轴：**两类六种**（B 级证据，见 6.1）——

| UI 上的选项 | 归类 | 谁算钱 | 配置项 |
| --- | --- | --- | --- |
| **服务端计费**（含按实时功率 / 按最大功率 / 按电量三个二级） | `server_*` | 服务端按实绩算 | 收费标准 + 充电费率 + 三类套餐 + 电损率 + 默认充电方式 + 刷卡设置 + 5 个展示开关 |
| **时长模式** | `device_duration` | 桩端倒计时，到时自停 | 套餐 + 3 个开关（显示功率/混合模式/隐藏单位） |
| **电量模式** | `device_energy` | 桩端计量电量，耗尽自停 | 时长模式全部 + **电费服务费模式**开关 |
| **功率模式** | `device_power` | 桩端按档位费率扣预付余额 | 「设置功率档位」+ 金额套餐 |

**注意「电量」在两侧都有**（`server_energy` 与 `device_energy`），UI 上只出现一个「按电量计费」在服务端组内、设备组内的「电量模式」是另一个东西。详见 6.1 的对比。

**设计意图**：只有 `server_*` 需要一整套费率配置，因为只有它由服务端算钱；`device_*` 三种是**把执行下放给桩端**，服务端只负责把套餐和档位表下发过去。表单一个比一个简单不是偷工减料，是职责边界。

**电量模式多的那个开关**是关键：开启后「根据电费和服务费之和与套餐电量相乘计算套餐费用」——即电量套餐有两种算法，桩端自算 or 服务端用真实费率兜底算。

**功率模式的档位是等宽的**（0-100w/101-200w/…/401-500w），与实时功率的不等宽档位（0-200/201-250/…）规则不同，因为桩端功率档位是本地固化的阶梯表，宽度必须规整。

### 2.1 设备计费三种模式（时长 / 电量 / 功率）的完整业务逻辑

由产品口述逐个澄清（B 级证据；乐摇摇实测只给了表单形态，语义靠口述补全）。

**① 时长模式**

```
后台给设备配时长模式，套餐 1元60分钟 / 2元120分钟
   ↓ 用户扫码选套餐支付
支付后启动时：服务端按已支付的那个套餐，向设备下发对应时长
   ↓
设备倒计时 → 耗尽自动停止
```

**② 电量模式**：同构，只是设备计的不是时间而是**电量**，耗尽即停。

**③ 功率模式——控制量是金额，不是功率**（此前被我误建模为「按功率范围控停」）

```
后台给设备配功率档位：0-100瓦 每小时1元；101-200瓦 每小时2元
后台给设备配充电套餐：1元 / 2元（预付额度）
   ↓ 用户支付 1 元后启动
设备按功率档位**实时计费**：当前功率 150 瓦 → 落 101-200 档 → 按每小时 2 元扣
   ↓
所以 1 元只够充 0.5 小时
   ↓
余额耗尽 → 自动停止
```

由此四种「控制量」各不相同，**不能笼统说成「到量自停」**：

| 模式 | 预付金额 | 设备本地消耗的是什么 | 停机条件 |
| --- | --- | --- | --- |
| `device_duration` | 套餐价 | **时间** | 已用时长 ≥ 套餐时长 |
| `device_energy` | 套餐价 | **电量** | 已用电量 ≥ 套餐电量 |
| `device_power` | 套餐价 | **金额**（档位费率 × 时长） | 剩余金额 ≤ 0 |

**唯一贯穿三者的是「钱在支付时已收满」**，变的只是桩端拿什么去花这笔钱。

由此可以确定四件此前模糊的事：

1. **设备计费下没有「实时算钱」这回事（对服务端而言）**。用户在充电期间无论用多少电，服务端都**不会再计一笔账**；金额在下单那一刻就由**套餐价**定死了。服务端计费内核在这条路径上**不参与计费**，只参与「选了哪个套餐 → 该下发什么」这步查表。
2. **套餐是「价格 + 消耗口径」的二合一**。同一个 `1元60分钟` 里，1 元是收款金额，60 分钟是桩端的消耗口径。二者同源，**不能拆成两个独立配置**——否则会出现「按 60 分钟的价收钱、按另一个时长下发」的口径漏洞。
3. **`device_power` 的档位表是「费率表」不是「控制范围」**。档位挂在**瓦数**上、值是**元/小时**，作用是把瞬时功率折算成金额消耗。乐摇摇 UI 上叫「设置功率档位」，产品口述叫「功率范围」——**实测语义以「费率阶梯」为准**，「范围」只是同一个说法的另一个叫法。这条纠正了本文早前「设备按功率范围控停」的错误理解。
4. **下发是「支付后启动时」一次性完成**，不是下模板时就发。这也解释了切换记录里为什么会有「进行中」状态：那是**切计费方式**的异步任务，与单次充电的控制量下发是两回事（见 6.5.2）。

**关键推论：设备是执行方，不是计费方。** 在 `device_*` 三种模式下服务端**不参与一次结算计算**；金额来自下单时的套餐价，停止条件来自桩端。这与 `server_*` 三种方式正好相反——那里设备只报数，算钱的是服务端。

> 有意思的是 `device_power` 与 `server_realtime_power` **算法完全一样**（按瞬时功率落档、按档位费率累计），差别只有一处：**余额记在桩端还是记在我们的账上**。桩端模式下这笔钱已经收完，扣的是余额；服务端模式下钱还没收，得等结算。所以「设备算钱」在功率这一支上确实成立——只是**算的是「余额够不够」，不是「该收多少钱」**。这条也说明：**不能因为设备在算，就认为它承担计费责任**。

对本项目的直接影响：`ChargeMode` 为 `device_*` 时，`pricing.Cost` 只在**下单时**用套餐价求一次值；结算时读的是桩端回报的实绩（用了多久 / 用了多少电 / 余额剩多少），而不是重新估算。若未收到实绩，只能按套餐口径兜底，且必须标记为兜底值而非实测值。

三个开关（显示功率 / 混合模式 / 隐藏单位）语义仍未确认——目前只知它们**只影响桩端展示**，不影响控制量下发与费用，暂列为不做/后置。

### 2.2 服务端计费的三个二级方式

`按最大功率计费` / `按实时功率计费` / `按电量计费`。三者的**配置项几乎一致**，差异只在收费标准表的结构：

| 二级方式 | 档位列 | 电费单价单位 | 超档兜底 |
| --- | --- | --- | --- |
| 按实时功率 | 有 | 元/小时 | 有 |
| 按最大功率 | 有 | 元/小时 | 有 |
| **按电量** | **无** | **元/度** | **无** |

按电量下档位、`+添加档位`、`删除档位`、`超过最大档位电费单价` **全部消失**——按电量计费是「一度电多少钱」，与功率档位无关。

## 3. 收费标准编辑器的真实结构

### 3.1 两条独立的收费线

**这是 0041 最大的建模错误。** 电费与服务费是两条线，各有自己的开关，且**开关分处两个界面**：

- **服务费收费**开关 → 在「收费标准」编辑器内
- **电费费率**开关 → 在「充电费率」区（编辑器外）

打开后各自的形态：

**服务费收费**（打开后出现三个 tab）
| tab | 服务费单价单位 | 合计列 |
| --- | --- | --- |
| 按充电时长和功率 | 元/小时 | **有**（只读，电费+服务费） |
| 按电量 | 元/度 | 无 |
| 按次 | 元/次 | 无 |

> 合计列只在「元/小时」时出现，因为只有同为「元/小时」的两列才在同一量纲上可加。**不给不可加的列做假合计**——这是个值得学的克制。

**电费费率**（打开后是倍率）
- `临时电费费率：__ 倍`
- `刷卡电费费率：__ 倍`

即同一份档位单价，按不同渠道乘不同倍率。它**专属电费线**，与服务费无关。

### 3.2 档位是链式的

档位区里 `0~200`、`201~250`、`351~550` 等**灰底不可编辑**——系统自动保证首尾相连（上一档高档 +1 = 下一档低档），只有**最后一行的「高档」可编辑**。

> 这从 UI 层就杜绝了档位区间重叠或断档，而这类脏数据在计费系统里会直接导致漏算电费。**存储应记每档的结束瓦数（链式），而非独立的高低档对。**

### 3.3 时段也是链式切分的

把时段1的结束时间从 24:00 改到 09:30，系统**自动派生出时段2（09:30~24:00）**，两段首尾相接、无缝覆盖全天。

> 时段**不是固定条数的并列列表**，是用户「切割」出来的。改的是边界，不是列表长度；系统负责保证相邻时段首尾相接、覆盖完整、不重叠不遗漏。
> **时间粒度 30 分钟**（00:30 / 01:00 / 01:30 …）。

### 3.4 套餐设置工具（反算器）

「根据电费成本和利润率辅助设置电费或功率区间单价」：输入 `电费成本（元/度）` + `电费毛利率（%）`，自动按功率档位反推各档电费单价。带「重置 / 确定」。

> 运营商知道自己的购电成本和目标毛利，不必逐档手算 0.17/0.2/0.35。0041 完全没有这个功能。

## 4. 套餐：独立模板池

### 4.1 拆出计费模板的理由（实测佐证）

「选择模板」弹窗里 170+ 个计费模板，每条带 `启用中/用中` 状态 + 「编辑」，**可按「适用设备类型 / 模板类型 / 最新修改时间」查看**。弹窗内**没有搜索框**，只能滚动——这正是 ChargePilot 可以做得更好的地方（搜索 + 筛选 + 带不可用原因）。

套餐在设备页是**独立的卡片列表**（`套餐编辑` 弹窗：套餐名称 / 价格 / 最低消费 / 时长 / 是否展示套餐备注 / 刷卡默认套餐），并提供「选择模板」与「添加套餐」两个入口。

→ **同一个计费模板可以配不同的套餐组合，同一批套餐可以复用到多个场地**。套餐内嵌在费率模板下会直接废掉这两个能力。

### 4.2 套餐编辑弹窗字段（实测）

```
套餐名称 *        （文本）
价格 *            （元）
最低消费          （元，可空）
时长 *            （分钟）
是否展示套餐备注  （开关）
```

## 6. 确定的建模

### 6.1 两类六种计费方式

```go
type ChargeMode string
const (
    // 服务端计费：三种，费用由 pricing.Cost 求出
    ModeServerRealtimePower ChargeMode = "server_realtime_power" // 按实时功率
    ModeServerMaxPower      ChargeMode = "server_max_power"      // 按最大功率
    ModeServerEnergy        ChargeMode = "server_energy"         // 按电量
    // 设备计费：三种，费用 = 用户已支付的套餐金额
    ModeDeviceDuration ChargeMode = "device_duration" // 时长
    ModeDeviceEnergy   ChargeMode = "device_energy"  // 电量
    ModeDevicePower    ChargeMode = "device_power"   // 功率档位费率
)

func (m ChargeMode) Executor() ChargeExecutor { … }

type ChargeExecutor string
const (
    ExecutorServer ChargeExecutor = "server" // 服务端算钱
    ExecutorDevice ChargeExecutor = "device" // 设备执行，钱在支付时已定
)
```

产品口述给出的分类轴（B 级证据）比后台 UI 的分组更准确：**先分「谁计费」，再分「按什么计」**。

```
                    ┌─ 服务端计费 ─ 按实时功率
                    ├─ 服务端计费 ─ 按最大功率
   谁计费 ───────────┤
                    ├─ 服务端计费 ─ 按电量
                    │
                    ├─ 设备计费 ─ 时长
                    ├─ 设备计费 ─ 电量
                    └─ 设备计费 ─ 功率档位费率
```

**关键点：电量在两侧都出现，且不是同一个东西。** 服务端按电量 = 我们用自己的费率引擎按实绩算；设备按电量 = 钱已由套餐价定死，桩端自己累计电量到限就停。0041 把两者混成一个「电量模式」，是这次必须拆开的原因之一。

**为什么拍平成 6 个值，而不是 `server` + 一个三元组**：设备侧三种模式**没有任何二级属性**，只有服务端侧才有。用 `server|device` + 仅服务端有值的 `ServerBasis`，等于制造出一个「设备侧也能填 server_basis」的字段——而空值与脏值正是本项目反复出问题的地方。拍平后 `ChargeMode` 自解释，主轴由 `Executor()` 推导，不冗余存两列。

> 命名：乐摇摇 UI 上写「功率模式」并把这个等宽阶梯表（0-100w/101-200w/…）叫「功率档位」，产品口述叫「功率范围」。三者指同一物，但**只有「档位/费率阶梯」是准确的描述**——「范围」容易被误读成功率上限，见 2.1 第 3 条。

### 6.2 两条独立的收费线

```go
type Spec struct {
    Electric  ElectricLine            // 电费线，必填
    Service   *ServiceLine           // 服务费线，nil = 不收
    Multiplier *ChannelMultiplier    // 电费线专属的渠道倍率
    TimeCharge *TimeCharge           // 按时间充电三项
    Packages   PackageSet            // 三类套餐
    LossRateBP int32
    DefaultChargeWay string
    CardMaxMinutes uint16
    Display   Display
}

type ElectricLine struct {
    Basis   ServerBasis // realtime_power | max_power | energy
    Periods []Period
}

type ServiceLine struct {
    Basis ServiceBasis  // minute_power | energy | session
}

// 时段：链式切分，覆盖全天
type Period struct {
    EndMinute int      // 结束时刻；开始由上一段推导；最后一段须为 1440
    Tiers     []Tier   // Basis==energy 时为空（按电量无档位）
}

type Tier struct {
    MaxWatts      int   // 链式：0 起，上一档 +1；最后档为上限
    ElectricCents int64 // 元/度 或 元/小时，取决于 Electric.Basis
    ServiceCents  int64 // 仅 Service!=nil 且 Basis==minute_power 时按档位有意义
}
```

**不引入布尔开关表达「有没有档位」**——`Electric.Basis == "energy"` 时 `Tiers` 自然为空。这样比每个字段带 `Enabled` 更不容易出错。`ServerBasis` 只在 `ModeServer*` 三种模式下有意义，设备侧模式整个 `Spec` 都不参与结算。

### 6.3 结算不变式

- **时段链不变量**：首段从 0 开始，相邻 `EndMinute` 严格递增，末段为 1440。违反则 `ValidateSpec` 拒绝——**绝不允许空洞或重叠**，否则深夜充电查不到价。
- **档位链不变量**：`MaxWatts` 从 0 起严格递增，档内区间为 `[prev+1, cur]`。违反则拒绝。
- **取价兜底**：任一时刻必须能唯一定位到一个 `Period`；定位不到一律走 `ErrMeterReview`，不得猜测。
- **非服务端模式不走实时计费**：`device_duration` / `device_energy` / `device_power` 下费用在下单时由套餐价定死、由桩端到量自停，`pricing.Cost` **不得**参与这三种模式的结算金额。`server_*` 是唯一以 `Cost` 为权威的模式。详见 6.7。

### 6.4 场地策略（station_policy）

```go
type StationPolicy struct {
    ForceRecharge        bool
    RechargeEntry        string // prepay_first 等
    RechargePackages     []RechargePkg  // 名称/充值金额/赠送金额
```

**退费是路径 × 规则两个正交维度**，不是单层枚举——0042 曾误建模为 `scan_refund: none/immediate/time_limited`。

### 6.5 设备分配与切换任务

- `pricing_rule.device_id`：NULL = 场地默认，设备规则优先。**不另建 `device_pricing_assignment` 表**——那会是同一个问题的第二个答案，必然与实际计费的那行产生分歧。
- `charge_offer.device_id`：套餐可全场卖或仅某设备卖；结算时 `device_id = ? OR device_id IS NULL`。
- **新增切换任务**：apply 写规则的同时建任务，记录设备列表、操作人、创建/完成时间、**切换前后计费方式**、每设备下发状态。设备明细页可查下发后的套餐快照。

> 这是实测暴露的真实可靠性缺口：下发会失败、会卡住（实测有卡 6 天的记录），纯同步事务无法表达。

### 6.5.1 计费方式按协议能力授权

**计费方式不是运营随便选的，它取决于该设备的协议实际上报了什么。** 报不出功率的设备配了功率计费，出的账既无法向用户解释也无法向电力部门解释——这比直接禁掉更糟。

实测证据：广州大学城11 同一场地内，**同一套 dc589 协议**，桩侧只出现 `时长模式`/`脉冲计费`，网关侧才出现 `服务端计费(实时功率)`。说明这是**设备能力**决定的，而非协议层面的限制——哪些设备能上报功率，是建档时就该确定的事实。

**授权规则**（按协议能力，不按人工勾选的布尔标志）：

| 协议上报内容 | 允许的服务端计费方式 | 允许的设备计费方式 |
| --- | --- | --- |
| 上报电量，不上报功率 | 仅 `server_energy` | `device_duration` / `device_energy` / `device_power` 均不受限 |
| 上报电量 + 分段功率 | `server_realtime_power` / `server_max_power` / `server_energy` | 同上 |
| 能力未知（新接入协议尚未声明） | **一律不提供功率类**，宁可少给不可给错 | 同上 |

> 设备计费三种方式不受上报能力限制，因为**它们要的正是设备自己计量的东西**——桩端能自停就说明它能量出自己。反过来，`server_*` 的三种方式全部依赖我们的费率引擎按实绩算，实绩里没有的东西就算不出来。这正是「谁计费」这条主轴在授权上的体现。

**落地方式**：
- 协议适配器（`internal/gateway/...`）在注册时**声明自己的计量能力**（`ReportsEnergy` / `ReportsSegmentedPower`），这是从帧解析事实推导出来的，不是配置项。
- 设备建档时把能力记入 `device_meta`，作为候选选择器的过滤依据。
- 候选选择器（6.6）对不支持的方式返回 `unavailable_reason = "该设备协议不上报功率，不支持按功率计费"`，**置灰但可见**。
- 协议**默认拒绝**：新增协议若未显式声明能力，按「只支持按电量」处理。这条比任何配置都重要——**遗漏声明的后果必须是保守的**。
- 存量设备能力未知时，一律按「只支持按电量」，需要运营显式确认后才放开。

**顺带修正未决项 14 的性质**：原描述是「所有计费基都得凑合用平均功率估算」，现在变成「只有明确支持功率上报的设备才能配功率计费」。问题从「估算准不准」变成「哪些设备支持」——后者是**可从厂商资料与实机验证的事实**，不是估算质量问题。0041 选定的「允许但按平均功率估算」这个全局取舍应当作废。

### 6.6 候选选择器

返回**全部**模板并带 `unavailable_reason`（置灰 + 原因），而不是提交时才 409。直接抄乐摇摇「不可用原因：计费方式不匹配」的交互。

### 6.7 执行方与计费方：会话该记什么

产品口述带来的最大结构性结论是**「设备是执行方，服务端是否计费方取决于模式」**。这条必须落到会话表，否则后端会在三种模式下反复试图「算钱」，而那笔钱在支付时就已经没有了。

| 计费方式 | 谁在算钱 | 钱从哪来 | 会话停止由谁决定 |
| --- | --- | --- | --- |
| `server_realtime_power` | **服务端** | `pricing.Cost(spec, usage)`，按实际用量 | 服务端（可发停机指令） |
| `server_max_power` | **服务端** | `pricing.Cost(spec, usage)`，按实际用量 | 服务端 |
| `server_energy` | **服务端** | `pricing.Cost(spec, usage)`，按实际电量 | 服务端 |
| `device_duration` | 桩端 | 套餐预付金额 | 桩端倒计时到 0 |
| `device_energy` | 桩端 | 套餐预付金额 | 桩端累计电量到限 |
| `device_power` | 桩端 | 套餐预付金额 | 桩端按档位费率累计扣款，**余额**到 0 |

这张表就是「两类六种」在会话层的全部体现：**分界线只有一个——`Executor()` 返回 `server` 还是 `device`**。跨过这条线的所有行为都不同（是否要费率、是否要下发控制量、结算金额取谁），不跨线的行为完全相同。

因此 `charge_session` 需要的实绩字段是**按模式互斥**的一组，不能一套字段全存：

```go
// 下发侧（下单时写入，是「我们要求设备做什么」）
// 仅 device_* 三种模式需要；server_* 下这些字段恒为零值
type ControlInstruction struct {
    Mode                  ChargeMode
    Minutes               uint16  // device_duration：倒计时长度
    EnergyMilliWh         uint64  // device_energy：电量上限
    BalanceCents          int64   // device_power：预付余额，桩端按档位费率从它扣
    TierCentsPerHour      []int64 // device_power：随余额一起下发的档位费率表
}

// 实绩侧（结束后回填，是「设备实际做到了什么」）
type SessionActual struct {
    StopReason  string // exhausted_time | exhausted_energy | balance_spent | server_stop | fault | user_stop
    UsedMinutes uint16
    UsedMilliWh uint64
    PeakWatts   int
    SpentCents  int64  // device_power：桩端实际扣掉的金额
    Reported    bool   // false = 用套餐值兜底
}
```

**金额来源是唯一的不变量**：

- `server_*`：金额**必须**等于 `pricing.Cost`，任何其它来源都是 bug——服务端计费这三种方式的全部意义就在这里。
- `device_*`：金额 = 用户**已支付的套餐金额**，**不得**再用 `pricing.Cost` 复算一次。复算会得到一个与用户付款不同的数字，进了对账就是事故。注意这里不是「封顶金额」而是「实收金额」——两者在设备计费下恰好相等，但这正是我们要守住的不变量，而不是可以顺带用别的方式凑出来的巧合。

**`Reported == false` 的兜底必须显式落库**，不能默默用套餐值顶替。理由和 `ErrMeterReview` 一样：兜底值是估计，混进实绩里就再也分不出哪一单是猜的。查询与对账按 `Reported` 过滤即可把两类分开。

**`device_power` 的实绩口径是唯一需要额外小心的**：桩端上报的 `SpentCents` 一般**略小于**实收（采样间隔内的残值，例如余额剩 0.2 元时设备仍以 2 元/小时跑完了最后 6 分钟）。差额是**算法残差，不是账务差错**。落库时应保留 `SpentCents` 原值并把差额记为 `residual_cents`，**不要四舍五入抹平**——抹平之后就再也查不出某台设备的采样粒度异常了。

**超出已付金额怎么办**是需要产品确认的点，且**只对 `device_duration` / `device_energy` 成立**：桩端到量自停是「控制」，但用户在自停前用掉的电量**可能超过**套餐电量（先充电后计量、桩端虚标），此时钱已收满。三个可能——按实绩补扣、超出白送、预授权。三者对账口径完全不同，**不替产品拍板**。`device_power` 不存在这个问题（桩端扣的是已收的余额，天然不会超支），只需处理上面的残差。

### 6.8 平台计费模式关掉的是分档折扣，不是自停

电川 5.8.1 变更说明（A 级证据，见 `docs/protocol/dianchuan-589-vs-dc589.md`）：

> 增加一个充电类型：`4 = 平台计费模式`，如果下发平台计费模式，**主板不进行分档**。

这条常被读成「设备不会自己停，所以平台必须主动停机」。**那是对它的误读**，本文早前也这么写过，现更正：

- B7 在任何充电类型下都下发「充电时间/电量」，**主板照样到量自停**。平台计费模式改的是**不套用分档折扣**，不是停止条件。
- 分档折扣的作用见 5.8.2 的算例：剩余时间 × (1 ÷ 分档比例)。也就是说，功率越高、折扣越大、给的时间越少——这是设备侧把「功率」换算成「时间」的机制。平台计费模式下不打折，等于平台自己按真实功率收钱，设备只管跑完下发的时长/电量。
- 因此 **`server_*` 不存在协议层面的「无上限敞口」**。一次会话的上限仍然是平台下发的那段时间或电量。

**真正成立的是另一件事，而且更重要**：平台计费模式下不打折，用户用同样 1 小时、功率更高时，**实际费用比设备计费模式高**。这意味着两条模式的报价不可互相换算，套餐预览必须走各自的算法——这正是 6.7「金额来源是唯一不变量」的现实理由。

**仍然需要一个停机回路，但它是产品选择不是协议要求**：若运营要给服务端计费加「消费封顶」，则必须由平台下发 B9 并处理应答失败（`0x00` 无此端口 / `0x04` 端口故障）。未设封顶时，设备到量自停即可，平台不必介入。`DecideStop` 因此只在设了封顶时才返回 `ShouldStop`。

## 9. 本轮实测推翻 0041 结论的记录

诚实记录，避免以后重犯：

| 次数 | 我的错误结论 | 真因 |
| --- | --- | --- |
| 1 | 「按电量没有档位表，服务费也不可选」 | 只看了默认单时段（00:00~24:00）就下结论，漏了时段可切分成多条 |
| 2 | 「按最大功率的服务费没有三个 tab」 | 在**服务费开关关闭**状态下看的编辑器 |
| 3 | 「按电量的服务费也没有三个 tab」 | 同上，犯了完全相同的错 |
| 4 | 「设备计费三模式统一为『预付金额 + 控制量』，功率模式是按功率范围控停」 | **把「档位」当成了控制上限**。档位挂在瓦数上、值是元/小时，是**费率表**；功率模式的控制量是**金额**，桩端拿已收的钱按档位费率扣，扣完才停。表单长得像时长/电量，语义完全不同 |

**教训**：

1. 判断一个字段「有没有」之前，必须先把它**展开到最终形态**再看；开关关闭态 ≠ 功能不存在。
2. **不要用「长得像」代替「算一遍」**。第 4 次的错误是：三种模式的结构看起来能统一，就顺手统一了，没有拿一个具体数字跑通（150 瓦 × 2 元/小时 → 1 元撑半小时，一算就露馅）。**凡是要建模的机制，先用一个具体算例跑通再落笔。**
