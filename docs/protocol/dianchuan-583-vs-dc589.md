## 0. 结论速览

1. **帧格式完全一致**（B）——`EE | LEN | CMD | SESSION_ID(6) | DATA | XOR`，小端，`LEN` = CMD 到 SUM 的字节数。dc589 的 `HeaderSize = 8` 与文档吻合。
2. **5.8.3 共 34 条指令，dc589 只覆盖 17 条，17 条未实现**（A）。其中最要命的是 **`0xC7` 获取平台参数配置表**。
3. **`0xC7` 是设备登录后的第一件事**（A）。dc589 的 `default` 分支对未知指令直接 `return error`，**任何真实电川设备登录后必然被网关断链**。这是阻塞级缺陷。
4. **C3/C4/C7 就是计费参数下发通道**（A）。这直接解除了 `go-rebuild.md` 中「无任何配置下发命令字、缺厂商资料」的资料缺口。
5. **充电类型 4=平台计费，文档明写「主板不进行分档」**（A）。这意味着 `server_*` 模式**必须由平台主动发 B9 停机**，设备不会在金额边界自停。
6. **协议里「功率」不是独立充电类型**（A）。它是叠加在「按时间/按电量」之上的**分档比例**修饰，与乐摇摇把它做成顶层计费方式不同。
7. 文档自身存在**三处缺陷**（档位 0/1 基不一致、金额单位不一致、序号错位），实现时极易踩中。

### 2.1 🔴 阻塞缺陷：真实设备登录后必被断链

5.8.3 第 4 节「工作流程」明文（A）：

```
连接服务器 → 发送 0xA0 指令登录 → 发送 0xC7 获取计费模板
           → 平台下发 0xC3 设置本地参数 → 发送心跳
```

而 `internal/gateway/protocol/dc589/adapter.go:231`：

```go
default:
    return fmt.Errorf("%w: unsupported command 0x%02x", ErrPayload, frame.Command)
```

**`0xC7` 走 `default` → 返回错误 → `ServeConn` 返回 → 连接关闭。** 真实电川桩在 `A1` 之后必然发 `C7`，因此**没有一台真实设备能连上来**。本地集成测试与模拟器之所以通过，是因为它们不按 5.8.3 的工作流程发 `C7`——**这是测试与协议不符，不是设备能工作**。

> 该缺陷此前被误判为「缺厂商资料、不属于漏写代码」。`go-rebuild.md` 第 278 行写的是「没有任何配置下发命令字，命令字空间里 A3、A6–A9、0xB0–0xB6 均为空位」。**这份 PDF 证明 C3/C4/C7 就是配置下发通道**，该判断的前提不成立。

## 3. 充电类型：与「两类六种」模型的对照

### 3.1 5.8.3 文档定义（A）

**B7 远程启动 · 充电类型**：

| 值 | 含义 | 备注 |
| --- | --- | --- |
| 0 | 按时间充电 | |
| 1 | 按电量充电 | |
| 2 | 按金额充电 | **预留，硬件无此功能** |
| 3 | 充满自停 | **预留，硬件无此功能** |
| 4 | **平台计费模式** | 5.8.1 新增：「如果下发平台计费模式，**主板不进行分档**」 |

### 3.2 dc589 实现

```go
ByTime=0, ByEnergy=1, PlatformBilling=4,
LongTime=10, LongEnergy=11, LongPlatformBilling=12
```

- `2`/`3` 被正确排除（5.8.3 标为预留），✅
- `10/11/12` 在 5.8.3 中**不存在**。按 `Long*` 命名推测是长时类变体，但**含义未经确认（C）**。
- `BuildStart` 接受 6 个值，与本文档无冲突。

### 3.3 🔴 关键推论：`server_*` 模式必须由平台主动停机

5.8.1 变更说明明写（A）：**下发充电类型 4（平台计费）时，主板不进行分档。**

这意味着——

| | 设备行为 | 谁决定何时停 |
| --- | --- | --- |
| **类型 0/1**（按时间/按电量） | 主板按分档比例消耗，到量自停 | **设备** |
| **类型 4**（平台计费） | 主板不参与计费相关计算 | **平台**（必须发 B9） |

对 ChargePilot 的直接后果：`server_*` 三种模式**不能只做「预估 + 事后结算」**，必须有一条**运行中的监控回路**——按实绩累计费用，达到阈值时下发 `0xB9 远程停止`。否则用户可以无限充电而费用不封顶。

**这条要求此前在方案中不存在。** 它应进入 `docs/pricing-model-0042.md` 6.7。

## 4. 🔴 协议里「功率」不是独立计费类型（A）

这是本份协议对计费建模最有价值的发现。

### 4.1 机制

「功率」在协议里**不是 B7 的充电类型**，而是 **C3 参数配置表中的两组字段**：

| 字段 | 位置 | 含义 |
| --- | --- | --- |
| 第一~五档功率值 | C3 第 7-11 项 | 0.1W 单位，**高档功率必须大于低档**（文档明确约束） |
| 第一档分档比例 | C3 第 12 项 | **固定 100%，不能设置**，下发其它值会设置失败并返回错误 |
| 第二~五档分档比例 | C3 第 13-16 项 | 1 = 1% |
| 第六~八档功率值/比例 | C3 第 23-28 项 | 5.8.2 新增，**仅 2 路智能插座 8 档机型** |
| 充满自停 | C3 第 17 项 | 0 关 / 1 开 |

### 4.2 分档的实际作用是「给时间打折」，不是扣余额

5.8.2 变更说明给出了明确算例（A）：

> 下发充电是 100 分钟，分档变成了 50 分钟，充电 20 分钟后，结束上报的剩余时间要按照 **30 分钟除以 0.5 = 60 分钟** 上报。

即：**剩余时间 × (1/分档比例)**。分档比例 0.5 意味着「跑慢一点就少给一半时间」。

`0xC2 分档上报` 的字段也印证这一点：分档前时间/档位、分档后时间/档位、分档时功率——**全是时间，没有金额**。

### 4.3 对 `docs/pricing-model-0042.md` 的挑战

方案中 `device_power` 被建模为独立计费方式，「桩端按档位费率扣预付余额」。**在电川固件上这个机制不存在。**

两种可能，需要产品/厂商确认：

| 解释 | 含义 | 对模型的影响 |
| --- | --- | --- |
| **解释一：功率是修饰而非类型** | 协议只有「按时间」「按电量」两种设备计费，功率表现为叠加其上的分档比例。乐摇摇把修饰做成了顶层选项 | `device_power` 不应是独立 `ChargeMode`，而应是 `device_duration`/`device_energy` + `banding` |
| **解释二：5.8.9 已扩展** | 5.8.9 可能新增了按金额/余额型充电类型 | 维持现有模型 |

**换算关系**（若采解释一）：平台用「元/小时」表达档位费率，固件用「分档比例」表达时间折扣，两者的桥是

```
分档比例 = 该档每小时价格 / 基准档每小时价格
```

这解释了老杨师傅给的例子为什么在电川上也能成立：1 元 ÷ 2 元/小时 = 半小时 ⟺ 150 瓦档比例 50% ⟺ 剩余时间减半。**平台口径与固件口径不同，但可精确互转。**

> 已登记为未决项 22。**在确认前不改动 6.1 的六值枚举**——推翻需要证据，不是推测。

## 5. C3 参数配置表（28 字段）与乐摇摇字段的对应

参数表是「配置下发」的实际载体，字段与乐摇摇后台高度对应（A）：

| C3 字段 | 默认 | 对应乐摇摇 | 对应本项目模型 |
| --- | --- | --- | --- |
| 设备运行模式 0 先消费/1 先按键/2 免费模式 | 0 | 默认充电方式 | `Spec.DefaultChargeWay` |
| 音量 0-8 | 4 | — | 未建模 |
| 本地投币一次时间 0-999 分钟 | 240 | — | 未建模 |
| **本地刷卡一次时间 0-999 分钟** | 240 | **套餐时长** | `Package.DurationMinutes` |
| **刷卡扣费金额 0-25.0 元** | 1.0 | **套餐价格** | `Package.PriceCents` |
| **刷卡是否退费** | 0 | 在线卡退费设置 | `CardRefundRule` |
| 第一~五档功率值 | 100/200/300/400/500 W | **功率档位** | `Tier` 表（设备侧） |
| 第一~五档分档比例 | 100% | — | `TierRatio`（新增） |
| 充满自停 | 1 | **充满自停 660** | `Package.StopWhenFull` |
| 浮充功率/时间、拔除时间 | 10W/1800s/300s | — | 未建模 |
| 密码（分体板） | 8888 | — | 未建模 |
| 温度保护值 0xFF 关 | 0xFF | — | 设备安全，非计费 |
| 第六~八档功率/比例 | 100W | — | 8 档机型专属 |

**两条重要佐证：**

1. **套餐确实是「金额 + 时长 + 充满自停」三件套**（A）。C3 只有**一个**刷卡金额和一个刷卡时间——说明设备侧只存**一套**卡计费参数，多套餐（1 元/2 元）的选择在**平台侧**，平台选好后通过 B7 的「充电时间/电量」字段下发。**这独立印证了「套餐是独立模板池、不在设备侧」的设计**（`pricing-model-0042.md` 第 4 章）。
2. **上限比预想紧得多**：刷卡金额最大 **25.0 元**，刷卡时间最大 **999 分钟**。方案里若出现更大数值，固件会返回 `0xC4` 错误码 4/5。

### 5.1 `0xC4` 错误码 = 计费下发失败的唯一观测点（A）

| 码 | 含义 | 码 | 含义 |
| --- | --- | --- | --- |
| 1 | 模式超范围 | 8 | **分档比例值设置错误** |
| 2 | 音量超范围 | 9 | 充满自停设置错误 |
| 3 | 投币时间超范围 | 10 | 浮充功率超范围 |
| 4 | **刷卡时间超范围** | 11 | 浮充时间超范围 |
| 5 | **刷卡金额超范围** | 12 | 充电器移除检查时间超范围 |
| 6 | 刷卡退费设置错误 | 13 | 温度保护值超范围 |
| 7 | **分档功率设置错误** | 0 | 成功 |

**这直接回答了未决项 17 的实现路径。** 此前记录是「需向厂商确认下发接口与超时/重试语义」，现在可确定：

- 下发通道 = `0xC3`
- 成功/失败 = `0xC4` 携带的具体错误码
- **失败是可分类的**（4=时长超限、5=金额超限、7=功率档位非法、8=比例非法），不必笼统记「下发失败」

超时/重试语义仍需实机确认（C）。

## 6. 厂商文档自身的三处缺陷（照抄会踩坑）

### 6.1 充电档位的 0 基 / 1 基不一致 🔴

| 指令 | 字段 | 取值 |
| --- | --- | --- |
| `0xB3` 单端口状态 | 充电档位 | **0**=第一档 … **4**=第五档 |
| `0xB4` 本地启动 | 充电档位 | **1**=第一档 … **5**=第五档 |
| `0xBB` 订单结束 | 充电档位 | **1**=第一档 … **5**=第五档 |
| `0xC2` 分档上报 | 分档前/后工作档位 | **1**=第一档 … **5**=第五档 |

**同一份文档里 B3 是 0 基、其余三处是 1 基。** dc589 目前未解析档位，尚未踩中；一旦实现就会踩。**必须在解析处显式注明基址并单测锁死。**

### 6.2 「充电金额」单位不一致 🔴

| 指令 | 字段 | 类型 | 单位 |
| --- | --- | --- | --- |
| `0xB3` / `0xB4` | 充电金额 | BIN **1** | `0x01 = 0.1 元` |
| `0xBB` | 充电金额 | BIN **2** | `0x0001 = 0.01 元` |
| `0xB6` | 扣费金额 | BIN **1** | `0x01 = 0.1 元` |
| `0xBD` / `0xB7` | 余额 | BIN **2** | `0x01 = 0.1 元` |

**BB 的单位比 B3/B4 细 10 倍。** 混用会得到差 10 倍的金额。dc589 未解析金额字段，尚未踩中。

### 6.3 停止原因缺 8（A）

`0xBB` 停止原因取值：0 时间用完、1 移除充电器、2 充满自停、3 故障停止、4 功率过大停止、5 离线卡退费停止、6 启动未连接充电器、7 远程停止、**9** 高温停止（5.8.3 新增）、10 电量用完。

**8 未定义。** 遇到 8 不能落进 default 猜含义。

> 顺带确认两个易混淆项：`4 功率过大停止` 是**保护性停机**，不是计费档位；`5 离线卡退费停止` 是**退费**触发，不是计费触发。

### 6.4 指令表序号错位（无功能影响）

5.8.3 指令一览表把 `0xBD` 插在序号 18、位于 `0xB6`(17) 与 `0xB7`(19) 之间；正文小节号也从 23 跳到「19. 本地充电上报」再到 22。`0xB4` 字段表也漏写了序号 1（端口号）。**只影响阅读，不影响实现。**

## 9. 建议的处理顺序

| 优先级 | 动作 | 理由 |
| --- | --- | --- |
| P0 | 实现 `0xC7` → `0xC3` → `0xC4` 链路 | 不做则**真机连不上**，一切无从验证 |
| P0 | `default` 分支改为「记录并忽略未知指令」而非断链 | 未知指令不应等于连接失败 |
| P1 | 把模拟器改成按 5.8.3 工作流程发 `C7` | 当前模拟器与协议不符，掩盖了 P0 缺陷 |
| P1 | 登记未决项 22（功率是类型还是修饰） | 决定 `device_power` 是否留在枚举里 |
| P1 | 方案 6.7 补「`server_*` 需主动停机回路」 | 协议明文要求，当前方案缺失 |
| P2 | 解析 `0xB4`/`0xB6`/`0xBD`/`0xD0`，打通投币与在线卡 | 现有链路只覆盖扫码 |
| P2 | 实现 `0xA6`/`0xA7` 心跳间隔 | 降低固定 90s 超时的猜测成分 |
| P3 | 档位/金额解析时按第 6 节显式处理基址与单位 | 现在不写，等实现时必踩 |
