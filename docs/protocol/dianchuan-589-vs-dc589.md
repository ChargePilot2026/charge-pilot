# 电川协议 5.8.9 与 dc589 实现差异对照（定论版）

> **对照物**：《电瓶车对接协议 5.8.9 版本 2024.11.28》（36 条指令 + 参数配置表 + OTA 附件）对照本仓库 `internal/gateway/protocol/dc589` 实现。
> **辅以**：《杭州电川科技协议 5.8.3 版本 2023.01.01》，用于建立版本谱系。
> 本文档**取代**同目录 `dianchuan-583-vs-dc589.md`（基于 5.8.3 的初版），其中三条结论已在第 2 节明确更正。

## 方法论声明

1. **字段表优先于样例注释。** 两份 PDF 的样例报文与其字段表存在多处自相矛盾（见第 7 节），且样例中的十六进制数字经文本提取后可能已失真。因此**长度与结构以 LEN 算术自洽处和字段表为准**，不对样例注释的字面值下结论。
2. 证据分级沿用 `docs/pricing-model-0042.md`：**A** 文档明文 / **B** 文档与实现双向印证 / **C** 无法确认。

## 2. 对初版报告的更正（重要）

初版基于 5.8.3 得出三条结论，拿到 5.8.9 后**其中一条必须撤回**：

| 初版结论 | 更正 | 依据 |
| --- | --- | --- |
| 🔴「`0xC7` 是设备登录后必发，真机必然被断链」 | ❌ **撤回**。5.8.5 明确「修改工作流程不向平台发送 `0xC7` 指令」，5.8.9 工作流程为「连接 → `0xA0` 登录 → 发送心跳」 | 5.8.5 变更记录 + 5.8.9 第 4 节 |
| 「停止原因 `8` 未定义」 | ❌ **撤回**。5.8.8 补充 `8 = 烟感停止`，5.8.9 停止原因表已完整 0–10 | 5.8.8 变更记录 + 5.8.9 `0xBB` 字段表 |
| 「C3/C4/C7 是配置下发通道」 | ✅ **保留，且更重要**——但风险等级从「必断链」降为「老固件兼容」 | 5.8.9 `0xC7` 备注「目前部分主板不会主动获取」 |

**教训**：初版把 5.8.3 的工作流程当成了现行流程。**协议文档有版本，同一份厂商的旧版本与新版本在「工作流程」这种行为约定上会直接相反**——而这类约定恰恰是编解码字段表里看不出来的。下次拿到协议，先查变更记录再读正文。

### 2.1 降级后仍需处理的 `0xC7` 风险

- 5.8.9 指令表对 `0xC7` 的备注是「**目前部分主板不会主动获取**」（A）。「部分」意味着**仍可能有在跑 5.8.3 及更早固件的板子会发**。
- `0xC2` 备注同理：「目前部分主板不会主动上报」。
- `internal/gateway/protocol/dc589/adapter.go:231` 的 `default` 分支对未知指令 `return error` → 断链。

**结论不变，但理由变了**：这不再���「所有真机都会断」，而是「**遇到未知/可选指令就断链**是错误的健壮性设计」。修法也不变——未知指令应记录并忽略，而非终止连接。优先级从 P0 降为 **P1**，但仍应在实机前修好。

## 5. 计费相关的实质发现

### 5.1 `10/11/12` 已确认：长充模式（A）

5.8.7 在拓展协议中加入长充模式，5.8.9 在 `0xB7` 充电类型中给出定义：

> **拓展：长充模式（该模式下，主板会持续供电，直到时间/电量用完或远程停止，**此模式正常状态下不使用**）**
> `10 = 时间长充`、`11 = 电量长充`、`12 = 平台计费长充`

- dc589 的命名 `LongTime` / `LongEnergy` / `LongPlatformBilling` **正确**（B）。初版报告中此项存疑，现已消除。
- `0xBB` 的充电类型字段同样接受 `0x10/0x11/0x12`（5.8.8 补充）。
- ⚠️ **「正常状态下不使用」是厂商的明确约束。** `BuildStart` 当前接受 6 个值且无任何场景限制，`ChargeMode(command.Mode)` 是直接类型转换——**上层若误传 10/11/12 会被原样下发**。建议在业务层限制 `server_*`/`device_*` 只能映射到 `0/1/4`，长充仅保留给运维排障通道并单独审计。

### 5.2 `0xE0/0xE1`：协议级的「不分档」开关（A）

5.8.9 新增。字段：`控制类型`（0 查询 / 1 设置）、`操作类型`（**0 = 移除功率**）、`参数`（0.1W 单位）、`预留 2 字节`。

这与 5.8.1「平台计费模式下主板不分档」是同一件事的两条实现路径：充电类型 `4` 天然不分档，而 `0xE0` 提供**主动关闭分档**的能力（5.8.7 拓展协议中与长充模式一并引入）。

**这是「服务端计费」在协议上的正式入口，目前完全未实现。**

### 5.3 5.8.9 新增「本地电量计费模式」（A）

这是 5.8.9 相对 5.8.3 唯一的计费语义变更。参数配置表第 1 项：

| 5.8.3 | 5.8.9 |
| --- | --- |
| `0 = 先消费`、`1 = 先按键`、`2 = 免费模式` | `0 = 时间先消费`、`1 = 时间先按键`、`2 = 免费模式`、**`3 = 电量先消费`、`4 = 电量先按键`** |

且第 3、4 项参数名改为「本地投币一次**时间/电量**」「本地刷卡一次**时间/电量**」，单位说明变为：

> 时间模式下 `1 = 1 分钟`；**电量模式下 `100 = 1Kwh`**

🔴 **同一个字段的单位随运行模式改变。** 同一字节值 `240` 在时间模式下是 240 分钟，在电量模式下是 2.4 度。解析与回写都必须先读运行模式，**绝不能把该字段当作固定单位处理**。这是本轮最容易造成 100 倍金额误差的一处。

**含义**：`device_energy` 不只有远程一条路径。设备本地投币/刷卡也能按电量扣费，这与 `0xB4`/`0xB6` 本地上报链路绑定——而这条链路 dc589 完全未实现。

### 5.4 `0xA4` 端口状态遥测是可选的，且开关在我们手上（A）

> 如果在 `0xA6` 的指令中在端口状态标志位置 1 打开则上传下面的数据，如果置 0 则不上传。（5.8.6 新增该开关）

dc589 的 `ParseHeartbeat` 两种形态都支持，**但从不发送 `0xA6`**。这意味着**端口级遥测能否拿到，取决于板子出厂默认值**——我们既没开它，也无从知道它当前是开是关。这是「能解析」与「能收到」之间的差别。

### 5.5 12 路以上主板的心跳是双包（A）

5.8.7 新增，`0xA4` 与 `0xB1` 均适用：

> 12 路以上主板心跳包会连发两次，第一包包含前十路的充电数据，后一包包含后面记录的充电数据；两包数据域的前 12 个数据是相同的；两包当中「正在充电端口数」包含的是主板所有的充电路数

dc589 每次 `ParseHeartbeat` 返回一个独立 `HeartbeatData` 并作为独立事件落库，**不合并两包**。后果：每条心跳记录里的「正在充电端口数」是全端口数，但只带其中一半的端口明细——**单条记录是残缺的**，而按单条查询的界面/告警会误判。

文档本身在此处自相矛盾（`B1` 写「前 9 个数据相同」，`A4` 写「前 12 个」；又说「12 路以上」但「前十路 + 后十路 = 20 路」），**合并规则必须实机确认**。

### 5.6 心跳超时语义：文档给了规则，代码是猜的

5.8.9 工作流程（A）：

> 上电一直发送 `0xA0` 指令间隔 **3 秒**，直到回复 `A1`；在已经连网过程中如果 **3 次未回复心跳则重新发送 `0xA0`**。

dc589 使用 **90 秒固定读超时**（`adapter.go:125`），与「3 次未回复」无对应关系，且心跳间隔本身由 `0xA6` 设定（我们不设）。**当前的超时值是拍脑袋的**。

## 6. 配置下发（`0xC3`）的准确形态

### 6.1 `0xC4` 错误码 = 下发失败的分类信号（A）

| 码 | 含义 | 码 | 含义 |
| --- | --- | --- | --- |
| 0 | 成功 | 7 | **分档功率设置错误** |
| 1 | 模式超范围 | 8 | **分档比例值设置错误** |
| 2 | 音量超范围 | 9 | 充满自停设置错误 |
| 3 | 投币时间超范围 | 10 | 浮充功率超范围 |
| 4 | **刷卡时间/电量超范围** | 11 | 浮充时间超范围 |
| 5 | **刷卡金额超范围** | 12 | 充电器移除检查时间超范围 |
| 6 | 刷卡退费设置错误 | 13 | 温度保护值超范围 |

**这确定了未决项 17 的实现路径**：下发 = `0xC3`，结果 = `0xC4` 的具体错误码，失败**可分类**到具体字段。剩余未确认的只有「应答是否一定到达、超时如何处理」（C，需实机）。

### 6.2 `0xC3` 报文长度存在二义性（C）

- 参数配置表附件列出 **28 个字段**（含第 23–28 项「第六~八档功率/比例」，注明**仅 2 路智能插座 8 档机型**）。
- 5.8.9 的 `0xC3` 样例只含前 **22 个字段**（33 字节），且样例 `LEN` 算术自洽（`0x29 = 41 = 8 + 33`）。

**因此 `0xC3` 的 DATA 长度至少有两种可能：33 字节（5 档机型）与 43 字节（8 档机型）。** 不能写死长度校验，否则会在 8 档机型上全部拒绝。需实机确认，或按长度自适应解析并对尾部缺失字段做校验降级。

### 6.3 参数配置表与乐摇摇字段的对应（更新）

| `0xC3` 字段 | 5.8.9 取值 | 对应本项目 |
| --- | --- | --- |
| 设备运行模式 | 0/1/2/**3/4** | `Spec.DefaultChargeWay` |
| **本地刷卡一次时间/电量** | 0–999，**单位随模式变** | `Package.DurationMinutes` / 电量 |
| **刷卡扣费金额** | 0–250 → 0.0–25.0 元 | `Package.PriceCents`（**上限 25 元**） |
| 刷卡是否退费 | 0/1 | `CardRefundRule` |
| 第一~五档功率值 | 0.1W，高档必须 > 低档 | 设备侧档位表 |
| 第一~五档分档比例 | **第一档固定 100%，下发其它值必然失败** | `TierRatio` |
| 充满自停 | 0/1 | `Package.StopWhenFull` |
| 浮充功率/时间、拔除时间 | 1–50W / 120–10800s / 5–3600s | 未建模 |
| 温度保护值 | 0xFF 关闭，50–100 | 设备安全，非计费 |
| 第六~八档功率/比例 | 8 档机型专属 | 未建模 |

**两条佐证成立：**

1. **设备侧只存一套卡计费参数**（一个金额 + 一个时间/电量），多套餐的选择在平台侧，通过 `0xB7` 的「充电时间/电量」下发。这独立印证了 `pricing-model-0042.md` 第 4 章「套餐是独立模板池、不在设备侧」。
2. **硬上限比预想紧**：金额 ≤ 25.0 元，时间/电量 ≤ 999。超出 `0xC4` 会回错误码 4/5。方案中的取值范围必须与之对齐，否则会稳定地收到拒绝。

## 8. 与 `pricing-model-0042.md` 的关系

| 方案结论 | 5.8.9 是否支持 | 说明 |
| --- | --- | --- |
| 两类六种（`server_*` / `device_*`） | ✅ 支持 | 充电类型 `0/1` = 设备侧，`4` = 服务端侧 |
| `server_*` 需平台主动停机 | ✅ **强化支持** | `4=平台计费` 主板不分档；另有 `0xE0` 移除功率作为显式入口 |
| 设备计费「设备是执行方」 | ✅ 支持 | `0/1` 到量自停；`10/11/12` 长充需远程停止 |
| 套餐 = 价格 + 消耗口径 | ✅ 强支持 | `0xC3` 的刷卡金额 + 刷卡时间/电量 |
| 设备侧只存一套卡参数、套餐在平台侧 | ✅ 强支持 | `0xC3` 仅一组金额与时长 |
| **未决项 22：功率是独立类型还是分档修饰** | 🟡 **部分解答，仍需确认** | 5.8.9 的 B7 充电类型只有 `0/1/4/10/11/12`，**没有「按功率」类型**；功率始终以 `0xC3` 的档位值 + 分档比例呈现。但**仍未证明 5.8.9 不支持余额型计费**——`0xE0`「移除功率」的出现说明固件侧有非分档的功率控制逻辑，值得向厂商追问 |
| **未决项 23：`server_*` 停机回路** | ✅ 支持，且新增 `0xE0/0xE1` 为配套通道 | |

**结论：未决项 22 保持未决，但可排除「协议存在按功率的独立充电类型」这一支。**

## 10. 建议的处理顺序（已按 5.8.9 修正）

| 优先级 | 动作 | 理由 |
| --- | --- | --- |
| **P0** | `default` 分支改为「记录并忽略未知指令」 | 老固件会发 `0xC7`/`0xC2`；未知指令不应等于断连 |
| **P0** | 限制 `BuildStart` 的场景映射，`10/11/12` 仅开放给运维通道 | 文档明写「正常状态下不使用」，当前无任何限制 |

| **P1** | 实现 `0xA6`/`0xA7`，显式打开端口状态上报 | 不做则端口遥测能否收到取决于板子默认值 |
