### 1.1 排除项

为避免选型扩散,本规格**明确不做**的选型:

- 不使用 OCPP 协议(已在需求文档明确)
- 不使用 gRPC(同步通信统一走 HTTP/JSON)
- 不使用 Kubernetes(单客户单部署,Docker Compose 已足够)
- 不使用 PostgreSQL / MongoDB / 时序数据库(单 MySQL 覆盖所有业务)
- 不使用 Vue / uniapp / Taro(React + 微信原生已锁定)
- 不使用 HashiCorp Vault / 云厂商 KMS(密钥文件+环境变量足矣)
- 不引入微服务网格 Istio / Linkerd

|---|---|---|---|
| Rust | 1.98.1 | 2026-09 | edition 2024 |
| Tokio | 1.53.1 | 2026-07 | MSRV 1.71 |
| Axum | 0.8.9 | 2026-04 | MSRV 1.80,路由语法 `{param}` |

| MySQL | 8.4.10 LTS | 2026-06 | 8.4 系列 LTS 至 2032 |
| Redis | 8.10 | 2026 | 引入 vector set、Redis Flex |

| OpenTelemetry Rust | 0.31+ | 2025-09 | OTLP temporal preference |

**升级策略**:

- **小幅版本**(如 Tokio 1.53.1 → 1.54.x):跟随官方,**每月评估一次**(CI 触发 cargo update / npm outdated)。
- **次版本**(如 Axum 0.8 → 0.9):**评估期 1 个月**,阅读 changelog,在测试环境跑通后升级。
- **主版本**(如 MySQL 8.4 → 9.x):**不主动升级**;待客户环境要求时再迁移。
- **安全补丁**(如 Caddy CVE 修复):**2 周内必须升级**(运维订阅含远程升级支持)。
- **MSRV 变化**:每次升级前检查依赖链 MSRV,确保所有 crate 可在统一 MSRV 编译。

> **关键原则**:**不锁定到具体小版本**(`Axum = "0.8.9"` ❌),而是锁定到次版本范围(`Axum = "0.8"` ✓),让 Cargo 自动选择 0.8.x 系列最新补丁。但**主版本升级必须人工触发**。

## 二、系统架构

### 2.1 整体拓扑

系统分**对外流量**与**内部通信**两类边界。共 **5 个服务**(原 admin 服务拆分为 **user** 与 **admin**)。

#### 为什么拆 user 与 admin

- **资源竞争**:小程序 API(扫码/充电/支付回调)高 RPS,PC 后台(审核/导出/配置)低 RPS,合在同一进程相互挤压
- **故障域隔离**:用户 API OOM 不应拖垮后台运营
- **安全姿态**:PC 后台是高权限入口,与公开 API 同进程增加横向风险
- **扩缩容粒度**:充电峰值只需扩容 user,后台不浪费

#### 对外流量(从客户端到服务)

```
                 小程序用户(微信内打开)
                         │
                         │ ① HTTPS /api/v1/user/... (REST + JWT)
                         ▼
                  ┌──────────────┐
                  │   Caddy 2.x  │  ② TLS 终止 + Let's Encrypt 自动续期
                  │   :443       │  ③ 按路径反代:
                  └──────┬───────┘     - /api/v1/user/* → user :8081
                         │            - /api/v1/admin/* → admin :8082
                         ▼            - /admin/* → admin :8082 (PC 后台 SPA)
                  ┌──────────────┐
                  │  user    │  ④ 用户鉴权 / 业务路由 / user_db 读写 / 调内部服务
                  │  :8081       │
                  └──────────────┘

                  ┌──────────────┐
                  │  admin   │  ⑤ 管理鉴权(双因素待二期) / 角色权限 / admin_db 读写 / 配置下发
                  │  :8082       │
                  └──────────────┘

                  ┌──────────────┐
                  │   PC 后台     │ ──HTTPS──▶ Caddy ──▶ admin
                  │  React+antd  │
                  └──────────────┘

                  ┌──────────────┐
                  │  充电桩       │ ──TCP/MQTT 长连接──▶ gateway :9100/:1883(直连,不过 Caddy)
                  └──────────────┘
```

                          │            │           │
                          │   ┌────────▼───────┐   │

                                      │

#### 小程序用户流量的完整路径(以"扫码启动充电"为例)

1. **小程序端**(`miniprogram/`):用户扫码 → `wx.login()` 拿 code → `POST https://api.example.com/api/v1/user/scan/start`
2. **Caddy**(端口 443):TLS 终止 → 按路径反代到 `user:8081`
3. **user**:
   - 验证 JWT(可能)
   - 调 `code2Session` 拿 `openid`
   - 调 `gateway` HTTP API:`POST /internal/start-charge`(设备启动指令)
   - 调 `billing` HTTP API:`POST /internal/quote`(预扣费预估)
   - 调微信支付下单:`POST https://api.mch.weixin.qq.com/v3/pay/transactions/jsapi`
   - 返回小程序:`{ payment_params: ... }`
4. **小程序**:`wx.requestPayment()` 调起支付
5. 用户完成支付 → 微信回调:`POST /api/v1/user/payment/wechat/callback`(**直接到 Caddy → user**)
6. **user** 验签 → 发布 `charge_started_stream` 事件 → Redis Stream
7. **gateway** 消费 Stream → 发送 MQTT 控制指令到设备 → 设备开始充电
8. 充电中:gateway 通过 MQTT 持续接收遥测 → 持久化到 `gateway_db.telemetry` → 越界则发布 `alert_stream` 事件
   - 同时 gateway 发布 `device_event_stream` → **user** 消费并填充 Redis 缓存 `snapshot:{order_id}`
   - 小程序每 5 秒 `GET /api/v1/user/charge/ongoing/snapshot` 拉取实时数据(详见 § 3.2.3)
9. **worker** 消费 `alert_stream` → 触发阈值复核 + 推送 Webhook(由 admin 调度)
10. 用户结束充电(拔插头 / 主动停止):gateway 检测状态变化 → 发布 `charge_ended_stream` 事件
11. **billing** 消费 → 计费 / 价费分离 / 多方分账 → 写 `billing_db` → 发布 `refund_required_stream` 事件(如果失败/超时/取消)
12. **user** 同时消费 `charge_ended_stream` → 关闭小程序轮询(`poll_continue: false`)→ 触发小程序跳转充电结束页
13. **user** 消费 `refund_required_stream` → 调微信退款 → 通过小程序消息通知用户

#### 关键边界

| 边界 | 协议 | 鉴权 | 端口 |
| --- | --- | --- | --- |
| 小程序 → user | HTTPS(REST + JSON) | JWT(openid) | 443(经 Caddy)→ 8081 |
| PC 后台 → admin | HTTPS(REST + JSON) | JWT(角色) | 443(经 Caddy)→ 8082 |
| 充电桩 → gateway | TCP 长连接 / MQTT | 仅 device_id | 9100 / 1883(直连,**不过 Caddy**) |
| 微信支付回调 → user | HTTPS(POST) | 微信签名 | 443(经 Caddy)→ 8081 |
| admin → user(读用户/订单) | HTTP(REST) | 服务间共享密钥 | 内部网络 |
| user ↔ billing | HTTP(REST) | 服务间共享密钥 | 内部网络 |
| admin ↔ billing | HTTP(REST) | 服务间共享密钥 | 内部网络 |
| gateway → user / admin | HTTP(状态查询) | 服务间共享密钥 | 内部网络 |
| 各服务 ↔ Redis | RESP 协议 | Redis 密码 | 6379 |
| 各服务 ↔ MySQL | MySQL Wire | MySQL 用户名密码 | 3306 |

**注意**:
- Caddy **不代理 TCP 9100 / MQTT 1883**——设备长连接直连 gateway
- **admin 不直接读 user_db**——通过 HTTP 调 user 获取用户/订单数据,保持数据库边界
- **微信支付回调走 user**(因为支付由小程序发起)

### 2.3 服务间通信

| 场景 | 通信方式 |
| --- | --- |
| **同步调用**(gateway 调 billing 计算费用 / admin 调 billing 查询分账) | HTTP/JSON(REST 风格),OpenAPI 3.0 规范,使用 `reqwest` 客户端 + `serde_json` |
| **异步事件**(充电结束通知 → 计费/账单/通知/告警分析) | Redis Stream:生产者写入,消费者 Worker Group 拉取 |
| **配置下发**(PC 后台 → 设备) | admin → Redis Stream → gateway → 设备 |
| **跨服务数据共享** | **不共享数据库**;只通过 HTTP / Stream 通信 |

### 2.4 数据库隔离策略

- 每个服务**独立 MySQL schema**(database),4 个 schema 同实例部署。
- 服务 A 不得跨 schema 查服务 B 的表;必须通过 HTTP 调服务 B 的 API。
- 单 MySQL 进程多 schema 部署,**不引入多实例**(单客户体量用不到)。
- 跨服务事务:使用**最终一致性** + 补偿事件(详见 § 5.4)。

## 三、服务详细设计

### 3.1 gateway 服务

#### 3.1.1 模块结构

```
gateway/
├── src/
│   ├── main.rs              // Tokio 启动入口
│   ├── config.rs            // 环境变量加载
│   ├── protocol/
│   │   ├── mod.rs
│   │   ├── tcp.rs           // TCP 监听 + 帧解析
│   │   ├── mqtt.rs          // rumqttd Broker 嵌入
│   │   └── adapter/         // 硬件厂适配器(每个厂商一个子模块)
│   │       ├── vendor_a.rs
│   │       └── vendor_b.rs
│   ├── device/
│   │   ├── registry.rs      // device_id 注册 + 在线状态
│   │   └── session.rs       // 连接会话状态
│   ├── telemetry/
│   │   ├── parser.rs        // 七重防护字段解析
│   │   └── forwarder.rs     // 持久化 + Redis Stream 发布
│   ├── alert/
│   │   ├── thresholds.rs    // 阈值规则
│   │   └── publisher.rs     // Redis Stream 发布告警
│   ├── api/                 // 对内 HTTP API(状态查询)
│   └── error.rs
├── migrations/              // sqlx 迁移文件
└── Cargo.toml
```

#### 3.1.2 协议接入层

**TCP 服务**:
- 端口 `0.0.0.0:9100`(可配置)
- Tokio `TcpListener` 接收连接,每连接一个 `tokio::spawn` 协程
- 帧解析:按各厂商私有协议(每个 adapter 实现 `Adapter::parse_frame(&[u8]) -> Frame` trait)
- 心跳超时:配置项 `tcp.idle_timeout_secs`(默认 90s)
- 连接数限制:配置项 `tcp.max_connections`(默认 10000)

**MQTT Broker**:
- 端口 `0.0.0.0:1883`(可配置)
- 嵌入 `rumqttd` 作为 crate 依赖(避免外部 Broker 进程)
- Topic 命名约定:`charge/{vendor_id}/{device_id}/{type}`(上行 / 下行)
- QoS:上行 QoS 1(保证至少一次);下行 QoS 1
- 客户端认证仅校验 `device_id`(参见 § 6.2)
- Broker 内部不做权限隔离(因为单客户部署,所有设备属同一客户)

#### 3.1.3 关键数据流

```
设备上报遥测 → TCP/MQTT 帧解析 → Adapter 标准化
  → 持久化到 gateway_db.telemetry(metrics 表)
  → 七重防护字段实时校验(§ 需求文档 6.4)
  → 越界则发布 alert_stream 事件
  → 状态变更(空闲/充电中/充满/故障) 发布 device_event_stream 事件
```

#### 3.1.4 告警阈值与通道(客户自配原则)

**不预设任何默认阈值**——所有告警规则(过流 / 过温 / SOC 异常 / 通信中断 / 功率骤降等)由客户运维在 admin PC 后台自定义配置。理由:

- 不同部署场景(小区 / 园区 / 街边 / 工厂)的安全阈值差异极大,系统预设容易误报或漏报
- 客户对自己设备的物理特性最清楚,自配阈值更准确
- 降低系统复杂度(MVP 阶段不背默认值)

**告警事件流程**:

```text
gateway 检测"越界" → 发布 alert_stream 事件
  → worker 消费 → 调 admin 内部 API 写入 alert 记录
  → admin 根据订阅规则推 Webhook(由客户运维配置订阅)
  → alert 记录展示在 admin PC 后台告警列表
```

**告警通道**:

- **唯一通道**:Webhook(由客户在 admin 后台"Webhook 订阅"中配置接收 URL + HMAC 签名密钥)
- 邮件 / 短信 / 企业微信:**本期不内置**(客户可通过 Webhook 自行集成,如邮件网关)
- 通道选择是**客户决策**,不是系统决策

**配置项**(`admin_db.alert_rule` 表):

| 字段 | 说明 |
| --- | --- |
| `device_id_pattern` | 适用设备(`*` 表示全部) |
| `metric` | 监测字段(`voltage_v` / `current_a` / `temperature_c` / `battery_soc` / `power_w` / `meter_kwh`) |
| `op` | 比较运算符(`>` / `<` / `!=` / `between`) |
| `threshold` | 阈值(数值或区间) |
| `window_seconds` | 持续时长(避免瞬时尖刺误报) |
| `severity` | `warning` / `critical` / `fatal` |
| `enabled` | 是否启用 |

#### 3.2.3 充电中实时数据(5s 轮询)

充电进行中,小程序需要实时展示功率 / 电量 / 费用 / 温度等数据。**采用 5s HTTP 轮询**(简单可靠,微信小程序支持完善)。

**轮询流程**:

```
┌──────────┐ 5s 1次  ┌──────────┐ 读缓存      ┌─────────────┐
│  小程序   │ ──────▶ │ user-api │ ──────────▶ │ Redis 缓存   │
│ 充电中页 │          │  :8081  │            │ snapshot:    │
│          │ ◀────── │         │ ◀────────── │ {order_id}   │
└──────────┘ JSON响应 └──────────┘            └─────────────┘
```

**API 契约**:`GET /api/v1/user/charge/ongoing/snapshot?order_id={order_id}`

请求:

| Query 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `order_id` | string | 是 | 当前充电订单 ID |

响应(200 OK):

```json
{
  "code": 0,
  "data": {
    "order_id": "ORD-2026-...",
    "charge_state": "charging",       // idle | charging | full | fault
    "current_power_w": 285.5,         // 实时功率
    "charged_kwh": 0.85,             // 累计电量
    "current_cost": 1.20,             // 累计费用(元)
    "estimated_remaining_min": 165,   // 预计剩余分钟数(按实时功率估算)
    "temperature_c": 38.5,            // 桩端温度
    "voltage_v": 220.5,               // 充电电压
    "elapsed_seconds": 1830,          // 已充电秒数
    "poll_continue": true,            // 是否继续轮询(true=继续,false=充电已结束)
    "next_poll_after_ms": 5000        // 客户端下次轮询间隔(服务端可动态调整)
  }
}
```

特殊响应:
- **`poll_continue: false`**:充电已结束(用户主动停止 / 充满自停 / 超时),客户端停止轮询,跳转充电结束页
- **`410 Gone`**:订单不存在或已关闭超过保留期
- **`404 Not Found`**:订单未在充电中(可能已结束且清理)

**数据源与缓存**:

| 数据 | 来源 | 缓存策略 |
| --- | --- | --- |
| 实时功率 / 电压 / 温度 | `gateway_db.telemetry` 最新记录 | Redis 缓存 `snapshot:{order_id}`,TTL 10s |
| 累计电量 / 费用 | billing 服务消费 `charge_ended` 事件后的中间态 | 由 user-api 按需计算 |
| 剩余时间 | 按实时功率与目标充满时间估算 | 服务端计算 |
| 充电状态(`charge_state`) | gateway 上报的实时状态 | 同 snapshot 缓存 |

**缓存填充机制**(双路径):

1. **被动路径**(`user-api` 收到轮询请求时):若 Redis 缓存 miss,直接查询 `gateway_db.telemetry` + `billing_db.order`,回填缓存(TTL 10s)。
2. **主动路径**(`worker` 消费 `device_event_stream`):遥测变化或充电状态变化时,主动更新 Redis 缓存 → 保证下次轮询响应 P99 ≤ 50ms。

**轮询频率策略**:

| 网络类型 | 默认间隔 | 可动态调整 |
| --- | --- | --- |
| WiFi | 5000ms | `next_poll_after_ms` |
| 4G/5G | 5000ms(默认) | 同上 |
| 弱网(<2G/3G) | 10000ms | 服务端识别 UA 返回 |

服务端通过响应中的 `next_poll_after_ms` 提示客户端下次轮询间隔,客户端必须遵守。

**终止条件**:

- 服务端返回 `poll_continue: false`(充电已结束)
- 客户端累计 3 次 HTTP 5xx → 提示用户"网络异常,正在重试"
- 客户端切到后台超过 60s → 停止轮询;恢复前台后重新发起首次轮询

**负载估算**(单客户部署 5000 设备):

- 同时充电设备数约 10%:500 台
- 每设备 12 req/min = 6000 req/min = 100 req/s
- user-api 单实例 1000 RPS 远高于此负载(利用率 < 10%)
- Redis 缓存命中率 > 90%(因缓存 TTL 10s + 5s 轮询)
- 数据库 QPS:cache miss 时 1 SELECT = 100 req/s × 10% = 10 QPS,远低于 MySQL 上限

## 四、数据层

### 4.1 数据库选型

- **MySQL 8.4 LTS**(社区版,无国产适配层)。
- 字符集:`utf8mb4` + `utf8mb4_unicode_ci`,支持 emoji 与生僻字。
- 排序规则:`utf8mb4_0900_ai_ci`(MySQL 8.4 默认)。
- 隔离级别:`READ COMMITTED`(默认;不需要 REPEATABLE READ 的间隙锁场景)。
- 主键策略:统一 `BIGINT UNSIGNED AUTO_INCREMENT`,业务 ID 用 UUID 单独字段。

### 4.2 5 个独立 Schema

| Schema | 归属服务 | 主要表(部分) |
|---|---|---|
| **gateway_db** | gateway | `device`、`device_session`、`telemetry`、`raw_frame_log` |
| **user_db** | user | `user`(openid / 手机号绑定)、`port_view`(找桩缓存)、`wallet_account`、`wallet_txn`、`coupon`、`coupon_grant`、`membership_card`、`payment_order`、`refund_record`、`invoice_request` |
| **admin_db** | admin | `customer`(客户)、`customer_user_role`(管理员账号)、`role`、`permission`、`whitelabel_config`、`announcement`、`webhook_subscription`、`ota_package`、`invoice_review`、`audit_log`、`customer_service_config` |
| **billing_db** | billing | `meter_reading`、`order`、`order_charge`、`order_split`、`settlement`、`billing_cycle` |
| **worker_db** | worker | `scheduled_task`、`task_execution_log`、`reconcile_log`、`webhook_retry_queue`、`compensation_tx` |

**跨服务数据访问原则**:
- **完全禁止跨 schema 直连**(任何服务不得 `SELECT * FROM other_service_db.*`)。
- **admin 读用户/订单**:通过 HTTP 调 user 接口,不允许直连 user_db。
- **billing 读订单状态**:从 Redis Stream 消费 `charge_ended_stream` + HTTP 调 user 获取订单。
- **每个服务仅对自己的 schema 有读写权限**(MySQL 用户按 schema 授权)。

### 4.2.1 关键表归属说明

| 数据 | 归属 schema | 原因 |
|---|---|---|
| 终端用户(微信 openid / 手机号绑定) | user_db | 终端用户相关数据全归 user |
| 管理员账号(用户名密码 / 角色) | admin_db | 与 PC 后台运营绑定 |
| 支付订单 | user_db | 微信支付回调走 user |
| 退款记录 | user_db | 退款由 user 编排 |

| 审计日志 | admin-db | 所有 admin 写操作的审计 |

### 4.3 ORM 与查询

- **统一 sqlx**(无重型 ORM)。
- 编译期 SQL 校验:`sqlx::query!` 宏需要 `DATABASE_URL` 环境变量,CI 阶段设临时 MySQL 跑 migration 后编译。
- 复杂查询:允许 `sqlx::query_as!(Struct, ...)` 直接映射;**不引入 SeaORM / Diesel**。
- 事务:`sqlx::Transaction<'_, MySql>` 通过 `pool.begin()` 获取,`commit` / `rollback` 显式控制。
- 跨服务事务:**不实现**,用最终一致性 + 补偿事件替代(详见 § 5.4)。

### 4.4 数据库迁移

- **sqlx-cli** 管理迁移文件。
- 迁移目录:每个服务 `migrations/{timestamp}_{name}.sql`,时间戳由 `sqlx migrate add` 生成。
- 启动流程:服务启动时执行 `sqlx::migrate!()` 自动应用未执行的迁移。
- 迁移是**幂等且单向的**(不回滚);破坏性变更通过"加列 → 写双写 → 切读 → 删旧列"4 阶段。

### 4.5 索引策略

- **所有外键列必须建索引**。
- 订单 / 计费 / 分账表的 `(customer_id, created_at)` 复合索引(高频按客户范围 + 时间查询)。
- 设备遥测表按 `(device_id, created_at)` 索引,分区按月(>6 个月可清理至冷存储)。
- 不使用全文索引(若有需求,引入 Elasticsearch;本期不做)。

### 4.6 数据保留

- 业务表(订单/计费/分账/告警/操作日志):**保留 ≥ 3 年**(合规底线,见需求 § 13.3)。
- 设备遥测原始数据:保留 **12 个月**,聚合后保留 3 年。
- 备份:**每日全量 + 周期性增量,异地存储**;`mysqldump` + 二进制日志 binlog。
- 清理任务:worker_db `data_retention` 任务定期执行(详见 § 3.4)。

### 4.7 缓存策略

- **Redis 8+** 部署(单实例,Docker Compose 内)。
- 业务缓存对象:
  - 计费规则模板(TTL 10 min)
  - 分账模板(TTL 10 min)
  - 角色权限(TTL 5 min)
  - 白标配置(TTL 30 min)
  - 找桩站点摘要(TTL 1 min)
- 失效策略:写时主动 `DEL`,TTL 双保险。
- 雪崩防护:TTL 加 ±10% 随机抖动。

### 4.8 数据增长策略(单实例 + 适度分表)

单 MySQL 实例(8.4 LTS)足够覆盖单客户 5000 设备 / 5 年规模(~2000 万订单 + ~1.5 亿遥测)。**预先分表,避免在线 DDL 风险**。

| 表 | 分表键 | 分表数量 | 分表名规则 | 触发分表的阈值 |
| --- | --- | --- | --- | --- |
| `payment_order` | `created_at` 按月 | 按需(滚动 36 个月分区) | `payment_order_2026m09` | 单月订单 > 200 万 |
| `telemetry` | `device_id` hash | 16 张 | `telemetry_{0..15}` | 单表行数 > 1 亿 |
| `wallet_txn` | `created_at` 按月 | 按需 | `wallet_txn_2026m09` | 单月 > 100 万 |
| `audit_log` | `created_at` 按月 | 按需 | `audit_log_2026m09` | 单月 > 50 万 |
| 其他表(分账 / 退款 / 优惠券 / 发票 / 设备元数据 / 用户等) | 不分 | — | — | 按需评估 |

**分表路由层**:`crates/common-db/router.rs`,所有 SQL 在执行前按分表键路由到正确的物理表。**禁止业务代码手写分表名拼接**。

**分区维护**:`worker_db.data_retention` 任务每月 1 日滚动创建下月分区 + 删除超龄分区。

**升级路径**(应对未来增长):

| 数据规模 | 应对方案 | 触发条件(任一) |
| --- | --- | --- |
| ≤ 5000 设备 / 5 年 | 单实例 + 分表 | 当前默认 |
| 5000–20000 设备 / 5 年 | 单实例 + 归档(冷数据迁出)+ 只读从库 | 单实例 QPS > 5000 / P95 > 200ms |
| > 20000 设备 | 引入读副本 + 分库(按客户分片) | 客户实际增长触发 |

**不引入分布式 SQL**(TiDB / OceanBase):单客户单部署场景下运维成本远高于收益。

## 五、异步事件与一致性

### 5.1 Redis Stream 事件总线

- 单 Redis 实例,持久化 `appendonly yes`。
- 事件流命名:

| Stream | 生产者 | 消费者 | 用途 |
| --- | --- | --- | --- |
| `device_event_stream` | gateway | admin / worker / user | 设备状态变更(上下线/充电中/充满/故障)**+ 充电中快照缓存填充**(见 § 3.2.3) |
| `alert_stream` | gateway | admin | 告警事件(Webhook 推送) |
| `charge_ended_stream` | gateway | billing / user | 充电结束(触发计费/分账/退款 + 关闭 user 轮询) |
| `refund_required_stream` | billing | admin | 退款触发(自动退款/调微信 API) |
| `invoice_required_stream` | billing | admin | 发票申请(待人工审核) |
| `webhook_retry_stream` | admin | worker | Webhook 失败重试 |
| `ota_schedule_stream` | admin | worker / gateway | OTA 推送调度 |
| `comp_tx_stream` | 各服务 | 各服务 | 跨服务补偿事务 |

### 5.2 消息格式

统一 JSON:

```json
{
  "event_id": "evt_uuid_v4",
  "event_type": "charge_ended",
  "occurred_at": "2026-09-25T22:00:00Z",
  "producer": "gateway",
  "schema_version": 1,
  "payload": { /* 业务字段 */ }
}
```

### 5.3 消费者组

每个 Stream 一个消费者组(命名 `{stream}.cg`),每个服务实例一个消费者。`消费者组` 拉取 + ack 机制;失败重试 3 次后转入 DLQ(`{stream}.dlq`)人工处理。

### 5.4 最终一致性

- 跨服务事务**禁止使用分布式锁**(指跨服务的 Saga / 2PC / 长锁等待)。
- **端口级短锁例外**:同一进程内对单个端口(物理资源)做并发互斥时,允许 Redis `SETNX(port_id, holder, 30s)` 形式,**作用域 = 单端口,生命周期 ≤ 充电启动耗时**,不构成跨服务事务。详见 § 5.6。
- 模式:**事件驱动 + 幂等消费**。
- 退款场景:
  1. billing 写 `refund_record(status=pending)`
  2. 发布 `refund_required_stream` 事件
  3. admin 消费,调微信退款 API
  4. admin 更新 `refund_record(status=success/failed)` + 发布 `comp_tx_stream` 事件
  5. billing 消费 `comp_tx_stream`,标记订单最终状态
- 幂等保证:`event_id` 作为去重 key,所有 `refund_record` / `order` 表写入先查幂等表。

**微信支付回调幂等**(独立去重维度):

- 微信服务器**会重复推送同一笔支付通知**(网络抖动时常见,5 min 内最多推 3 次)
- `POST /api/v1/user/payment/wechat/callback` 入口先按微信 `transaction_id`(`支付订单唯一键`)查幂等表:
  - 已存在 → 直接返回 200 OK(不重复扣减余额 / 不重复发事件)
  - 不存在 → 处理回调 + 写入幂等表 + 发布 `charge_started_stream` 事件
- 幂等表:`payment_callback_idempotent(transaction_id, processed_at)`,保留 30 天
- 与 Redis Stream 的 `event_id` 幂等是**正交两套**:前者去重"重复回调",后者去重"重复消费"

### 5.5 端口级并发控制(扫码 → 启动充电)

**问题**:同一端口 5 秒内被两个用户扫码启动充电,如何避免双订单?

**方案**:Redis `SETNX(port_id, holder=order_id, ttl=30s)` 短锁 + 双重兜底。

```text
小程序 A 扫码 → user-api 收到 POST /charge/start
  ├─ SETNX(charge:lock:port_123, order_aaa, 30s)
  │   ├─ 成功 → 进入启动流程:查端口空闲 → INSERT order → 通知 gateway → 释放锁(订单状态进入 charging)
  │   └─ 失败 → 查询 holder 对应订单状态:
  │       ├─ holder 订单 status=charging → 返回 "端口已被占用,请选择其他端口"
  │       └─ holder 订单 status=created 但 30s 内未启动 → 强制释放并重试(异常路径)
  └─ gateway 收到启动指令 → 设备确认继电器闭合 → 订单状态 charging(锁自动过期或主动释放)
```

**双重兜底**(防止 Redis 锁丢):

1. **DB 唯一索引**:`payment_order(port_id, status='charging')` 加部分唯一索引 → 即使 Redis 锁失效,数据库层面拒绝重复 charging 订单
2. **gateway 端确认**:gateway 收到启动指令后,实际查询设备继电器状态;若已闭合,拒绝第二条启动(发 `port_already_in_use` 错误回 user)

**锁释放时机**:**不依赖 TTL 过期**(避免锁悬空),由持有方主动 `DEL`。若启动链路中途失败,worker 周期任务扫描 `charge:lock:*` 中 status=created 但 60s 仍未进入 charging 的记录,强制释放。

**为什么不算分布式锁**:锁只覆盖单个端口(物理资源互斥),生命周期 ≤ 充电启动链路(秒级),不阻塞其他服务,无死锁风险,不跨服务事务。

### 5.6 失败处理

- Redis Stream 消费失败:指数退避(2s / 4s / 8s / 16s / 30s),3 次后入 DLQ。
- 告警:`alert.dlq` 流入 worker_db,worker 周期任务重试 + 通知运维。
- 数据兜底:每个事件带 `schema_version`,consumer 拒绝不识别的 schema,触发告警。

## 六、协议层

### 6.1 TCP 设备接入

- **协议**:私有 TCP 协议(各家硬件厂不同)。
- **端口**:9100(可配置)。
- **库**:Tokio 原生 `TcpListener` + `tokio::sync::mpsc` + 各厂商 adapter。
- **帧格式**:每个 adapter 自定义(常见为 `length-prefixed` 或 `delimiter-based`)。
- **示例(伪代码)**:

```rust
// 每个 adapter 实现
trait Adapter: Send + Sync {
    fn vendor_id(&self) -> &'static str;
    fn parse_frame(&self, buf: &[u8]) -> Result<Frame, ParseError>;
    fn serialize_frame(&self, frame: &Frame) -> Vec<u8>;
}
```

### 6.2 设备认证

- 设备**仅校验 `device_id`**,**不校验 secret**(需求文档已明确)。
- 鉴权流:
  1. 设备 TCP/MQTT 连接建立后,首帧携带 `device_id`
  2. gateway 查 `gateway_db.device` 表,存在且 `status=enabled` 则接受连接
  3. 不存在则断开连接,记日志(运维告警)
- 鉴权失败重试:同一 IP 短时间内多次鉴权失败,临时封禁(配置项 `auth.fail_ban_seconds`,默认 60s)。
- **TLS**:本期**不启用** TCP/MQTT TLS(局域网/专网场景为主);二期再加。
- **`device_id` 格式约定**:
  - 长度:8–32 字符
  - 字符集:`[a-zA-Z0-9_-]`(字母 / 数字 / 下划线 / 连字符)
  - 厂商前缀:2–4 字母(如 `xx_xxxx_xxxx`,其中 `xx` 为厂商代码,见 `gateway_db.vendor` 表)
  - 大小写敏感,网关层不做大小写转换
  - 注册时 `gateway_db.device.device_id` 加唯一索引
- **设备时钟同步**:
  - 设备 RTC 时钟漂移是常见问题,遥测时间戳错乱会污染计费数据
  - 设备端要求:**每次联网成功时 NTP 同步**(NTP 服务器地址由客户在 admin 后台配置,默认 `pool.ntp.org`);同步失败时仍允许充电,但 `gateway_db.telemetry.timestamp_drift_ms` 字段记录偏差
  - 服务端校验:gateway 写入 `telemetry` 表前检查 `|server_ts - device_ts| > 30 min` 则标记 `timestamp_drift=true`;计费时**以服务端时间为准**(避免设备 RTC 错误导致充电时长异常)
  - 客户运维在 admin 后台"设备详情"页可看到每个设备的 RTC 漂移历史,作为设备健康度参考

### 6.3 MQTT 设备接入

- **Broker**:`rumqttd` crate 嵌入,Rust 进程内运行。
- **端口**:1883(可配置)。
- **客户端认证**:与 TCP 一致(仅校验 device_id)。
- **Topic 约定**:
  - 上行:`charge/{vendor_id}/{device_id}/telemetry` — 遥测
  - 上行:`charge/{vendor_id}/{device_id}/event` — 事件(状态变更/告警)
  - 下行:`charge/{vendor_id}/{device_id}/cmd` — 控制指令(配置下发/OTA)
- **QoS**:上下行均 QoS 1(保证至少一次);遥测频率高,**关闭 retain**。

设备上报字段 → 数据库列(需求文档 § 7.4):

### 6.5 离线数据补传机制(AB 组合)

设备在网络抖动 / 临时停电 / 维护期间会断开连接。**离线期间产生的遥测和事件必须回传**,否则计费 / 告警 / 充电结束判定全部失真。

**A 方案(优先,本地缓存 + 重连补传)**:

- 设备本地持久化最近 **60 分钟**遥测(降级模式:存储不足时缩短到 30 min 或 15 min)
- 存储介质:优先 Flash(SPI NAND ≥ 4 MB);无 Flash 的低端设备使用 RAM + 掉电保护电容(只缓存最近 5 min)
- 重连成功后,设备主动 POST `POST /api/v1/internal/device/backfill` 提交缓存(批量,每批 ≤ 500 条)
- gateway 按 **真实时间戳** 入 `gateway_db.telemetry` 表(不去重,允许相同时间戳多条,后续聚合时去重)
- 计费逻辑按补传后的真实数据计算

**B 方案(兜底,无缓存设备按最后已知值估算)**:

适用场景:老固件设备 / 低端设备(无本地存储)/ 长时间离线(> 60 min 缓存窗口)

- 设备重连后**不主动补传**,只上报"我刚恢复在线"事件
- gateway 检测到 `charge_state=charging` 但 `last_telemetry_ts > 5 min ago` → 标记订单为 `billing_mode=estimated`
- billing 计算时:
  - 功率 = 该端口最近 7 天成功订单的 P50 功率(端口画像)
  - 时长 = 离线开始到重连(或当前)的实际时长
  - **金额 = 估算功率 × 估算时长 × 阶梯电价**(电费部分)
  - 服务费按实际充电开始 / 结束时间正常计算
- 订单上明确标注"估算订单",小程序充电结束页提示"本次计费基于设备离线,如有疑问请联系客服"

**降级路径**:

```text
设备重连
  ├─ 检测到本地缓存(60 min 内数据) → 走 A 方案
  └─ 无缓存 / 缓存已过期 → 走 B 方案(估算订单)
```

**为什么 AB 组合**:

- A 保证新设备数据完整性,符合"计费准确"的合规底线
- B 保证老设备 / 异常场景下仍能结清订单,不出现"无法结束充电"的死局
- 用户侧感知差异:新设备无感,老设备看到"估算订单"提示

### 6.6 OTA 升级与失败检测(双触发)

需求文档已定:**全量发布 + 失败自动回滚**。本节规定"失败"的判定标准与回滚机制。

**升级流程**:

1. admin PC 后台上传固件包 → admin_db `ota_package` 表(签名 / SHA-256 / 版本号 / 适用设备型号)
2. 客户运维选定目标设备范围 → admin 发布 `ota_schedule_stream` 事件
3. gateway 消费事件 → 通过 MQTT 下行 `charge/{vendor_id}/{device_id}/cmd` 推送升级指令(携带 URL + 签名)
4. 设备下载固件 → 校验签名(SHA-256 + 厂商私钥签名)→ 写入**备份区**(非当前运行区)
5. 设备重启切换到备份区 → 启动后自检 → 上报 `ota_apply_result` 事件

**失败判定(双触发)**:

| 触发条件 | 检测端 | 判定 |
| --- | --- | --- |
| 固件签名验证失败 | 设备本地 | **立即回滚**到上一备份区 + 上报 `ota_failed(reason=signature_invalid)` |
| 升级窗口内无心跳 | gateway 端 | gateway 在 `ota_apply_window`(默认 **30 分钟**)内未收到设备任何 MQTT 上行 → 视作升级失败 → 推送回滚指令 + 上报 `ota_failed(reason=heartbeat_lost)` |
| 设备主动上报启动失败 | 设备本地 | 设备自检失败 → 立即回滚 + 上报 `ota_failed(reason=self_check_failed)` |

**回滚机制**:

- 桩端固件**双备份区**(A 区 / B 区),任何时候至少一个分区可启动
- 升级写入**非当前运行区**(若当前 A 区在跑,写入 B 区;切换后下次升级反过来)
- 回滚 = 重启切换到上一分区(无网络依赖,设备本地完成)
- 回滚后设备正常上线 → 上报 `ota_rollback_done` 事件

**回滚失败的兜底**:

- 设备两次连续回滚均失败(双分区都坏) → 标记设备为 `fault=fatal_ota`,需现场维护
- gateway 通过 `alert_stream` 上报 → admin PC 后台告警 + 客户运维触发现场处理

**不启用灰度**:需求文档明确不支持(全量发布)。同一型号的所有设备同时升级。

## 七、API 设计

### 7.1 REST 风格

- 资源命名:**名词复数**,如 `/api/v1/orders`、`/api/v1/devices/{id}`。
- HTTP 方法语义:
  - `GET` 读(只读)
  - `POST` 创建
  - `PUT` 整体替换
  - `PATCH` 部分更新
  - `DELETE` 删除
- 状态码:标准 HTTP(200 / 201 / 204 / 400 / 401 / 403 / 404 / 409 / 422 / 500)。
- 响应包装:

```json
{
  "code": 0,
  "message": "ok",
  "data": { /* 业务对象 */ },
  "trace_id": "abc123"
}
```

错误情况:

```json
{
  "code": 40001,
  "message": "参数错误",
  "data": null,
  "trace_id": "abc123",
  "errors": [{ "field": "amount", "rule": "min:0.01" }]
}
```

### 7.2 统一错误码

| 区间 | 用途 |
| --- | --- |
| 0 | 成功 |
| 1xxx | 通用错误(参数 / 鉴权 / 权限 / 资源不存在 / 内部错误) |
| 2xxx | 业务错误(订单状态冲突 / 余额不足 / 设备已占用 等) |
| 3xxx | 第三方错误(微信支付失败 / 退款失败 等) |

具体错误码字典随项目迭代维护在 `errors.toml`,集中管理。

### 7.3 鉴权

#### 7.3.1 小程序用户(openid 鉴权)

- 微信登录后,**前端将 `wx.login()` 返回的 `code` 提交到 user**。
- admin 调 `code2Session` 换取 `openid` + `session_key`。
- admin 签发 **短期 JWT**(15 min)+ **长期 Refresh Token**(30 天,存 Redis 允许撤销)。
- 后续请求 `Authorization: Bearer <jwt>`。

#### 7.3.2 PC 后台用户(JWT + 角色)

- 用户名 + 密码登录 → admin 签发 JWT(包含 `user_id`、`role_ids`、`customer_id`、`exp`)。
- JWT 过期 8 小时;Refresh Token 7 天。
- 每个请求 admin 中间件:
  1. 验签(HS256,密钥从环境变量 `JWT_SECRET`)
  2. 解析 `customer_id` 与 `role_ids`
  3. 注入请求扩展
  4. Axum 中间件按角色权限做菜单/数据/字段过滤

#### 7.3.3 设备接入(仅 device_id)

- 见 § 6.2。**无 JWT,无 TLS**。

### 7.4 限流

- **Caddy** 层:IP 维度 1000 req/s(简单粗暴)。
- **admin/billing** 服务层:基于 `tower::limit::RateLimitLayer`,按 user_id 维度 100 req/s。
- **支付回调**:不限制(签名校验通过即放行)。

### 7.5 分页

- `GET /api/v1/orders?page=1&page_size=20`
- 默认 `page=1`,`page_size=20`,最大 100。
- 响应包含 `total`、`page`、`page_size`、`data[]`。

### 7.6 OpenAPI 规范

- `utoipa` crate 从 Axum handler 提取 OpenAPI 3.0 文档。
- 服务启动时暴露 `GET /api/docs/openapi.json` + Swagger UI `/api/docs/swagger`。
- PC 后台与小程序前端通过 npm 包共享类型(由 `openapi-typescript` 生成)。

### 7.7 API 版本演进(单版本 + 强制升级)

**原则**:仅维护 `/api/v1/` 一个版本,**不维护多版本共存**。

| 场景 | 升级策略 |
| --- | --- |
| **新增字段**(如响应增加可选字段) | **前后端同时发版**(向后兼容,小程序与 PC 后台均可平滑升级) |
| **新增端点**(全新资源) | 同上,无需协调 |
| **破坏性变更**(字段重命名 / 删除 / 类型变更 / 路径变更) | **强制同时升级**:服务端代码改动 + 小程序发版 + PC 后台发版必须**同一发布窗口**完成 |

**强制升级流程**:

1. 服务端 PR 合并时,标记 `BREAKING CHANGE:` 前缀(Conventional Commits 规范)
2. CI 检查:检测到 `BREAKING CHANGE` 时,自动创建 GitHub Issue 关联前端两个仓,要求同步发版
3. 发布窗口:服务端与前端在 24h 内统一发版,期间可短暂出现不兼容 → **禁止**(必须协调完成后再发)

**不维护 /v2/ 原因**:

- 客户规模小(单客户单部署),小程序与 PC 后台均可控发版
- 引入多版本会增加 OpenAPI 文档维护成本(同步生成多份 TypeScript 类型)
- 强制升级流程简单清晰,运维负担可控

**何时需要演进到 /v2/**:

- 单客户规模达到 5 万 + 设备,前后端无法同步发版
- 出现多个长期共存的小程序版本(例如不同省份客户的定制版本)

## 九、安全

### 9.1 TLS 与证书

- **TLS 终止在 Caddy**(反代 `admin` 服务 + PC 后台静态资源)。
- 证书:Let's Encrypt 自动签发,`certbot` + `cron` 自动续期。
- 算法:TLS 1.3,加密套件 `TLS_AES_256_GCM_SHA384` / `TLS_CHACHA20_POLY1305_SHA256`。
- **HTTP Strict Transport Security**(HSTS):`max-age=63072000; includeSubDomains`。
- **数据库 / Redis 连接**:docker-compose 内部网络,**不加密**(性能 + 单客户场景)。

**证书续期失败兜底**:

- Caddy 通过 ACME HTTP-01 挑战自动从 Let's Encrypt 申请 + 续期证书(默认有效期 90 天)
- 续期失败 → Caddy 自身日志 + 触发 `alert_stream` 事件 `cert_renew_failed`
- **T-7 告警**:证书剩余有效期 ≤ 7 天时,通过 Webhook + 邮件双通道告警(由 admin 后台订阅配置)
- **不切备证书**(无 ZeroSSL 等备 CA 兜底),证书完全过期 = 整个对外服务中断,需运维立即手动处理
- 运维响应 SOP:`docs/runbook/cert-renew-failed.md`(运维订阅交付物)

### 9.2 密钥管理

- 所有密钥、API Key 通过**环境变量**注入容器(仅环境变量,**不读 config.yaml**)。
- 容器编排:Docker Compose `environment` / `env_file: .env`(`.env` 不进 Git)。
- 密钥轮换:每次部署可滚动更新环境变量;服务**热加载 SECRET 不支持**(需重启)。
- **JWT 密钥轮转策略**:MVP 阶段**不主动轮转**。仅在以下场景由运维手动更换:
  1. 疑似密钥泄露 / 安全事件
  2. 客户运维人员变动
  3. 等保三级审查 / 年度合规自查要求
  4. 客户合同约定的强制轮转周期(如部分客户合同要求半年 / 一年)
- 手动轮转流程:运维在维护窗口改 `JWT_SECRET` 环境变量 → `docker compose up -d` 重启服务 → 旧 JWT 立即失效,小程序需重新登录;新 JWT 用新密钥签发。**无灰度切换**(MVP 简化),轮转瞬间所有用户被强制登出。
- 二期可加"双密钥并存 24h"灰度机制(需重构 common-auth 支持多密钥)。

### 9.3 密码与敏感字段

- 用户密码:`argon2id`(rust 库 `argon2`)哈希,默认参数 `m=19456, t=2, p=1`。
- 敏感字段加密:数据库列加密(如手机号 / 身份证 / 银行卡),使用 MySQL `AES_ENCRYPT` 函数 + 静态密钥(从环境变量)。
  - 注意:静态密钥风险;**二期改为 KMS 派生**。

### 9.4 数据脱敏策略

**当前范围:MVP 阶段仅做存储加密,日志与接口不脱敏**。

| 层面 | 处理 | 备注 |
| --- | --- | --- |
| **数据库存储** | MySQL `AES_ENCRYPT` + 静态密钥(从环境变量) | § 9.3 已实现 |
| **应用日志(tracing)** | 不脱敏,记录完整字段 | MVP 简化 |
| **链路追踪(Tempo)** | 不脱敏,记录完整字段 | MVP 简化 |
| **查询接口响应** | 不脱敏,按角色权限过滤可见字段 | 由前端按权限隐藏 |

**取舍说明**:

- **优点**:实施简单,系统复杂度低,客户无需配置脱敏规则
- **风险**:运维/客服查日志时可见明文手机号 / 身份证;合规审查(等保三级)可能要求补充脱敏
- **触发补做条件**:
  1. 客户合规审查要求补充脱敏
  2. 发生日志泄露安全事件
  3. 启用 SaaS 多租户模式(同一实例服务多客户)

**二期计划**:tracing-rs 自定义 layer + 接口层按角色精确脱敏(手机号 `138****5678` / 身份证显示后 4 位)。本期不实施。

### 9.5 操作日志

- 所有 **admin** 写操作(`POST/PUT/PATCH/DELETE`)必须记录到 `audit_log` 表:
  - `user_id`、`customer_id`、`action`、`resource`、`before`、`after`、`ip`、`user_agent`、`trace_id`
- 保留期:**≥ 180 天**(等保三级)。
- 审计日志**不可修改**(只追加;数据库层面通过权限隔离)。

### 9.6 Webhook 安全

- Webhook 推送:**HMAC-SHA256** 签名(`X-Signature` header)。
- 签名密钥:每个订阅方独立(`webhook_subscription.secret`),生成时仅返回一次。
- 验证:接收方用密钥 + body 计算 HMAC,与 header 比对。

### 9.7 SQL 注入与 XSS

- SQL 注入:**全部走 sqlx 参数化查询**,禁止字符串拼接 SQL。
- XSS:PC 后台 React 自动转义;对外 HTML 输出(发票 PDF 模板)走白名单 escape。
- CSRF:PC 后台 axios + JWT header(无 cookie,免 CSRF)。
- CORS:Caddy 层配置 `Access-Control-Allow-Origin`,默认仅允许同源。

### 9.8 等保三级

- 按需求文档 § 3.4 / § 14.1 实施,具体技术控制:
  - 网络:仅暴露 80/443(对外)+ 1883/9100(设备网)
  - 主机:Docker 容器最小化基础镜像
  - 应用:输入校验、输出编码、错误处理不泄漏细节
  - 数据:加密传输(TLS) + 加密存储(敏感字段)
  - 身份:双因素(管理员登录待二期)
- 详细等保测评材料(技术控制矩阵)由第三方测评机构生成,本规格只覆盖技术实现。

## 十、部署

### 10.1 Docker Compose 一键启动

```yaml
# docker-compose.yml(简化示意)
version: '3.8'
services:
  mysql:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
    volumes:
      - mysql_data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s

  redis:
    image: redis:8-alpine
    command: redis-server --appendonly yes

  gateway:
    image: chargepilot/gateway:latest
    depends_on:
      mysql: { condition: service_healthy }
      redis: { condition: service_started }
    environment:
      DATABASE_URL: mysql://...
      REDIS_URL: redis://...
      JWT_SECRET: ${JWT_SECRET}
    ports:
      - "9100:9100"  # TCP
      - "1883:1883"  # MQTT

  user:
    image: chargepilot/user:latest
    depends_on: [mysql, redis]
    environment: { ... }
    ports:
      - "8081:8081"  # 内部 HTTP(由 Caddy 反代,小程序入口)

  admin:
    image: chargepilot/admin:latest
    depends_on: [mysql, redis, user]
    environment: { ... }
    ports:
      - "8082:8082"  # 内部 HTTP(由 Caddy 反代,PC 后台入口)

  billing:
    image: chargepilot/billing:latest
    depends_on: [mysql, redis]
    environment: { ... }

  worker:
    image: chargepilot/worker:latest
    depends_on: [mysql, redis, user, admin]
    environment: { ... }

  caddy:
    image: caddy:2.11-alpine
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - caddy_data:/data
      - caddy_config:/config
    ports:
      - "80:80"
      - "443:443"
```

### 10.2 资源基线(单客户部署)

| 服务 | CPU | 内存 | 备注 |
| --- | --- | --- | --- |
| mysql | 2 核 | 4 GB | innodb_buffer_pool_size = 2 GB;5 schema 共享 |
| redis | 1 核 | 1 GB | maxmemory 512 MB,allkeys-lru |
| gateway | 2 核 | 1 GB | Tokio worker 线程数 = CPU 数 |
| **user** | **2 核** | **1 GB** | **高 RPS,优先扩容** |
| **admin** | **1 核** | **512 MB** | 低 RPS,可缩减 |
| billing | 1 核 | 512 MB | 计算密集度低 |
| worker | 1 核 | 512 MB | 后台任务 |
| caddy | 1 核 | 256 MB | 静态资源代理 + TLS 终止 |
| **合计** | **11 核** | **8.75 GB** | 适用 8 核 / 16 GB 起跳的客户服务器 |

> **扩容建议**:充电峰值期间(节假日晚高峰)只需 `docker compose up --scale user=3`;后台流量低,可维持 `admin=1`。

### 10.3 部署流程

1. 客户准备云服务器(最低 4 核 / 8 GB / 100 GB SSD,公网带宽 ≥ 10 Mbps)。
2. 客户安装 Docker + Docker Compose。
3. 拷贝 `docker-compose.yml` + `.env.example` + `Caddyfile` 到服务器。
4. 填充 `.env`(数据库密码、JWT 密钥、微信支付配置)。
5. `docker compose up -d`,服务自动:
   - MySQL 启动 + 初始化 schema
   - 各服务启动时执行 `sqlx::migrate!()` 应用迁移
   - **Caddy 自动从 Let's Encrypt 申请并续期证书**(无需手动配置证书)
6. **首次部署**需手动:
   - 通过 PC 后台"白标配置"上传 Logo / 主题色
   - 配置微信支付商户号 / 汇付天下密钥
   - 配置首条公告

#### Caddyfile 示例

```caddyfile
# 单域名示例:api.example.com 同时托管 PC 后台 + 提供小程序 API
api.example.com {
    # 自动 HTTPS(Caddy 内置 Let's Encrypt)
    encode zstd gzip

    # 根路径:返回空 404,不泄露任何路径信息(防侦察)
    @root path /
    respond @root 404

    # 小程序 API(openid JWT 鉴权)
    reverse_proxy /api/v1/user/* http://user:8081

    # 微信支付回调(无需鉴权,验签走微信签名)
    reverse_proxy /api/v1/public/* http://user:8081

    # PC 后台 API(角色 JWT 鉴权)
    reverse_proxy /api/v1/admin/* http://admin:8082

    # PC 后台静态资源 + SPA 入口(React)
    reverse_proxy /admin http://admin:8082    # SPA 入口(/admin 单独匹配)
    reverse_proxy /admin/* http://admin:8082   # SPA 客户端路由(/admin/devices 等)

    # 健康检查(任一服务)
    reverse_proxy /health http://user:8081
}
```

**安全原则**:
- **未匹配路径返回空 404**,**不泄露任何路径信息**(防侦察攻击 / 信息泄露)
- 路径映射在内部文档维护,**不对外暴露**
- PC 后台入口仅通过**事前告知**给客户运维,不通过任何自动发现机制暴露

Caddy **不代理 TCP 9100 / MQTT 1883**——这两端口由 gateway 服务直接对外监听,Caddyfile 无需配置。

### 10.4 升级

- **每客户独立升级**(需求文档 § 13.2)。
- 流程:出新版本 Docker Image → 客户服务器 `docker compose pull` + `docker compose up -d`。
- **滚动升级**:gateway / admin / billing 可逐个重启(无状态);worker 重启不影响主流程。
- 数据库迁移:服务启动时自动执行;**严禁**运行中的服务执行迁移后立即切流量(迁移完成后再启动新版本)。

### 10.5 监控与告警

- **本系统不内置业务监控大盘**,由客户运维侧决定监控栈(可用 Prometheus + Grafana)。
- 自暴露:`/metrics` 端点(详见 § 8.2)+ `/health`、`/ready`。
- 自身告警:`alert.dlq` 中流转事件由 worker 周期任务扫描,通过 Webhook + 邮件上报给客户运维。

## 十二、开发流程

### 12.1 分支策略

**GitHub Flow**:
- `main` 分支永远可发布。
- 新功能/修复:`feature/{name}` 或 `fix/{name}` 分支 → PR → CI 通过 + Code Review → squash merge 到 main。
- 紧急修复:`hotfix/{name}` 分支 → 直接 PR 到 main → 立即发版。
- **不**长期保留开发分支(避免 merge 地狱)。

### 12.2 Commit 规范

- Conventional Commits:`feat:` / `fix:` / `refactor:` / `test:` / `docs:` / `chore:`。
- 一个 commit 一件事;粒度小;commit message 中文 / 英文皆可。
- 禁止 `--force` push 到 `main`。

### 12.3 代码规范

- Rust:`rustfmt` + `clippy -D warnings`(CI 强制)。
- TypeScript / React:`eslint` + `prettier`。
- 命名:snake_case(Rust) / camelCase(TS)。
- 注释:业务复杂逻辑必须有中文注释;公共 API 必须有 rustdoc / TSDoc。
- 函数长度:< 80 行(超过需重构或拆分)。
- 模块导出:每个 crate 仅 `pub` 必要的项。

### 12.4 Code Review

- **每个 PR 必须 ≥ 1 人 review**(AI 辅助开发时,AI 生成的代码仍需人工 review)。
- 关注:业务正确性 / 安全 / 性能 / 可测试性 / 命名清晰度。
- 不在 review 中夹带未相关修改(避免 PR 范围蔓延)。

> **本节选型依据**:基于 2026-09 公开信息查核。Cloudflare Tunnel(cloudflared 2026.9.1,2026-09-11 发布,Apache-2.0)在免费 + 自定义域名 + 无流量限制三项上仍领先于 ngrok / Tailscale Funnel / frp 等同类方案。

#### 12.5.1 本地服务启动

#### 12.5.2 小程序调试接入(Cloudflare Tunnel)

微信小程序要求 HTTPS + 域名白名单 + ICP 备案。直接用 `http://192.168.x.x:8081` 不可行。**采用 Cloudflare Tunnel 公网穿透**(免费,无需自有 VPS / 公网 IP)。

**Cloudflare Tunnel 工作原理**:

```
┌──────────────┐  启动  ┌──────────────┐  自动     ┌──────────────────┐
│ 开发者本地    │ ───────▶│ cloudflared  │ ────────▶│ Cloudflare Edge  │
│              │         │ (客户端)      │ 加密隧道  │ 自动 HTTPS + 域名  │
│ user:8081    │ ◀───────│              │ ◀────────│ *.trycloudflare.com│
└──────────────┘  请求   └──────────────┘  响应    └──────────────────┘
                                                       ▲
                          小程序(扫码/支付) ──HTTPS──┘
```

**配置步骤**:

1. **安装 cloudflared**(开发机):
   ```bash
   # macOS
   brew install cloudflared
   # Linux
   wget https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64.deb
   sudo dpkg -i cloudflared-linux-amd64.deb
   # Windows
   winget install Cloudflare.cloudflared
   ```

2. **启动 user 服务隧道**(快速试用,Quick Tunnel,无需账号):
   ```bash
   cloudflared tunnel --url http://localhost:8081
   # 输出示例: https://random-word-1234.trycloudflare.com
   ```

3. **配置小程序**:将 API base URL 设置为该临时域名:
   ```typescript
   // miniprogram/src/config.ts
   export const API_BASE = 'https://random-word-1234.trycloudflare.com';
   ```

4. **微信开发者工具**:
   - 打开项目,详情 → 不校验合法域名(勾选)
   - 真机调试:扫码后,小程序访问 `https://xxx.trycloudflare.com/api/v1/user/...`
   - Cloudflare Edge 自动 HTTPS + 自动转发到本地 user:8081

> **Quick Tunnel 限制**(开发者须知):
> - 域名**每次重启随机变化**,需同步更新小程序 `API_BASE`
> - 不支持 SSE(本系统充电中轮询走普通 HTTP,不受影响)
> - 单月 1 GB 流量 + 20,000 请求,仅作短期调试
> - `*.trycloudflare.com` **无法**加入微信小程序"request 合法域名"白名单(必须自有已备案域名);真机调试需勾选"不校验合法域名",仅本机生效
>
> **长期开发场景**(固定域名 + 团队共享 + 微信支付回调可加入白名单)→ 改用下面的命名隧道。

**命名隧道配置**(需 Cloudflare 账号 + 域名已托管至 Cloudflare DNS):

```bash
# 登录 Cloudflare 账号
cloudflared login

# 创建命名隧道
cloudflared tunnel create chargepilot-dev

# 配置 DNS 路由(dev.chargepilot.com → 本地)
cloudflared tunnel route dns chargepilot-dev dev.chargepilot.com

# 创建 config.yml
cat > ~/.cloudflared/config.yml <<EOF
tunnel: chargepilot-dev
credentials-file: /home/user/.cloudflared/<TUNNEL_ID>.json
ingress:
  - hostname: dev.chargepilot.com
    service: http://localhost:8081
  - hostname: dev-admin.chargepilot.com
    service: http://localhost:8082
  - service: http_status:404
EOF

# 后台运行
cloudflared tunnel run chargepilot-dev
```

**配合微信开发者工具**:

| 场景 | 配置 |
| --- | --- |
| 仅 PC 模拟器 | 微信开发者工具详情 → 勾选"不校验合法域名" + "不校验 TLS 版本" |
| 真机调试 | 同上 + 扫码预览,需确保手机能访问外网 |
| 生产环境 | 域名 ICP 备案 + 加入小程序后台"request 合法域名" |

**仅 PC 后台调试**(无需小程序):直接 `https://admin.localhost:8082` 用浏览器,配合 hosts 解析或本地 Caddy。

#### 12.5.3 frp 备选方案(自有 VPS)

**对比**(2026-09 查核):

| 维度 | Cloudflare Tunnel(Named) | frp | ngrok 免费版 | Tailscale Funnel |
| --- | --- | --- | --- | --- |
| 月流量限制 | 无公开上限 | 自定(取决于 VPS) | 1 GB | 未公开(存在非正式上限) |
| 固定自定义域名 | ✅ 免费 | ✅ 自备域名 | ❌ 仅随机域名(付费 ≥ $8/月) | ❌ 仅 `*.ts.net`(无法接入微信白名单) |
| VPS / 公网 IP | ❌ 不需要 | ✅ 需要 | ❌ 不需要 | ❌ 不需要 |
| 自动 HTTPS | ✅ Cloudflare Edge | ❌ 需自签 + Let's Encrypt | ✅ | ✅ |
| 国内访问速度 | 受 Cloudflare 节点影响(海外免费节点常见 200ms+) | 取决于 VPS 位置 | 受 ngrok 中转 | 受 Tailscale 中继影响 |
| 客户端开源 | ✅ Apache-2.0 | ✅ Apache-2.0 | ❌ 闭源 | ✅ BSD |
| 配置复杂度 | 低 | 中(VPS + server + 客户端) | 低 | 低(需先加入 tailnet) |
| 适用 | 个人 / 小团队 / 长期开发 | 自有合规 VPS 的企业 | 仅短期 Webhook 测试 | tailnet 成员间快速分享 |

**结论**:本系统默认采用 Cloudflare Tunnel(免费 + 固定域名 + 真机可调);如客户合规要求拒绝使用第三方 CDN,或不便托管域名至 Cloudflare,改用 frp 自建。

## 十四、性能 SLO

### 14.1 延迟目标

| 接口 | P50 | P95 | P99 |
| --- | --- | --- | --- |
| 小程序 API(扫码启动 / 订单查询) | ≤ 100ms | ≤ 300ms | ≤ 500ms |
| PC 后台 API(列表 / 详情) | ≤ 200ms | ≤ 500ms | ≤ 800ms |
| 微信支付下单 | ≤ 300ms | ≤ 800ms | ≤ 1.5s(含微信 API) |
| 计费引擎单订单结算 | ≤ 50ms | ≤ 100ms | ≤ 200ms |
| 分账计算(N=8) | ≤ 20ms | ≤ 50ms | ≤ 100ms |
| Redis Stream 端到端延迟 | ≤ 200ms | ≤ 1s | ≤ 5s |

### 14.2 吞吐目标

- **单客户部署**:**5000 设备并发**(TCP/MQTT 混合)。
- API:**1000 RPS 稳态**(单 user 实例);admin 预期 ≤ 100 RPS。
- 消息总线:**10000 events/s**(单 Redis Stream)。
- 数据库:**5000 QPS**(单 MySQL 8.4 4 核 4 GB 配置)。

### 14.3 可用性

- 业务可用性(SLA):**≥ 99.5%**(单机部署可达 99.9%)。
- 数据库恢复:RTO ≤ 4 小时,RPO ≤ 1 小时(备份 + binlog)。
- 升级窗口:每月 1 次,每次 ≤ 30 分钟。

### 14.4 数据库备份与灾备(mysqldump 简化方案)

**MVP 简化方案**:`mysqldump` 逻辑备份 + 定时 cron 异地 scp + 每半年一次演练。

**备份策略**:

| 备份类型 | 工具 | 频率 | 保留 | 存放 |
| --- | --- | --- | --- | --- |
| 全量逻辑备份 | `mysqldump --single-transaction --routines --triggers` | 每日 02:00(cron) | 本机 7 天 + 异地 30 天 | 本机 `/var/backup/mysql/` + 异地 OSS / scp 到备用机 |
| binlog 增量 | MySQL binlog(`ROW` 格式)+ `mysqlbinlog` | 实时(开启 `log_bin`) | 本机 7 天 | 本机 MySQL data dir |
| 配置备份 | `mysqld --print-defaults` + 配置文件 tar | 每周一次 | 异地 30 天 | 异地 OSS |

**RPO 实际值**:

- `mysqldump` 全量每日一次 + binlog 实时 → RPO **最坏 ≤ 1 天**(`mysqldump` 间隔期间只能恢复 binlog)
- binlog 启用后,真实 RPO 由 binlog flush 频率决定 → **实际可达分钟级**
- § 14.3 承诺"RPO ≤ 1h"在 **binlog 持续可用**前提下成立;若 binlog 损坏或丢失,RPO 退回到最近 `mysqldump` 时间点(最坏 24h)

**演练**(每半年一次):

- 运维在临时实例(可借用测试服务器 / 云上临时 ECS)执行全量恢复演练
- 步骤:`mysqldump` 文件导入 → binlog 重放 → 启动服务 → 跑核心冒烟用例 → 记录 RTO 实测值
- 演练报告写入 `docs/runbook/backup-drill-YYYY-MM.md`
- 演练发现的问题(如恢复时间超出 RTO、binlog 损坏) → 列入下个迭代修复

**异地备份方式**(二选一):

1. **OSS / S3**:运维订阅里提供 `rclone` 或 `aws s3 cp` 脚本,定时同步到客户自购的 OSS 桶
2. **备用机 scp**:客户有第二台服务器时,定时 scp 到备用机;备用机仅在主服务器宕机时启用

**不启用实时主从 / binlog 实时同步到异地实例**:

- 单客户单部署场景下,运维成本远高于收益
- 触发启用条件:客户合同要求 RPO ≤ 5 min + 接受运维复杂度上升

**二期升级路径**(若客户需要):

- 引入 Percona XtraBackup 物理热备(更快恢复)
- 引入 binlog 实时同步到异地只读实例(几乎 RPO = 0)
- 启用异地灾备实例自动切换

微信原生小程序**不接入** Cargo / pnpm workspace:

- 小程序的 npm 依赖通过微信开发者工具"构建 npm"生成 `miniprogram_npm/`
- 跨端代码复用:**禁止**小程序直接引用 web/ 或 services/ 代码;若需共用类型,通过手工同步或独立 `miniprogram/types/` 维护

### 15.5 跨技术栈共享资产

| 资产 | 来源 | 消费方 | 同步方式 |
| --- | --- | --- | --- |
| OpenAPI 规范 | services 启动时暴露 `/api/docs/openapi.json` | web/apps/admin + web/packages/api-types | `tools/gen-api-types.ts` CI 触发生成 |
| 数据模型结构体 | crates/common-types | services/* + 未来其他 Rust 服务 | workspace 内部 |
| 业务常量(分账上限、扣减顺序) | crates/common-types | services/* | workspace 内部 |
| 协议文档 | docs/技术规格.md | 全员 | Git 同步 |

### 15.6 共享 crate(`crates/`) 设计原则

- **依赖方向**:`services → crates`(services 依赖 crates,反之不可)
- **零业务逻辑**:`common-*` 只放**基础设施**(鉴权、DB、配置、可观测性),不涉及充电/订单/分账业务
- **业务类型**:`common-types` 放跨服务共享的**纯数据结构**(如 `OrderSummary`、`SplitParty`),不依赖具体业务规则
- **版本管理**:跟随 workspace 版本,每次 release 整体升级;不单独发版

### 15.7 模块边界与重构规则

| 行为 | 边界处理 |
| --- | --- |
| 共享代码应放入 `crates/common-*` 还是复制? | **优先放入 crates**(workspace 共享零成本);若代码涉及具体业务(如计费规则),放入 `common-types`;若仅为单一服务用,**留在该服务内**,禁止跨服务引用 |
| 服务间需要共享类型如何做? | 定义在 `crates/common-types`,服务引用;**禁止**服务间直接 `use` 对方代码 |
| 前端复用类型? | 通过 `tools/gen-api-types.ts` 从 OpenAPI 自动生成到 `web/packages/api-types`,前端通过 `import type` 引用 |
| 文档与代码不同步? | 文档与代码在同一 PR 提交,CI 检查关键变更(如新 API 端点必须有 OpenAPI 更新) |

### 15.8 国际化策略(架构预留 + 本期只译中文)

**MVP 阶段**:仅中文,**架构层预留 i18n 框架**,但不投入翻译成本。

**前端(PC 后台 + 小程序)**:

- **PC 后台**:集成 `react-i18next`(或类似 i18n 库),所有用户可见文案走 `t('xxx')` 包裹;本期 `locales/zh-CN.json` 全量翻译,`locales/en-US.json` 仅占位空对象
- **小程序**:集成微信官方 `wx.T()` 或自封装轻量 t 函数,所有文案走 `t('xxx')`;本期 `zh-CN.js` 全量翻译,`en-US.js` 仅占位空对象

**后端**:

- 错误码文案(`errors.toml` 中的 `message` 字段)按 `locale_code` 索引;本期只填 `zh-CN`
- API 响应中的可见文案(如有)同样按 locale 索引
- 客户端通过 `Accept-Language` header 或查询参数 `?lang=zh-CN` 协商

**不做的**:

- 不集成付费翻译服务
- 不做完整文案翻译记忆库(TMS)
- 不做 RTL / 多语种排版适配

**二期补做条件**:

1. 出现明确海外客户(港 / 澳 / 台 / 海外华人)
2. 客户合同要求英文版本
3. 业务向东南亚 / 欧洲扩张

**翻译协作流程**(二期):

- 新增文案 → 由产品经理 / 客户运营在 `locales/` 提交 PR
- CI 检查:新增 `t('xxx')` 键必须在 `zh-CN.json` 存在,否则 PR 校验失败
