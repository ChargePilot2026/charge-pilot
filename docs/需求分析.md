## 一、产品定位与商业模式

### 1.1 产品定位

**本系统是一款独立部署形态的二轮车充电运营管理软件**。每一套系统对应**一个付费客户**（典型为物业公司、运营商、地方政府或国资平台），客户自行采购云服务器与数据库，由我们（或合作伙伴）完成一次性部署。

- **不是**面向终端用户的 SaaS。
- **不是**自营充电桩业务的工具。
- **不是**多客户共享一套平台的"多租户 SaaS"。
- **是**面向单客户的"独立部署 + 运维订阅"软件产品。
- 销售渠道可以是充电桩硬件厂商、政府集成商或直接销售；硬件厂本身**不是**本系统的客户。
- 与硬件解耦:通过**协议适配网关**,支持多家硬件厂协议(每个客户按需启用对应适配器;具体实现由《技术规格文档》定义)。

### 1.2 商业模式

| 维度 | 决策 |
| --- | --- |
| 交付形态 | 独立部署 / 单客户一套 |
| 收费模式 | 基础买断(源码 + 实施)+ 运维订阅(远程支持 + 版本升级 + 二开支持) |
| 客户关系 | 单客户一套部署:每个付费方独立采购云服务器、数据库,独立部署一套系统 |
| 客户类型 | 不区分(物业集团/运营商/地方国资/政府城投/集成商一套配置覆盖) |
| 升级交付 | 每个客户独立升级,不做集中升级工具 |
| 参与方载体 | 用户 = 小程序;其他参与方 = 同一 PC 后台 + 客户客服团队微信 |
| 支付渠道 | 用户侧仅显示"微信支付";后端可选**微信直连**(商户号直连)或**汇付天下**(三方聚合,最终走微信通道) |
| 用户身份 | 微信 `openid` 隐式身份,无任何额外认证 |
| 用户体系 | 余额 + 月卡/年卡 + 优惠券 + 找桩地图 + 个人中心 + 发票申请 + 在线客服 |
| 退款方式 | 原路自动返回微信支付,实时到账 |
| API 开放 | 闭源 + 查询类 API + 告警 Webhook 推送 |
| AI 预警 | 一期不做,仅阈值告警 |

### 1.3 目标客户与生态位

**真正客户**:物业集团、运营商、地方国资平台、政府监管 / 城投公司、产业链集成商(均使用同一套配置,不做类型差异化)。

## 二、市场背景（精简）

只保留与产品决策强相关的市场信号，详细数据放附录 A。

- **保有量基础**：中国电动两轮车社会保有量约 3.5–4.2 亿辆。
- **火灾倒逼**：2023 年全国电动自行车火灾 2.1 万起，80% 发生在充电阶段；强制国标 GB 47371—2026（2027.4.1 实施）锁死安全底线，硬件厂必须配套合规软件。
- **市场参与者结构**（避免点名）：
  - **充电硬件厂**：重资产硬件生产，部分自研配套软件。
  - **第三方 SaaS 平台**：为运营商/物业提供软件服务，跨硬件兼容。
  - **换电柜运营商**：服务 B 端骑手，独立赛道，本系统不进入。
  - **政府/物业监管平台**：地方"锂康码 / 一网统管"等监管系统，需要接入而非竞争。
- **本系统的位置**：在"硬件厂配套"细分位置，区别于通用 SaaS（强调跨硬件兼容）和自研软件（强调成本可控 + 可定制）。

### 3.3 价格政策

国家发改委、市场监管总局 2024 年 6 月《发改办价格〔2024〕537 号》明确：

- 充电费用实行**价费分离**（电费 + 服务费分别标示、分别计价）。
- 居民住宅小区按**居民合表电价**（0.55–0.62 元/度）计收。
- 自 **2025.1.1** 起强制实现"充电电量单独计量"。

**对系统的硬约束**：系统必须在计费逻辑中明确区分"电费"与"服务费"，账单、出账、分账、对账均按两条线分别处理。

### 3.4 合规等级

本系统按 **等保三级** 要求进行安全设计与实施。

> **载体规则**:用户侧**仅小程序**;运营/财务/巡检/管理员角色使用**同一个 PC 后台**;**客服坐席通过微信原生客服会话**(对应客户配置的客服团队微信)直接接待小程序端用户咨询。
>
> **关于合伙人 / 区域代理**:系统**不内置**该角色。客户组织外的渠道方(如区域代理、合伙人)由客户在系统外自行管理,业绩分成与佣金发放通过 Excel 等线下方式处理。

### 4.2 单客户单部署模型

**核心约束**：一套系统 = 一个付费客户 = 一套独立部署。

- 每个客户自行采购云服务器、数据库(选型见《技术规格文档》)、域名、备案。
- 每个客户拿到一套独立部署包、独立的数据库实例、独立的密钥与配置。
- 客户之间数据**完全物理隔离**，互不可见，无任何共享。
- 同一硬件厂卖出的不同客户 = 多个独立部署，**不共用平台**。
- 升级与运维：每套独立升级；运维订阅针对每套独立续费。

## 五、核心功能模块

### 5.1 设备接入与充电闭环

- 协议适配网关,**优先支持 TCP 裸连与 MQTT 私有协议**(详见第六章)。
- 兼容 GB 47371 七重防护遥测字段。
- 充电启动方式:**仅扫码即充**(不做预约充电、不做定时充电)。
- 充电过程完整闭环:扫码 → 启动 → 计费 → 结束 → 推送账单。
- 状态实时追踪:空闲 / 充电中 / 故障 / 离线 / 充满。
- 设备来源标识 `hardware_vendor_id`(协议级属性,**仅用于协议兼容与故障归因,不是租户隔离维度**)。

### 5.2 用户账户与计费

- **用户身份**:基于微信小程序 `openid` 隐式身份,**不要求任何额外认证**(无实名、无强制手机号绑定)。
- **手机号绑定(可选)**:用户可在个人中心**自愿选择**绑定手机号;绑定后由客户配置奖励:
  - 赠送余额(具体金额由客户配置)
  - 赠送优惠券(具体类型/面额由客户配置)
  - 客户可二选一,也可同时配置两种奖励(用户绑定后任选其一)。
- **账户余额**:
  - 用户通过微信支付在线充值(可选金额档位由客户在 PC 后台配置)。
  - 客户线下代售:由客户(物业)在 PC 后台为指定用户充值/开通。
  - 客户可配置余额有效期(默认长期有效)。
  - 充值优惠:支持**充值赠送余额**(如充 100 送 5),规则由客户配置。
- **会员卡**:支持月卡 / 年卡预付费扣减,客户在后台配置卡种、价格与有效期。
- **优惠券**:支持**四种发放机制**(并存):
  - 客户手动发放(指定用户)。
  - 用户主动领取(配置领取活动)。
  - 自动规则触发:**首充优惠 / 邀请有奖 / 满减满返 / 节日活动**(全部支持)。
  - 邀请有奖:**邀请双方均获得奖励**,分享路径支持微信好友卡片 + 生成专属海报。
- **扣减顺序**:**会员卡 → 优惠券 → 余额 → 微信支付**(逐级扣减,扣完即止)。
- **服务协议与隐私声明**:系统提供默认模板,客户可在后台调整;**首次扫码启动前用户需勾选同意**。
- **支付渠道**:用户侧**仅显示"微信支付"**;后端可选**微信直连**(商户号直连)或**汇付天下**(三方聚合,最终走微信通道),由客户在 PC 后台配置。

### 5.3 退款与异常订单

- **退款通道**:**原路返回微信支付**,实时到账。
- **自动退款触发**(以下情形均触发原路自动退款):
  - 充电失败(详见判定规则)。
  - 充电超时(>10h,GB 47371 推荐上限)。
  - 用户在启动后 **60 秒内**主动取消。
- **按已充结算后退款**:用户提前拔出充电插头(>60 秒),按已充电量结算后退还剩余。
- **计量异常**:不自动退款,需客户财务人工审核。
- **退款到账后**:**通过小程序消息主动通知用户**。
- **余额不足**:**提前结束充电**,按已充电量结算后退还余额。

### 5.4 多方分账与财务管理

- **多方按比例分账**(详见第八章):**N ≤ 8**,每方比例可独立配置(0–100%,合计 100%)。
- **可选分账模式**:
  - **模式 A(默认)**:电费 + 服务费均按比例分账给参与方。
  - **模式 B(电费不分账)**:仅服务费按比例分账,电费归电网公司或物业专户,**不进分账池**;**系统仅做记账与对账,不接入电网/物业缴费接口**。
  - 模式 A/B 在客户维度可独立配置。
- 价费分离:每一笔订单按"电费"与"服务费"两条线分别入账。
- 账单与对账:按客户、按周期生成账单。
- 提现管理:客户向下游角色发起提现申请,财务人员审核打款。

### 5.5 阈值告警 + 白标配置 + 角色权限

- **七重防护遥测告警**:阈值越界即触发告警,推送到 PC 后台 + 小程序 + Webhook。
- **告警分级**:低(提示)/ 中(推送)/ 高(自动断电)。
- **Webhook 推送**:外部系统订阅告警事件。
- **查询 API**:设备状态、订单、告警、电量等只读接口(设备控制 API 一期不开放)。
- **白标配置中心**(按客户维度):
  - 主题色 / Logo / 应用名称
  - 每个客户独立**小程序**;**公众号仅作品牌露出,不接入业务功能**(不提供菜单/推送/客服接入)
  - 域名 / 二维码生成
  - 计费规则模板、充值档位、会员卡模板
  - 分账模板(参与方、比例、模式)
  - 优惠券、公告、代售录入后台
- **角色权限**:功能级 + 数据级 + 字段级(含手机号/身份证号等敏感字段脱敏)。
- **不提供工单系统**:告警由客户巡检/客服人员在 PC 后台直接处理;处理记录留痕可追溯。

### 5.6 远程运维(OTA)

## 七、设备接入与充电闭环

### 7.1 协议现状与决策

**关键判断**:二轮车充电桩在国内主流采用**私有协议**,由各家硬件厂自定义。

- **TCP 裸连**:设备主动建连或被动监听,私有报文格式。
- **MQTT 私有协议**:基于标准 MQTT 3.1.1/5.0,但 Topic 与 Payload 为厂商自定义。
- 少量厂商使用 HTTP/HTTPS 轮询。
- 早期 Modbus 设备(已逐步退出)。

**结论**:系统协议层必须以 **TCP 适配器 + MQTT 适配器**为主,HTTP 适配器可选。

### 7.2 设备注册与认证

- **设备唯一标识**:每台桩有唯一 `device_id`(由客户管理后台在首次注册时生成或导入),作为系统在协议层与业务层的唯一索引。
- **首次注册**:客户管理后台扫码 / 录入设备序列号 → 平台生成或绑定 device_id → 推送配置到桩端。
- **设备来源标识**:每台设备记录 `hardware_vendor_id`(协议级属性),仅用于协议兼容与故障归因,**不是租户隔离维度**。
- **在线升级**:协议层支持 OTA 推送,包括配置变更(费率、定时策略)**和桩端主控固件升级**(详见 § 5.5)。

### 7.3 协议适配器插件化要求

**系统需支持的协议版本** = 市场上主流硬件厂的私有协议。每家硬件厂的协议 = 一个适配器实现。这些适配器是**协议兼容性维度**的概念,**不是多租户维度**——一套客户部署只启用该客户实际使用的硬件厂适配器。

每家硬件厂对应一个独立适配器,适配器内部按各家私有协议实现(具体实现留给《技术规格文档》)。系统按客户维度启用适配器组合——客户 A 启用硬件厂 X + Y,客户 B 启用硬件厂 Z,完全独立。

### 7.4 七重防护遥测字段

设备必须上报的核心字段(一期强校验,二期可放宽):

| 字段名 | 含义 | 上报频率 |
| --- | --- | --- |
| `voltage_v` | 充电电压(伏) | 每秒 |
| `current_a` | 充电电流(安) | 每秒 |
| `temperature_c` | 桩端温度(℃) | 每 5 秒 |
| `battery_soc` | 电池剩余电量百分比 | 充电中每 30 秒 |
| `relay_status` | 继电器状态(吸合/断开) | 实时 |
| `fault_code` | 故障码 | 实时 |
| `charge_state` | 充电状态(空闲/充电中/充满/故障) | 实时 |
| `meter_kwh` | 累计充电电量(度) | 每 30 秒 |
| `slot_id` | 充电插口编号 | 充电中 |

> 字段名称、取值范围、编码规范的具体格式由《技术规格文档》定义;本表仅描述业务含义与上报频率要求。

## 八、计费引擎与价费分离

### 8.1 计费模型

**多维度计费策略**:

- 按时长(分钟)
- 按电量(kWh)
- 按功率分档(**默认档位 ≤150W / 150-285W / 285-400W / 400-600W,客户可在后台调整档位边界**)
- 按峰谷分时电价(高峰/平段/低谷)
- 按会员卡(月卡 / 年卡;详见 § 5.2)

### 8.2 价费分离（核心）

订单在系统中必须按两条线分别入账：

- **电费**：按充电电量 × 居民合表电价计算。
- **服务费**：按充电电量 × 单价 或 时长 × 单价 计算。
- **禁止合并后二次拆分**。价费分离是产品逻辑层的硬约束。
- 单次充电结束后，平台通过小程序向用户推送**充电时长、充电电量、电费金额、服务费金额、总金额**。

### 8.3 分时电价配置

时段模板（示例）：
- 高峰：08:00-11:00, 18:00-21:00
- 平段：06:00-08:00, 11:00-18:00, 21:00-23:00
- 低谷：23:00-次日 06:00

不同时段 × 不同设备类型 × 不同用户等级的差异化定价模板可由客户在 PC 后台配置。

### 8.4 异常订单处理

| 场景 | 处理 |
| --- | --- |
| **充电失败**(以下任一情形) | **原路自动退款**(微信支付)+ 小程序消息通知 + 触发告警 |
| - 设备上报启动失败 / 通信超时 | (归类为"充电失败") |
| - 用户启动后 60 秒内主动取消 | (归类为"充电失败") |
| - 启动后 30 秒内未进入充电状态 | (归类为"充电失败") |
| - 安全告警导致启动中断 | (归类为"充电失败") |
| **充电超时**(>10h,GB 47371 合规) | 自动断电 + **原路自动退款** + 推送告警 |
| **用户提前拔出充电插头**(启动后 > 60 秒) | 按已充电量结算 + **退还剩余金额**原路返回 |
| **余额不足**(充电中) | 提前结束充电 + 按已充电量结算 + **退还余额**原路返回 |
| **计量异常** | **不自动退款**,客户财务人工审核 |

## 九、多方分账与财务管理（核心章节）

### 9.1 多方按比例分账模型

**支持多方分账,上限 N ≤ 8**(N ≥ 2),每方比例可独立配置,**比例合计必须 = 100%**。

示例(**模式 A:电费 + 服务费均分账**):

```
总服务费  1.00 元/度，电费按客户与电网约定另行结算
平台     0.10 元/度（10%）
硬件厂   0.20 元/度（20%）
平台运营 0.10 元/度（10%）
物业 A   0.30 元/度（30%）
物业 B   0.30 元/度（30%）

合计 = 1.00 元/度（100%）
```

示例（**模式 B：仅服务费分账，电费不分账**）：

```
服务费  1.00 元/度
平台     0.10 元/度（10%）
物业     0.90 元/度（90%）

电费  0.55 元/度（居民合表电价）
电费不进分账池，由电网公司或物业专户全额上缴/留存
```

### 9.2 两种分账模式

| 模式 | 电费 | 服务费 | 适用场景 |
| --- | --- | --- | --- |
| **模式 A（默认）** | 进入分账池，按比例分配给参与方 | 进入分账池，按比例分配给参与方 | 自营充电场景、客户想拿走电费差价 |
| **模式 B（电费不分账）** | **不进分账池**，全额归电网公司或物业专户 | 进入分账池，按比例分配 | 物业仅提供场地、运营由平台 / 物业承担分账 |

- 同一套部署可在客户维度**全局配置**模式 A 或模式 B。
- 模式 B 下,电费**不进分账池**——系统仅记录电费流水,**不接入电网公司或物业的缴费接口**,电费资金流由客户/物业与电网公司自行结算(按居民合表电价上缴,或按物业代收约定全额留物业账户)。

### 9.3 参与方配置

每个分账参与方需要配置：

| 字段 | 含义 |
| --- | --- |
| `party_id` | 参与方唯一标识 |
| `party_name` | 显示名称（如"XX 物业 A 项目"） |
| `party_type` | 平台 / 客户 / 子场地 等(系统不内置合伙人/区域代理类型) |
| `share_ratio` | 比例（0–100%，小数点后两位） |
| `bank_account` | 分账到账的对公账户 |
| `settlement_cycle` | 日清 / 周结 / 月结 |
| `effective_range` | 生效的设备范围 / 项目范围 |

### 9.4 支付渠道

**用户侧**:小程序**仅显示"微信支付"**一个入口,不做任何渠道选择提示。

**后端可选通道**(由客户在 PC 后台配置选用):

| 后端通道 | 适用 | 备注 |
| --- | --- | --- |
| **微信直连(商户号直连)** | 客户已有微信支付商户号 | 直连模式,**不走服务商**,分账与到账时效更可控 |
| **汇付天下(三方聚合)** | 客户无自有微信商户号 | 三方聚合通道,最终仍走微信支付,适合快速接入场景 |

支付流程:

```
用户扫码 → 小程序展示"微信支付"入口 →
  调起微信支付 → 支付成功 → 资金进入客户选定的后端通道 →
  按分账模板自动触发分账 → 各参与方对公账户
```

> **决策说明**:用户侧只看到"微信支付",不暴露后端通道差异;后端通道是客户级的运维决策,与终端用户体验无关。

**红线**:平台**不自持资金池**,不触碰用户充电本金;分账资金经持牌支付机构备付金专户自动划拨。

### 9.5 账单与对账

- 按客户、按周期生成账单（默认按物业方）。
- 对账周期：日清 / 周结 / 月结（由客户配置）。
- 导出格式：CSV / Excel / PDF。
- 审计凭证：区块链存证（可选）。

### 9.6 提现流程

```
客户管理员/财务在 PC 后台发起提现申请 → 财务人员审核 → 
  系统触发分账 → 支付渠道专户自动到账 → 客户后台显示到账记录
```

- **发起方**:**客户管理员 / 财务**(在 PC 后台主动发起)。
- **审核方**:同客户财务人员(可配置是否需要审核)。
- 下游角色(子物业 / 子场地)的提现由客户在自有 PC 后台中处理。

## 十、阈值告警与告警推送

### 10.1 一期不做 AI 模型

**重要决策**：一期仅做**阈值告警**，不引入机器学习模型。理由：

- 阈值规则已可覆盖 90% 安全场景。
- AI 模型可作为后续增强功能独立销售。

### 10.2 阈值告警规则

| 告警级别 | 触发条件 | 推送通道 |
| --- | --- | --- |
| 高(自动断电) | 超温 ≥ 70℃ / 短路 / 过流 1.1 倍 / 过压 1.2 倍 | 设备立即断电 + Webhook 推送 + 小程序弹窗 |
| 中 | 空载超时 / 充满未拔 / 充电时长 > 10h(与 § 8.4 自动退款协同:告警推送与超时自动处理并发) | Webhook + 小程序推送 |
| 低 | 功率波动 / 信号弱 / 固件版本低 | Webhook + 后台聚合展示 |

> **告警与异常处理协同关系**:阈值告警属于**信息通知**(推送给 PC 后台/小程序/Webhook);当同一触发条件同时落入异常订单处理范围(§ 8.4)时,**两者并发执行**——告警照常推送,系统按异常订单规则自动处理(自动退款 / 断电等)。

### 10.3 告警 Webhook 推送

外部系统（物业 OA / 监管平台 / 上游业务系统）订阅告警事件：

```
POST <订阅方 URL>
Headers: Authorization: Bearer <subscription_token>
Body: {
  "alert_id": "ALT-2026...",
  "device_id": "...",
  "hardware_vendor_id": "...",     // 设备来自哪家硬件厂（协议级属性）
  "level": "high|medium|low",
  "type": "over_temperature",
  "timestamp": "2026-09-25T21:00:00Z",
  "payload": { ... }
}
```

> `hardware_vendor_id` 在 Webhook 中**仅作为设备来源标识**（用于协议兼容与故障归因），**不是租户标识**。系统内所有数据归属均以"客户 ID"为唯一隔离维度。

**重试策略**：指数退避，最多 3 次。

### 10.4 API 边界

| API 类别 | 用途 | 鉴权 |
| --- | --- | --- |
| 查询 API | 设备状态 / 订单 / 告警 / 统计 | API Key + 签名 |
| 告警 Webhook | 推送告警事件 | 订阅 Token |
| 设备控制 API | 不开放（一期） | - |
| 完整 CRUD API | 不开放（一期） | - |

## 十一、白标配置中心与角色权限

### 11.1 深白标能力(按客户维度)

由于一套系统对应一个客户,**白标按客户维度配置**,每个客户独立一套品牌露出:

| 维度 | 可定制项 |
| --- | --- |
| 品牌 | Logo / 名称 / 应用名称 |
| 视觉 | 主题色 / Icon / 字体 |
| 应用 | 独立**小程序**(每个客户一个);**公众号仅作品牌露出,不接入业务功能** |
| 域名 | 每客户独立子域名 |
| 计费 | 每客户独立计费规则模板 |
| 分账 | 每客户独立分账模板 |

### 11.2 角色与权限

PC 后台使用同一套 UI,通过角色权限区分不同参与方。系统需提供**三层颗粒度**的权限控制:

- **菜单权限(功能级)**:每个角色可见的菜单可配置。
- **数据范围(数据级)**:每个角色可见的数据范围可配置(按项目 / 区域 / 站点 / 设备组)。
- **操作权限(操作级)**:每个角色可执行的操作(查看 / 审核 / 编辑 / 导出 / 删除)可配置。
- **字段级脱敏**:敏感字段(手机号、身份证号、银行卡号、地址等)可按角色配置为完全隐藏 / 部分脱敏(如 `138****1234`)/ 完整可见。
- **审计日志**:所有敏感操作留痕,可追溯到人。

> **关于合伙人 / 区域代理**:不预置该角色。客户如需外部渠道方,自行在组织外管理,本系统不参与。

## 十二、监管对接

### 12.1 对接模式

```
平台 → 标准化数据对象 → 监管平台 (锂康码 / 一网统管 / 消防监管)
```

依据 **GB/T 42236.2—2026** 的四层信息交换体系：

- 信息接入层：用户与设备终端（扫码、NFC、蓝牙）。
- 基础设施层：充电设备、电池、传感器。
- 运营服务层：本平台。
- 数据共享层：第三方监管平台。

### 12.2 必须上报的数据对象

| 对象 | 字段 |
| --- | --- |
| 运营商信息 | vendor_id / 名称 / 联系人 |
| 站点信息 | 站点 ID / 名称 / 地址 / 经纬度 / 服务类型 |
| 设备信息 | device_id / 型号 / 协议 / 固件版本 |
| 订单信息 | 订单 ID / 起止时间 / 电量 / 金额 |
| 告警信息 | 告警 ID / 类型 / 级别 / 时间 |
| 电池信息 | 电池编码 / SOC / 健康度（如有） |

### 12.3 推送方式

- HTTP/HTTPS POST + 签名认证。
- 国密 SM2/SM4（按客户要求可选）。
- 失败重试 + 离线缓存。

## 十三、部署与运维要求

### 13.1 部署形态

- **单客户单部署**：每个客户独立一套部署。
- 客户**自行采购**云服务器、数据库、域名、备案。
- 提供一键部署包与文档，运维门槛尽量低。

### 13.2 升级与运维

- **基础买断**:一次性交付,含部署文档与培训。
- **运维订阅**:按年付费,包含远程技术支持、版本升级、二开支持。
- **升级方式**:每客户独立升级,人工调度;**不提供集中升级工具**(每个客户的部署包独立交付、独立升级)。
- 多客户场景下我们提供部署文档与运维手册,**不集中管理客户数据**。

### 13.3 业务连续性要求

- SLA ≥ 99.5%(单机部署实际可达 99.9%)。
- **数据保留 ≥ 3 年**(账务与合规底线)。
- 备份策略:每日全量 + 周期性增量,**异地存储**。
- 故障恢复时间目标(RTO)≤ 4 小时。
- 数据恢复点目标(RPO)≤ 1 小时。

## 十四、安全与合规要求

### 14.1 安全等级

按 **等保三级** 要求设计与实施:

- 设备接入认证(基于 device_id + 平台侧凭证,详细认证机制见《技术规格文档》)。
- 平台双因素认证(管理员登录)。
- 敏感数据加密(传输 + 存储)。
- 操作日志、审计日志留存 ≥ 180 天。
- 数据本地化(部署在客户所在地)。
- 个人信息保护法合规(实名信息加密、用户授权)。

### 14.2 业务可用性

- 充电响应时间：从扫码到启动充电 ≤ 3 秒。
- 计费响应：订单完成后 ≤ 1 秒推送账单。
- 告警响应：阈值越界到推送 ≤ 5 秒。

## 十五、业务边界与不做事项

- **不做硬件制造**:本系统为纯软件产品,**不绑定任何硬件厂商**——但通过协议适配器支持多家硬件厂协议。
- **不做 C 端换电业务**:渗透率低,套餐敏感,本系统不进入。
- **不做电池梯次利用 / 拆解**:仅做溯源与数据开放。
- **不做保险产品**:仅做数据开放与流量分发。
- **不做整车销售 / 二手车交易**。
- **不做 AI 模型训练 / 推理**(一期仅阈值告警)。
- **不进入海外市场**(一期):所有支付、合规、监管对接均针对中国大陆。
- **不做合伙人 / 区域代理管理**:完全外自管理,系统不内置渠道角色与多级分账。
- **不做电网 / 物业缴费接口集成**(模式 B):系统仅记账,不介入电费资金流;电费结算由客户/物业与电网自行处理。
- **不做 OTA 灰度发布**:桩端固件 OTA 全量发布,失败自动回滚;灰度试点由客户在自有小范围预发布完成,系统不提供灰度机制。
- **不做运维工单系统**:仅阈值告警 + 处理记录留痕;不提供派单、流转、SLA 等工单能力。
- **不做预约充电 / 定时充电**:仅支持扫码即充,充电启动后由用户主动结束或充满自停。
- **不做用户实名认证**:基于微信 openid 隐式身份,不要求身份证号绑定;**手机号绑定为可选**(详见 § 5.2)。
- **不做第三方导航 SDK 集成**:找桩地图跳转系统地图或微信内置地图。
- **不做评价公开**:充电评价仅 PC 后台留存,不对外公开显示。
- **不做集中升级工具**:每个客户独立升级,系统不提供多客户集中管理后台。
- **不做客户类型差异化配置**:物业 / 运营商 / 政府 / 国资 一套配置覆盖,不做预设模板区分。
